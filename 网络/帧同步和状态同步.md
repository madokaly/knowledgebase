可以把**帧同步（Frame Synchronization / Lockstep）**和**状态同步（State Synchronization / State Replication）**理解成多人联机游戏里两种完全不同的网络同步思路：

> **帧同步：同步“玩家做了什么”。**  
> **状态同步：同步“游戏世界现在是什么样”。**

它们的最终目标都是：

> 让不同客户端看到的游戏世界尽可能一致。

但实现方式、服务器职责、带宽消耗、延迟表现、作弊风险、适用游戏类型都差很多。

---

# 一、先用一个最直观的例子

假设有两个玩家：

```
玩家A
玩家B
```

场景里有一个角色，玩家 A 按下：

```
W
```

角色要往前走。

---

## 1. 帧同步怎么做

客户端不会告诉其他人：

```
我的角色现在坐标是：
(100, 0, 50)
```

而是告诉服务器：

```
第 1000 帧：
玩家A输入 = W
```

服务器再广播：

```
第1000帧：

玩家A：W
玩家B：无输入
```

然后：

```
客户端A
客户端B
服务器（有时服务器不跑完整逻辑）
```

都执行同样的逻辑：

```
if (Input == W)
{
    Player.MoveForward();
}
```

因为：

```
初始状态相同
+
输入相同
+
逻辑相同
=
最终状态相同
```

这就是帧同步最核心的思想：

> **同步输入，不同步结果。**

---

# 二、状态同步怎么做

状态同步则完全不同。

玩家 A 按下：

```
W
```

客户端可以把输入发给服务器：

```
MoveForward
```

然后真正的游戏状态由服务器计算：

```
Server:

PlayerA.Position =
(100.5, 0, 50)
```

服务器之后把结果发给客户端：

```
PlayerA Position = (100.5, 0, 50)

PlayerA HP = 800

PlayerA State = Running
```

客户端收到以后：

```
更新角色状态
```

所以：

> **状态同步同步的是“结果”。**

---

# 三、一句话区别

可以先牢牢记住这两句话：

```
帧同步：

同步 Input
输入 → 本地执行游戏逻辑 → 得到状态
```

而：

```
状态同步：

同步 State
服务器执行游戏逻辑 → 得到状态 → 发给客户端
```

画成图就是：

```
帧同步：

Player Input
     ↓
   Server
     ↓
Input Frame
     ↓
 ┌───┼───┐
 ↓   ↓   ↓
A    B    C
 ↓   ↓   ↓
Game Simulation
 ↓   ↓   ↓
Same State
```

状态同步：

```
Player Input
     ↓
   Server
     ↓
Server Simulation
     ↓
Game State
     ↓
 ┌───┼───┐
 ↓   ↓   ↓
A    B    C
```

# 四、什么是“帧”

这里有一个很容易误解的问题：

> 帧同步里的“帧”，不一定等于渲染帧。

例如游戏：

```
渲染帧率：
144 FPS

逻辑帧率：
30 FPS
```

帧同步真正同步的一般是：

```
Logic Tick
逻辑帧
```

例如：

```
LogicFrame = 1000
```

这一帧包含：

```
Frame 1000
{
    Player1 = Attack
    Player2 = MoveLeft
    Player3 = Skill1
}
```

下一帧：

```
Frame 1001
{
    Player1 = MoveForward
    Player2 = None
    Player3 = Dodge
}
```

服务器不断广播：

```
1000
1001
1002
1003
...
```

客户端严格按照：

```
帧号 + 输入
```

执行游戏逻辑。

---

# 五、帧同步的核心原理

帧同步实际上依赖一个非常重要的数学性质：

```
State(t+1)
=
Simulation(
    State(t),
    Input(t)
)
```

中文就是：

> 下一帧状态 = 当前状态 + 当前帧输入经过游戏逻辑计算。

比如：

```
位置(t+1)

=
位置(t)
+
速度 × dt
```

如果：

```
A客户端
B客户端
```

拥有相同的：

```
位置
速度
dt
输入
逻辑
```

理论上得到的：

```
位置(t+1)
```

应该完全一样。

继续执行：

```
Frame 1
Frame 2
Frame 3
...
Frame 10000
```

所有客户端依然应该一致。

这就是：

> **确定性模拟（Deterministic Simulation）**

---

# 六、帧同步最重要的条件：确定性

这也是帧同步最困难的地方。

假设：

```
客户端A：

100帧后
Position = 100.0001
```

客户端B：

```
Position = 100.0002
```

一开始只差：

```
0.0001
```

好像完全无所谓。

但是经过：

```
物理
碰撞
技能判定
AI
移动
随机数
```

之后可能变成：

```
客户端A：

怪物被击中
HP = 500
```

客户端B：

```
怪物没有被击中
HP = 1000
```

然后之后所有逻辑全部不同。

这叫：

> **Desync**
> 
> 中文一般叫：
> 
> **不同步 / 逻辑分叉**

---

# 七、为什么浮点数会导致帧同步问题

帧同步中特别怕：

```
float
double
```

因为不同：

```
CPU
编译器
平台
SIMD
浮点优化
指令集
```

可能产生微小误差。

比如：

```
float a = 0.1f;
float b = 0.2f;

float c = a + b;
```

理论：

```
0.3
```

实际上浮点表示可能类似：

```
0.3000000119
```

不同平台、不同优化路径，又可能产生不同舍入结果。

如果游戏里做：

```
if (distance < 1.0f)
{
    Hit();
}
```

两个客户端分别算出：

```
客户端A：
distance = 0.9999999

客户端B：
distance = 1.0000001
```

结果：

```
A：
Hit

B：
Miss
```

游戏状态从这里开始彻底分叉。

---

# 八、因此帧同步经常使用定点数

一种经典解决方案：

> Fixed Point  
> 定点数

比如不用：

```
float position = 1.234f;
```

而是：

```
int position = 1234;
```

规定：

```
1000 = 1米
```

那么：

```
1234

实际表示：

1.234 米
```

所有计算用整数：

```
position += velocity;
```

整数运算非常容易保证：

```
Windows
Android
iOS
Xbox
PS
```

结果一致。

这就是很多帧同步游戏会自己实现：

```
Fixed32
Fixed64
FixedVector2
FixedVector3
FixedQuaternion
```

的原因。

---

# 九、随机数也必须确定

例如技能暴击：

```
if (Random.Range(0, 100) < 20)
{
    Critical();
}
```

如果：

```
客户端A：
Random = 10

客户端B：
Random = 80
```

那么：

```
A暴击
B没暴击
```

瞬间 Desync。

因此帧同步不能随便使用：

```
UnityEngine.Random
std::rand()
```

而通常使用：

> **确定性随机数生成器 PRNG**

例如：

```
RandomSeed = 123456
```

然后：

```
第1次：

65

第2次：

12

第3次：

98
```

所有客户端只要：

```
Seed相同
调用顺序相同
```

就能得到完全一样的随机数。

# 十、帧同步服务器通常在干什么

经典 Lockstep 模型下，服务器主要负责：

```
收集输入
↓
排序输入
↓
打包成逻辑帧
↓
广播给所有客户端
```

例如：

```
Server Frame 1000

PlayerA:
MoveForward

PlayerB:
Attack

PlayerC:
Skill2
```

然后广播：

```
Frame 1000
```

服务器甚至可以：

> 不执行完整战斗模拟。

这也是传统帧同步服务器成本低的重要原因。

# 十一、经典帧同步流程

假设：

```
逻辑帧率 = 30 FPS
```

每：

```
33.33ms
```

一个逻辑帧。

---

## Step 1

玩家点击攻击：

```
Client A

Input:
Attack
```

---

## Step 2

发送给服务器：

```
PlayerId = A
Frame = 500
Command = Attack
```

---

## Step 3

服务器收集所有人的输入：

```
Frame 500

A = Attack
B = MoveLeft
C = None
```

---

## Step 4

服务器广播：

```
Frame 500
{
    A Attack
    B MoveLeft
    C None
}
```

---

## Step 5

所有客户端执行：

```
Simulate(Frame500);
```

最终：

```
客户端A状态
=
客户端B状态
=
客户端C状态
```

理论上应该完全一致。

# 十二、传统 Lockstep 最大的问题：等人

最经典的帧同步叫：

> **Lockstep**
> 
> 锁步同步

意思是：

```
所有玩家一起走
```

比如：

```
Frame 1000
```

必须收齐：

```
A输入
B输入
C输入
```

才能执行：

```
Frame 1000
```

如果 C 网络延迟突然：

```
300ms
```

那么：

```
A
B
```

可能都要等：

```
C
```

于是：

> 一个人卡，全房间卡。

经典 RTS：

```
Warcraft
StarCraft
Age of Empires
```

早期很多都是类似 Lockstep。

# 十三、现代帧同步会怎么优化

现代帧同步通常不会简单地：

```
等所有玩家输入
```

而是加入：

```
输入预测
Rollback
快照
重演
```

其中最重要的就是：

> **Rollback**
> 
> 回滚同步

# 十四、Rollback 是什么

假设：

```
当前已经模拟到：
Frame 105
```

但你还没收到：

```
PlayerB Frame100
```

的输入。

可以暂时预测：

```
B Frame100 = NoInput
```

然后继续运行：

```
100
101
102
103
104
105
```

后来网络包到了：

```
B Frame100 = Attack
```

发现：

```
预测错了。
```

那么：

```
回滚到 Frame99
```

重新执行：

```
Frame100
Frame101
Frame102
Frame103
Frame104
Frame105
```

这个过程：

```
Rollback
+
Resimulation
```

中文可以理解：

```
状态回滚
+
重新模拟
```

---

# 十五、格斗游戏为什么特别喜欢 Rollback

比如格斗游戏：

```
Player1 Punch
```

如果等待网络确认：

```
Input
↓
网络
↓
服务器
↓
返回
↓
角色出拳
```

可能产生：

```
100ms
```

操作延迟。

格斗游戏会感觉非常难受。

Rollback 的思路：

```
玩家按 Punch

↓
立即出拳
```

然后再等待远端输入。

如果预测正确：

```
什么都不用做
```

预测错：

```
Rollback
```

玩家获得：

> 非常好的本地输入响应。

因此很多现代格斗游戏采用：

```
Rollback Netcode
```

# 十六、帧同步的优势

## 1. 带宽非常小

例如一个玩家输入：

```
MoveDirection = 2 bytes
SkillID = 1 byte
Flags = 1 byte
```

可能：

```
4 Bytes
```

10 个玩家：

```
40 Bytes / Frame
```

即使：

```
30 Tick
```

数据量也不大。

---

## 2. 很容易做录像

这是帧同步的巨大优势。

只要保存：

```
初始状态
+
所有输入帧
```

就可以重新播放整场游戏。

例如：

```
Replay
{
    RandomSeed
    MapConfig

    Frame1 Input
    Frame2 Input
    Frame3 Input
    ...
}
```

重新模拟即可。

所以：

```
MOBA录像
RTS录像
```

特别适合帧同步。

---

## 3. 很容易做观战

观战者：

```
下载初始状态
+
输入流
```

然后自己模拟。

---

## 4. 服务器带宽低

因为服务器不需要一直同步：

```
100个角色的位置
血量
速度
动画
状态
```

只同步：

```
玩家输入
```

---

# 十七、帧同步的缺点

帧同步最大的难点其实不是网络，而是：

> **确定性模拟。**

特别是：

```
大型3D物理世界
UE Chaos
Unity PhysX
复杂AI
大量布料
复杂碰撞
```

想做到跨平台完全确定性非常困难。

尤其是：

```
Windows
Android
iOS
PS5
Xbox
```

全部保证：

```
Frame100000

所有状态一模一样
```

工程成本非常高。

# 十八、再来看状态同步

状态同步的核心思想：

> **服务器是权威世界。**

通常叫：

> **Authoritative Server**

> 权威服务器

# 二十一、但是状态同步不能直接瞬移

假设服务器：

```
20 Tick
```

即：

```
50ms
```

同步一次位置。

客户端收到：

```
Packet1

X = 10
```

50ms 后：

```
Packet2

X = 11
```

如果客户端直接：

```
transform.position = serverPosition;
```

看到的就是：

```
10
↓
突然跳
↓
11
↓
突然跳
↓
12
```

角色会一卡一卡。

所以状态同步必须配合：

> **插值（Interpolation）**

# 二十二、插值

服务器给：

```
t0:
Position = 10
```

下一包：

```
t1:
Position = 11
```

客户端不是瞬移：

```
10 → 11
```

而是在多个渲染帧中：

```
10
10.1
10.2
10.3
...
10.9
11
```

例如：

```
Position =
Lerp(
    StateA.Position,
    StateB.Position,
    Alpha
);
```

这样就平滑了。

# 二十三、状态同步通常会故意显示“过去”

这是非常重要的网络游戏设计。

假设服务器：

```
Tick 20Hz
```

客户端为了保证已经拥有：

```
StateA
StateB
```

两个状态，可以故意：

```
落后服务器 100ms
```

显示。

例如：

```
Server Time:
10.0s

Client Render Time:
9.9s
```

客户端始终在：

```
已知历史状态
```

之间插值。

于是非常平滑。

这个叫：

> **Interpolation Buffer**
> 
> 插值缓冲区

# 二十四、那自己的角色怎么办

问题来了。

如果：

```
玩家按 W
```

必须：

```
Client → Server
```

服务器处理：

```
Server → Client
```

然后角色才动。

假设 Ping：

```
100ms
```

那么按 W 后：

```
100ms
```

角色才开始走。

操作手感会非常差。

所以现代状态同步几乎都会使用：

# 二十五、客户端预测

玩家按：

```
W
```

```

```

也就是：

```

```

> **Server Reconciliation**
> 
> 服务器校正 / 客户端纠正

# 二十八、状态同步还有一个重要技术：Lag Compensation

例如 FPS：

你看到敌人在：

```
位置A
```

你开枪。

但网络有：

```
100ms Ping
```

服务器收到你的开枪消息时：

```

```

```

```

```

```

因此服务器可能：

```

```

```
回退到玩家开枪时看到的时间点
```

然后判断命中。

这叫：

> **Lag Compensation**
> 
> 延迟补偿

或者：

> **Server-side Rewind**
> 
> 服务器回溯

# 四十三、两者在作弊方面的区别

传统纯帧同步：

客户端自己计算：

```
伤害
碰撞
移动
```

如果客户端被修改：

```
模拟逻辑
```

可能存在作弊风险。

但现代帧同步服务器也可以：

```
Server Simulation
```

然后做：

```
State Hash
```

校验客户端。

例如客户端每：

```
100帧
```

上传：

```
WorldStateHash
```

服务器发现：

```
ClientA:
AB1234

ClientB:
AB1234

ClientC:
FF9999
```

说明：

```
ClientC可能Desync或者作弊
```

因此：

> 帧同步并不等于服务器无法防作弊。

只是强权威状态同步通常更自然。

# 四十四、State Hash 是什么

假设游戏状态：

```
Player1 HP
Player1 Position

Player2 HP
Player2 Position

Monster HP

RandomSeed
```

组合起来计算：

```
Hash
```

例如：

```
CRC32
XXHash
```

得到：

```
0xAF92128C
```

如果所有客户端：

```
Hash相同
```

基本说明：

```
当前模拟状态一致
```

帧同步调试里：

> State Hash / Frame Hash

非常重要。

因为如果出现：

```
10000帧
```

的录像不同步，可以逐帧找：

```
Frame5000 Hash一致
Frame5001 Hash一致
Frame5002 Hash不一致
```

那么：

> Desync 就发生在 Frame5002。

# 四十五、面试最容易问的核心问题

如果面试官问：

> 帧同步和状态同步有什么区别？

可以直接回答：

> **帧同步主要同步玩家输入，所有客户端基于相同初始状态和相同输入执行确定性的游戏逻辑，因此需要严格保证确定性；优点是带宽低、录像和观战容易，缺点是确定性要求高，复杂物理和跨平台实现困难。**
> 
> **状态同步则由服务器作为权威端执行游戏逻辑，并把位置、血量、状态等结果同步给客户端。优点是服务器权威、适合复杂3D游戏，缺点是带宽和服务器压力更大，并需要插值、客户端预测和服务器校正来解决网络延迟和画面卡顿。**

这已经是一个比较标准的回答。

# 四十七、三个概念一定要区分

你之后学网络同步时，经常会看到：

```
Interpolation
Prediction
Rollback
```

这三个很容易混。

可以这样理解：

### Interpolation 插值

```
我已经知道过去两个状态。

A -------- B
     ↑
   插值
```

重点：

> 已知状态之间求平滑状态。

---

### Prediction 预测

```
我只知道当前状态。

A -------- ?
           ↑
         猜未来
```

重点：

> 根据当前状态预测未来。

---

### Rollback 回滚

```
过去预测错了：

100
101
102
103
 ↓

回到100

重新执行
```

重点：

> 回到历史状态重新模拟。
