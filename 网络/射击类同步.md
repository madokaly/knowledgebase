射击类游戏，尤其是 **FPS / TPS / 联机动作射击**，通常不会单纯使用“帧同步”或“状态同步”中的某一种，而是采用：

> **服务器权威状态同步 + 客户端预测 + 服务器校正 + 插值 + 延迟补偿**

这是目前实时射击游戏里最常见的方案。

你可以把整个同步系统拆成 4 个问题：

1. **自己怎么移动才不延迟？**
2. **别人怎么移动才不抖？**
3. **开枪到底算没算打中？**
4. **服务器和客户端结果不一致怎么办？**

---

# 一、先给结论：射击游戏通常怎么同步

一个典型 FPS 架构大概是：

```
                   输入
客户端A ───────────────────────→ 服务器
  │                                │
  │ 本地立即预测移动               │ 权威模拟
  │                                │
  │ ←────── 权威位置/状态 ─────────│
  │
  │ 误差修正 / Reconciliation
  ↓

客户端A看到自己：客户端预测
客户端A看到别人：服务器状态 + 插值

开枪：
客户端A立即播放枪口火焰、后坐力
        ↓
发送开枪请求
        ↓
服务器回溯历史位置
        ↓
服务器判断是否命中
        ↓
服务器同步伤害结果
```

所以：

```
本地玩家：
Client Prediction
客户端预测

远程玩家：
Interpolation
插值

状态错误：
Server Reconciliation
服务器校正

射击判定：
Server Authority
服务器权威

高延迟命中：
Lag Compensation
延迟补偿 / 服务器回溯
```

---

# 二、为什么射击游戏很少使用纯帧同步

先复习两个概念。

## 1. 帧同步

帧同步不是同步角色位置，而是同步：

```
玩家输入
```

例如：

```
Frame 100

Player A:
MoveForward = 1
Fire = true

Player B:
MoveForward = 0
Fire = false
```

所有客户端执行同样的逻辑：

```
输入
↓
游戏模拟
↓
得到相同结果
```

这种方案很适合：

```
RTS
MOBA
格斗
部分动作游戏
```

但 FPS 有几个问题。

### 问题1：FPS非常依赖实时响应

如果必须等服务器确认：

```
按 W
↓
发送服务器
↓
服务器确认
↓
客户端移动
```

假设 Ping = 100ms。

你按：

```
W
```

可能 50~100ms 后角色才开始动。

射击游戏会感觉非常明显：

```
操作迟钝
```

---

### 问题2：物理模拟很难完全确定

例如：

```
角色碰撞
刚体
子弹
布娃娃
PhysX
浮点运算
```

不同机器可能出现：

```
0.000001
```

级别的误差。

随着帧数累积：

```
客户端A：
Position = 10.01

客户端B：
Position = 10.07
```

最终：

```
状态漂移
```

---

### 问题3：人数和世界状态复杂

FPS 可能同步：

```
玩家
武器
子弹
载具
掉落物
门
炸弹
可破坏物
AI
```

纯 Deterministic Lockstep：

```
确定性帧同步
```

实现成本非常高。

所以主流射击游戏更多使用：

> **服务器权威状态同步**

---

# 三、服务器权威状态同步

核心思想：

> **服务器的世界才是真实世界。**

客户端只是：

```
表现 + 输入 + 预测
```

服务器负责：

```
角色位置
血量
伤害
死亡
弹药
武器状态
命中判定
游戏规则
```

例如：

客户端：

```
我按了 W
```

发送：

```
Input
{
    MoveForward = 1;
    Tick = 1024;
}
```

服务器收到：

```
Input
↓
模拟角色移动
↓
Position = (100, 20, 5)
```

然后服务器广播：

```
PlayerA
Position = (100,20,5)
Rotation = ...
Velocity = ...
```

客户端更新。

---

# 四、问题来了：这样移动不会延迟吗？

会。

如果完全按照服务器状态：

```
Client
  按W
   ↓
网络
   ↓
Server
计算移动
   ↓
网络
   ↓
Client
显示移动
```

Ping = 100ms：

```
至少 ~100ms 响应延迟
```

FPS 基本没法玩。

因此需要：

# Client Prediction

也就是：

> **客户端预测**

---

# 五、本地玩家：Client Prediction 客户端预测

假设你按：

```
W
```

客户端不会等服务器。

而是：

```
按 W
↓
客户端立即移动
↓
同时把输入发服务器
```

例如：

```
void PlayerInput()
{
    MoveForward();

    SendInputToServer();
}
```

于是：

```
客户端画面：

按 W
↓
立刻移动
```

几乎：

```
0ms 操作延迟
```

服务器同时收到：

```
Input #100
Input #101
Input #102
```

然后服务器独立计算：

```
真实位置
```

---

# 六、服务器校正 Server Reconciliation

问题是：

客户端预测：

```
Position = 10.5
```

服务器算出来：

```
Position = 10.2
```

谁对？

答案：

```
服务器
```

所以服务器会发：

```
Server State

Tick = 100
Position = 10.2
```

客户端需要修正。

但这里不能简单：

```
transform.position = serverPosition;
```

否则角色会：

```
瞬移
抖动
拉扯
```

因此会使用：

> Server Reconciliation

服务器校正。

---

# 七、Reconciliation 是怎么做的

客户端需要保存：

```
历史输入
```

例如：

```
Input 100 → W
Input 101 → W
Input 102 → W
Input 103 → W
```

服务器告诉客户端：

```
我已经处理到 Input 101

Position = 10
```

客户端当前已经预测到：

```
Input 103

Position = 12
```

客户端做：

```
Step 1

恢复服务器状态

Position = 10
```

然后重新执行：

```
Input 102
Input 103
```

得到：

```
Position = 12
```

这就是：

> Replay Unacknowledged Inputs

重新执行服务器尚未确认的输入。

# 八、完整流程

假设：

```
Client Tick 100
```

玩家按 W。

客户端：

```
Input100
↓
本地执行
↓
Position = 1

发送 Input100
```

下一帧：

```
Input101
↓

```

下一帧：

```

↓
Position = 3
```

这时候服务器回复：

```
服务器：

Input100已经执行完

Position = 0.9
```

客户端：

```
当前预测：
3

服务器：
0.9
```

客户端：

```
恢复：
0.9

重新执行：
Input101
Input102
```

得到：

```
2.9
```

于是修正到：

```
2.9
```

而不是直接回：

```

```

# 九、为什么远程玩家不能 Client Prediction

你可以预测：

```
自己
```

因为你知道自己的输入：

```
W
A
鼠标移动
Space
```

但是你不知道别人下一帧会干什么。

比如敌人：

```
现在向左跑
```

下一帧可能：

```
继续左跑
急停
右转
跳跃
蹲下
开枪
```

所以：

```
远程玩家
```

通常不用 Client Prediction。

而是：

> Snapshot Interpolation

状态快照插值。

---

# 十、远程玩家：Interpolation 插值

服务器例如：

```
20Hz
```

更新玩家状态。

即：

```
每 50ms 一个状态
```

服务器发送：

```
Snapshot 100
Position = 0

Snapshot 101
Position = 1

Snapshot 102
Position = 2
```

如果客户端直接显示：

```
0
↓
1
↓
2
```

会变成：

```
瞬移
瞬移
瞬移
```

所以客户端会：

> 故意晚一点显示其他玩家。

例如服务器当前：

```
Server Time = 10.0s
```

客户端显示：

```
9.9s
```

也就是：

```
100ms过去的世界
```

于是客户端通常拥有：

```
Snapshot A
Snapshot B
```

然后：

```
Position = Lerp(A.Position, B.Position, t);
```

形成平滑运动。

---

# 十一、为什么要故意晚 100ms

这其实非常重要。

假设服务器状态：

```
t=1.0
位置 0

t=1.05
位置 1
```

客户端想显示：

```
t=1.025
```

就可以：

```
Lerp(0,1,0.5)
```

得到：

```
0.5
```

但是如果客户端显示的是服务器“现在”：

```
t=1.05
```

那么：

```
下一个状态还没收到
```

无法插值。

所以需要：

```
Interpolation Buffer
插值缓冲区
```

# 十二、射击游戏里的核心时间线

实际上客户端看到的是三个不同时间。

```
                时间轴 →

服务器：
------------------------- NOW

自己：
------------------------- NOW
        ↑
Client Prediction

敌人：
------------------- NOW
            ↑
       比服务器落后 ~100ms
       Interpolation
```

也就是说：

```
自己：
预测未来一点

敌人：
显示过去一点

服务器：
权威现在
```

这是 FPS 网络同步一个非常核心的概念。

# 十三、然后出现射击游戏最难的问题

假设：

```
Ping = 100ms
```

你屏幕看到敌人在：

```
位置 X
```

你瞄准：

```
头
```

然后点击鼠标。

但是请求到服务器时：

```
50ms过去了
```

敌人在服务器已经跑到了：

```
位置 Y
```

服务器如果直接判断：

```
Raycast
```

就会发现：

```
没打中
```

玩家会说：

> 我明明瞄准他了。

所以 FPS 需要一个非常重要的技术：

# Lag Compensation

也就是：

> 延迟补偿

# 十四、Lag Compensation 服务器回溯

服务器保存：

```
玩家过去一段时间的历史状态
```

例如：

```
Time 10.00
PlayerB Position = 10

Time 10.05
PlayerB Position = 11

Time 10.10
PlayerB Position = 12

Time 10.15
PlayerB Position = 13
```

客户端开枪时告诉服务器：

```
ShotTime = 10.05
```

服务器现在：

```
10.15
```

服务器不会直接用：

```
Position = 13
```

判断。

而是：

```
Rewind World
```

把玩家回滚到：

```
10.05
```

也就是：

```
Position = 11
```

然后执行：

```
Raycast
```

看看当时是不是命中。

这叫：

```
Server Side Rewind
服务器回溯
```

# 十五、为什么不是客户端直接告诉服务器“我打中了”

因为会作弊。

如果客户端发送：

```

Damage = 100
```

外挂直接发送：

```
我击中了 PlayerB

Damage = 999999
```

甚至：

```
敌人在哪都无所谓

永远爆头
```

所以通常客户端只发送：

```

{
    Origin
    Direction
    Weapon
    Timestamp
}
```

服务器：

```
检查弹药
↓
检查射速
↓
检查武器状态
↓
回滚历史
↓
Raycast
↓
命中检测
↓
计算伤害
```

最终：

```
服务器说打中了
```

才是真的打中。

# 十六、Hitscan 武器怎么同步

Hitscan 就是：

```

例如很多：

# 十七、为什么枪口火焰不能等服务器

因为：

```

```

玩家会感觉枪械：

由服务器决定。

> Client-side responsiveness + Server-side authority

客户端负责响应性，服务器负责权威性。

验证
↓
移动角色
↓
生成 State
```

```
State
{
    LastInput = 100;
    Position = ...
}
```

客户端：

```
收到 State
↓
恢复权威状态
↓
删除 Input <= 100
↓
Replay 剩余Input
```

这就是：

```
Client Prediction
+
Server Reconciliation
```

# 三十三、丢包怎么办

假设：

```
Snapshot100
收到

Snapshot101
丢失

Snapshot102
收到
```

客户端可能：

```
100 → 102
```

继续插值。

如果太久没有新包：

```
Extrapolation
外推
```

例如：

```
Position =
    LastPosition +
    Velocity * dt;

```

# 三十四、Interpolation 和 Extrapolation 区别

Interpolation：

```
已知：

A -------- B
     ↑
   求这里
```

两个状态都知道。

所以：

```
非常稳定
```

---

Extrapolation：

```
已知：

A -------- ?
           ↑
         猜这里
```

根据：

```
Velocity
Direction
Acceleration
```

猜未来。

容易错。

因此：

```
FPS更偏向：

Interpolation
```

而不是长期：

```
Extrapolation
```

# 三十六、时间同步

# 三十九、Lag Compensation 也有问题

假设：

```
玩家A Ping 200ms
玩家B Ping 20ms
```

玩家B已经跑进墙后面。

但玩家A屏幕里：

```
玩家B还没进墙
```

A开枪。

服务器回滚：

```
200ms
```

发现：

```
当时B确实在墙外
```

于是服务器判：

```
命中
```

B会感觉：

> 我都进掩体了为什么还能被打死？

这就是经典：

```
Die Behind Cover
躲到墙后还被击杀
```

这是 Lag Compensation 的副作用。
