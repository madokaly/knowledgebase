动作类战斗游戏的网络同步，实际很少只用“帧同步”或者只用“状态同步”。尤其是《鸣潮》《原神》这类第三人称动作游戏、ARPG、多人 Boss 战，通常都是：

> **服务器权威 + 状态同步为主 + 客户端预测 + 插值 + 局部事件同步 + 必要时回滚/校正。**

可以把它理解成一种**混合同步方案**。

---

## 一、动作游戏到底需要同步什么

动作游戏和普通 MMO 最大区别是：

**战斗过程非常连续，而且玩家对延迟极其敏感。**

比如玩家按下攻击键：

```
玩家输入
 ↓
角色前摇
 ↓
位移
 ↓
攻击判定
 ↓
命中敌人
 ↓
伤害
 ↓
击退 / 硬直
 ↓
特效 / 音效
```

这些内容不应该全部按照同一种方式同步。

通常会拆成：

|内容|常见同步方式|
|---|---|
|玩家输入|输入同步 / RPC|
|角色位置|状态同步 + 预测|
|角色旋转|状态同步 + 插值|
|动画状态|事件同步 / 状态同步|
|技能释放|事件同步|
|攻击命中|服务器判定|
|伤害|服务器权威|
|Buff / Debuff|状态同步|
|Boss AI|服务器运行|
|敌人位置|Snapshot 状态同步|
|子弹|状态同步 / 客户端模拟|
|特效|客户端本地播放|
|音效|客户端本地播放|
|受击反馈|本地预测 + 服务器确认|

所以动作游戏本质上是：

```
逻辑层：服务器权威

表现层：客户端尽量自己演
```

# 二、动作游戏常见的 5 种同步技术

先建立整体概念。

```
动作游戏同步
│
├─ 1. 状态同步 Snapshot
│
├─ 2. 输入同步 Input Sync
│
├─ 3. 客户端预测 Client Prediction
│
├─ 4. 服务器校正 Server Reconciliation
│
└─ 5. 插值 Interpolation
```

复杂项目还会增加：

```
Rollback
Lag Compensation
Dead Reckoning
Event Replication
Interest Management
```

# 三、状态同步：动作游戏最常见的基础方案

所谓状态同步，就是服务器直接告诉客户端：

> 角色现在是什么状态。

例如：

```
struct PlayerState
{
    Vector3 Position;
    Vector3 Velocity;
    Quaternion Rotation;

    int HP;

    int AnimState;

    int SkillID;

    bool IsGrounded;
};
```

服务器可能：

```
20Hz
30Hz
60Hz
```

周期性发送：

```
玩家A：
Position = (10, 0, 20)
Rotation = 90°
Velocity = (3,0,5)
HP = 800
State = Attack
```

客户端收到后更新。

流程：

```
Client Input
     │
     ▼
Server
     │
计算逻辑
     │
     ▼
World State
     │
     ▼
Snapshot
     │
     ▼
Clients
```

例如：

```
服务器 Tick 1000

PlayerA:
Pos = 100
HP = 1000

服务器 Tick 1001

PlayerA:
Pos = 101
HP = 850
```

客户端只需要接收：

```
位置
血量
状态
技能
```

因此叫：

> **State Synchronization 状态同步**

# 四、为什么不能直接靠状态同步

假设客户端 → 服务器延迟：

```
Ping = 100ms
```

玩家按：

```
W
```

如果完全服务器权威：

```
0ms
玩家按 W

50ms
服务器收到

服务器计算角色移动

100ms
客户端收到位置

角色开始移动
```

玩家会感觉：

```
按 W

......

角色才走
```

这对于动作游戏几乎不可接受。

因此必须使用：

# 客户端预测

# 五、客户端预测 Client Prediction

客户端不会等服务器。

玩家按：

```
W
```

客户端立即：

```
MoveForward();
```

因此：

```
Input
 │
 ├────────────► 本地立即执行
 │
 └────────────► 发送服务器
```

完整流程：

```
        玩家输入
           │
      ┌────┴────┐
      │         │
      ▼         ▼
客户端预测     Server
      │         │
角色立即移动    权威计算
      │         │
      └────┬────┘
           ▼
       Server State
           │
           ▼
        校正客户端
```

例如：

客户端预测：

```
Position = 10.2
```

服务器返回：

```
Position = 10.18
```

差距很小：

```
Client : 10.2
Server : 10.18
```

那么缓慢修正。

# 六、服务器校正 Server Reconciliation

假设：

客户端预测：

```
Pos = 10
```

服务器认为：

```
Pos = 9
```

就发生：

```
Client
10

Server
9
```

不能直接：

```
transform.position = serverPosition;
```

否则角色会：

```
瞬移
抖动
拉扯
```

也就是常说的：

> 橡皮筋效应 Rubber Banding

所以通常：

```
if (Error < SmallThreshold)
{
    // 不处理
}
else if (Error < LargeThreshold)
{
    // 平滑修正
    SmoothCorrection();
}
else
{
    // 差距太大，直接纠正
    SnapToServer();
}
```

例如：

```
误差 < 5cm
忽略

误差 5cm ~ 1m
平滑拉回

误差 > 1m
直接校正
```

实际项目阈值取决于：

```
角色速度
网络质量
战斗精度
游戏类型
```

# 七、输入序号：动作同步里非常关键

客户端发送输入时不会只发：

```
MoveForward
```

通常还会带：

```
Sequence ID
Tick
Timestamp
```

例如：

```
struct PlayerInput
{
    uint32 Sequence;

    float MoveX;
    float MoveY;

    bool Jump;
    bool Attack;

    float DeltaTime;
};
```

发送：

```
Input 101
Input 102
Input 103
Input 104
```

服务器处理到：

```
102
```

返回：

```
ServerPosition
LastProcessedInput = 102
```

客户端：

```
删除 101
删除 102

重新执行：

103
104
```

这个过程叫：

> **Server Reconciliation**

# 八、Reconciliation 的核心原理

假设：

客户端输入：

```
Input 1 → W
Input 2 → W
Input 3 → W
Input 4 → W
```

客户端已经执行：

```
1
2
3
4
```

服务器只执行到了：

```
1
2
```

服务器返回：

```
Position = P

Ack = 2
```

客户端：

```
先把位置设置成 P

然后重新执行：

Input3
Input4
```

因此：

```
Server State
     │
     ▼
Reset Client
     │
     ▼
Replay Unconfirmed Inputs
     │
     ▼
Correct Position
```

这就是：

> **预测 + 重演未确认输入**

# 九、为什么其他玩家不能用预测

假设：

```
玩家A = 自己

玩家B = 网络玩家
```

玩家A：

```
你知道自己的输入
```

所以可以：

```
预测移动
```

但玩家B：

```
你不知道他下一帧按什么
```

所以无法准确预测。

因此远端玩家主要使用：

> Snapshot Interpolation

# 十、Snapshot 插值

服务器发送：

```
t = 1.0

Pos = 10
```

下一次：

```
t = 1.05

Pos = 12
```

客户端不会直接：

```
10

瞬移

12
```

而是：

```
10

10.4

10.8

11.2

11.6

12
```

也就是：

```
Position = Lerp(
    PreviousState.Position,
    NextState.Position,
    Alpha
);
```

这就是：

> **Interpolation 插值**

# 十一、为什么客户端通常故意落后几十毫秒

这是网络同步里非常重要的思想。

服务器：

```
Snapshot A
100ms

Snapshot B
150ms
```

客户端如果渲染：

```
150ms
```

可能：

```
B 还没收到
```

导致无法插值。

所以客户端可能故意显示：

```
ServerTime - 100ms
```

例如真实服务器：

```
200ms
```

客户端显示：

```
100ms
```

客户端已经拥有：

```
State 80ms

State 130ms
```

因此可以稳定插值：

```
80
 │
 │ interpolation
 ▼
100
 │
 │
 ▼
130
```

所以：

> 远端角色实际通常是“过去的角色”。

例如：

```
Server world:

PlayerB ─────────►

Client sees:

PlayerB
   ↑
大约落后几十~100ms
```

这是用：

```
一点延迟
```

换：

```
平滑
稳定
抗抖动
```

# 十三、攻击判定应该放哪里

动作游戏最重要的问题之一：

```
Hit Detection
```

假设客户端说：

```
我砍中了 Boss
```

如果服务器直接相信：

```
Client:
Boss -1000 HP

Server:
OK
```

作弊程序就可以：

```
Damage = 99999999
```

所以通常：

```
客户端：

“我释放了技能1001”

           ↓

服务器：

检查技能状态
检查冷却
检查位置
检查攻击范围
检查目标
检查命中

           ↓

计算 Damage

           ↓

广播结果
```

即：

```
Client
 │
 │ Attack Request
 ▼
Server
 │
 │ authoritative hit detection
 ▼
Damage Result
 │
 ▼
All Clients
```

关键原则：

> **客户端负责表现，服务器负责结果。**

# 二十、Lag Compensation 延迟补偿

射击、格斗、动作游戏经常有一个问题。

玩家看到：

```
敌人在这里
    ↓
   [B]
```

但服务器此时：

```
B已经移动
           ↓
          [B]
```

原因：

```
网络延迟
```

服务器如果只看当前状态：

```
Miss
```

玩家就会觉得：

```
明明打中了
```

因此服务器保存历史：

```
Time 100
PlayerB Pos = 10

Time 110
PlayerB Pos = 11

Time 120
PlayerB Pos = 12

Time 130
PlayerB Pos = 13
```

玩家A说：

```
我在 Time110 攻击
```

服务器：

```
Rollback World → Time110
```

检查：

```
Attack vs PlayerB
```

这个叫：

> **Lag Compensation 延迟补偿**

注意它和完整的 Rollback Netcode 有区别。

# 二十一、Rollback Netcode

Rollback 更常见于：

```
格斗游戏
```

例如：

```
Street Fighter
Tekken
Guilty Gear
```

核心思路：

```
没有收到对方输入

↓

预测输入

↓

继续运行

↓

收到真实输入

↓

发现预测错误

↓

Rollback

↓

重新模拟
```

例如：

```

预测敌人：
No Input

Frame 105

收到：

Frame100
Enemy Attack
```

那么：

```
恢复 Frame100

↓

执行 Enemy Attack

↓

重新模拟

Frame101
102
103
104
105
```

速度极快，因此玩家可能根本看不出来。

# 二十三、帧同步为什么不一定适合 3D ARPG

经典帧同步：

```
ClientA Input
       │
ClientB Input
       │
       ▼
      Server
       │
 Broadcast Inputs
       │
       ▼
All Clients Simulate
```

服务器只同步：

```

```

例如：

```

PlayerA:
W + Attack

PlayerB:

```

```
同样逻辑
```

```
同样结果
```

```

```

```
+
```

```
AI

NavMesh

动画 RootMotion
```

都有可能产生不同结果。

所以：

> 大型动作游戏更偏向状态同步，而不是纯帧同步。

# 二十八、面试时建议这样回答

如果面试官问：

> 动作游戏通常使用什么同步方式？

可以回答：

> **大型 3D 动作游戏通常以服务器权威的状态同步为基础，同时结合客户端预测、服务器校正、快照插值以及事件同步。玩家自己的移动为了降低输入延迟会进行 Client Prediction，服务器返回权威状态后进行 Reconciliation；远端玩家和怪物因为客户端不知道其输入，一般使用 Snapshot Interpolation。技能伤害、HP、Buff、死亡等关键 Gameplay 状态由服务器权威计算，而动画、特效、音效、镜头震动等表现可以由客户端提前预测执行。FPS 还经常加入 Lag Compensation，而格斗游戏则更适合 Rollback Netcode。**

把这一段说清楚，基本已经覆盖动作游戏网络同步的核心。

最后给你一张最值得记住的结构：

```
                     Server
                 【最终权威世界】
                       │
         ┌─────────────┼─────────────┐
         │             │             │
       Player         Boss         Combat
       State           AI           Damage
         │             │             │
         └─────────────┴─────────────┘
                       │
                    Snapshot
                       │
          ┌────────────┴────────────┐
          ▼                         ▼

       Local Player              Remote Player
          │                          │
          │                          │
 Client Prediction          Snapshot Interpolation
          │                          │
          ▼                          ▼
 Server Reconciliation        Smooth Movement
          │
          ▼
       Low Latency

          + 所有关键结果

       Damage / HP / Death
             │
             ▼
         Server Authority
```

**最核心的四句话：**

```
自己角色 → 预测
其他角色 → 插值

表现 → 客户端
结果 → 服务器
```

这四句话基本就是现代多人动作战斗同步的骨架。
