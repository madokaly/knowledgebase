# 一、HI-Z 是什么？

**HI-Z = Hierarchical Z-Buffer，层次化深度缓冲 / 分层 Z 缓冲。**

它的核心思想非常简单：

> 不要一上来就对每个像素做精确深度比较，而是先用“大块区域”的深度信息做粗粒度判断。

普通 Depth Buffer（深度缓冲）可能是：

```
1920 × 1080
```

HI-Z 会在此基础上构造一个类似 **MipMap（金字塔）** 的深度层级：

```
Mip 0 : 1920 × 1080     // 原始深度
Mip 1 :  960 × 540      // 每 2×2 像素合并
Mip 2 :  480 × 270
Mip 3 :  240 × 135
Mip 4 :  120 × 67
...
Mip N :    1 × 1
```

可以想象成：

```
                ┌────────┐
                │ 1 × 1  │
                └────┬───┘
                     │
              ┌──────┴──────┐
              │    2 × 2    │
              └──────┬──────┘
                     │
            ┌────────┴────────┐
            │      4 × 4      │
            └────────┬────────┘
                     │
        ┌────────────┴────────────┐
        │          8 × 8          │
        └────────────┬────────────┘
                     │
              ......继续展开
                     │
        ┌────────────┴────────────┐
        │      原始 DepthBuffer   │
        │       1920 × 1080       │
        └─────────────────────────┘
```

越往上：

```
分辨率越低
↓
一个像素代表的屏幕区域越大
↓
判断越粗糙
↓
但速度越快
```

这就是 **Hierarchical（层次化）** 的含义。

# 二、为什么需要 HI-Z？

假设屏幕前面有一堵墙：

```
Camera

   ↓

██████████████████
████   墙壁   ████
██████████████████

        ↓

        怪物
        Monster
```

怪物完全在墙后面。

如果没有比较好的遮挡剔除机制，GPU 可能依然经历：

```
怪物 Mesh
    ↓
Vertex Shader
    ↓
三角形装配
    ↓
Rasterization 光栅化
    ↓
产生大量 Fragment
    ↓
Depth Test
    ↓
发现：
"哦，全部被墙挡住了"
    ↓
全部扔掉
```

前面许多工作白做了。

尤其一个模型可能有：

```
100,000 个三角形
几十万个 fragment
```

最后一个像素都看不见。

HI-Z 的目标就是尽量更早发现：

> “这个物体所在的整块屏幕区域已经被更近的东西挡住了。”

那么就可以直接：

```
Object
  ↓
HI-Z 检测
  ↓
完全遮挡
  ↓
Cull
  ↓
后面的工作尽量不做
```

# 三、HI-Z 最核心的数据结构：Depth Pyramid

假设原始深度是：

```
Mip 0：

0.2    0.3    0.4    0.3
0.1    0.4    0.5    0.2
0.3    0.2    0.6    0.4
0.2    0.3    0.5    0.3
```

这里暂时采用传统 Z：

```
Near Plane = 0

Far Plane  = 1

越小 → 越靠近相机
越大 → 越远
```

为了做**保守遮挡剔除**，通常需要知道：

> 这块区域中“最远的那个已写入深度”。

因此传统 Z 下，经常采用：

```
2 × 2 区域
↓
取 Max Depth
```

例如左上角：

```
0.2    0.3
0.1    0.4
```

得到：

```
max = 0.4
```

右上角：

```
0.4    0.3
0.5    0.2
```

得到：

```
max = 0.5
```

于是：

```
Mip 1：

0.4    0.5
0.3    0.6
```

继续向上：

```
Mip 2：

max(
    0.4 0.5
    0.3 0.6
)

= 0.6
```

得到：

```
Mip 0：

0.2 0.3 0.4 0.3
0.1 0.4 0.5 0.2
0.3 0.2 0.6 0.4
0.2 0.3 0.5 0.3

        ↓ Max Reduce

Mip 1：

0.4 0.5
0.3 0.6

        ↓ Max Reduce

Mip 2：

0.6
```

这就是一个简单的 **Hierarchical Depth Pyramid（层次深度金字塔）**。

# 四、为什么传统 Z 要取 Max？

这是理解 HI-Z 最重要的地方之一。

假设某个区域：

```
Depth：

0.2    0.3
0.4    0.5
```

这里：

```
最远深度 = 0.5
```

现在后面有一个物体，它距离相机最近的位置都是：

```
Object Near Depth = 0.7
```

因为：

```
0.7 > 0.5
```

说明物体最近的地方，都比这一块已有深度中最远的位置还要远。

换句话说：

```
已有场景：

0.2
0.3
0.4
0.5

物体：

0.7
```

因此：

```
Object 完全在它们后面
```

可以安全判断：

```
Occluded
// 完全被遮挡
```

所以传统 Z 下，可以理解为：

```
ObjectNearestDepth > HiZ.MaxDepth

              ↓

       可以判断为被遮挡
```

注意这里有一个非常重要的条件：

> 必须是整个物体覆盖的屏幕区域都满足这个条件。

不能只检查某一个像素。

# 五、如果使用 Reversed-Z 呢？

现代引擎非常常见：

```
Reversed-Z
// 反转深度
```

传统 Z：

```
Near = 0
Far  = 1

越大越远
```

Reversed-Z：

```
Near = 1
Far  = 0

越大越近
```

于是刚才的逻辑也反过来了。

传统 Z 用：

```
// 越大代表越远
HiZ = Max(depth);
```

Reversed-Z 通常对应：

```
// 越小代表越远
HiZ = Min(depth);
```

所以不要死记：

> HI-Z 一定取 Max。

更准确的说法应该是：

> 用于保守遮挡判断时，HI-Z 通常需要保存这个区域的“最远深度代表值”。

因此：

|深度方式|Near|Far|“最远”代表值|
|---|---|---|---|
|Traditional Z|0|1|**Max**|
|Reversed-Z|1|0|**Min**|

当然，不同算法用途不同，例如 SSR、SSGI、Ray Marching 等构造的深度金字塔可能选择 Min、Max，甚至同时保存：

```
MinDepth + MaxDepth
```

所以一定结合具体算法看。

# 六、HI-Z 怎么判断一个模型是否被挡住？

这是游戏引擎里非常经典的流程。

例如有一个模型：

```
         ┌───────────────┐
         │               │
         │     Enemy     │
         │               │
         └───────────────┘

              3D AABB
```

首先计算模型的：

```
Bounding Box
// 包围盒
```

然后把包围盒投影到屏幕：

```
World Space
世界空间

      ↓ ViewProjection

Clip Space
裁剪空间

      ↓ Perspective Divide

NDC

      ↓ Viewport Transform

Screen Space
屏幕空间
```

最后得到一个屏幕矩形：

```
┌──────────────────────────┐
│                          │
│     ┌──────────────┐     │
│     │   Enemy      │     │
│     │              │     │
│     └──────────────┘     │
│                          │
└──────────────────────────┘
```

比如占据：

```
ScreenRect：

X = 800 ~ 900
Y = 400 ~ 500
```

大约：

```
100 × 100 pixels
```

---

## 选择合适的 HI-Z 层级

如果直接用 Mip0：

```
100 × 100
= 10,000 个 Depth Sample
```

那失去了 HI-Z 的意义。

所以会选择更高的 Mip。

例如：

```
Mip0：

100 × 100

Mip1：

50 × 50

Mip2：

25 × 25

Mip3：

12 × 12

Mip4：

6 × 6

Mip5：

3 × 3
```

最终可能只需要：

```
4 ~ 9 次 Depth Sample
```

就能判断整个模型是否被遮挡。

这就是 HI-Z 非常快的根本原因：

```
逐像素测试

10000 次
```

变成：

```
粗粒度层级测试

4 ~ 9 次
```

# 七、一个完整例子

假设有一堵墙：

```
Camera
  |
  v

██████████████
████  Wall ███
██████████████

        Enemy
```

墙的深度：

```
0.3
```

Enemy 的 AABB 最近点：

```
0.7
```

投影 Enemy：

```
Screen Rect

┌──────────────┐
│    Enemy     │
└──────────────┘
```

找到一个合适的 HI-Z Mip。

该区域可能得到：

```
0.31   0.32
0.30   0.34
```

传统 Z 使用 Max：

```
MaxDepth = 0.34
```

Enemy 最近深度：

```
EnemyMinDepth = 0.7
```

比较：

```
0.7 > 0.34
```

意味着：

```
Enemy 最近的位置
都比这一块最远的遮挡物还远
```

所以：

```
完全遮挡
↓
Cull
```

# 八、为什么 HI-Z 必须“保守”？

假设：

```
墙
████████
████████

               怪物
             ┌──────┐
             │      │
             └──────┘
```

但其实怪物有一点露出来：

```
████████
████████
       ┌──
       │Enemy
```

这时候你绝对不能把整个怪物 Cull 掉。

否则会出现：

```
模型突然消失
模型闪烁
摄像机移动时物体突然 pop
```

因此遮挡剔除需要：

```
Conservative
// 保守
```

也就是：

```
100% 能证明它被遮挡
    ↓
才剔除

无法证明
    ↓
就当它可见
```

因此 HI-Z 一般允许：

```
本来被挡住了
但没 Cull 掉
```

这种情况只是：

```
性能差一点
```

但尽量不能出现：

```
明明可见
却 Cull 掉
```

因为那会产生画面错误。

# 九、HI-Z 和 Early-Z 到底什么关系？

这是面试非常容易问的地方。

简单理解：

```
HI-Z
    ↓
粗粒度

Early-Z
    ↓
细粒度
```

可以把 GPU 深度测试想象成：

```
Triangle
   ↓
┌─────────────────────────┐
│ HI-Z                     │
│ Hierarchical Z           │
│                         │
│ 先检查 Tile / Block      │
│ "这一整块有没有必要画？" │
└────────────┬────────────┘
             │
         可能可见
             ↓
┌─────────────────────────┐
│ Early-Z                  │
│                         │
│ 对具体 Fragment 做测试   │
│ "这个像素能不能通过？"   │
└────────────┬────────────┘
             ↓
         Pixel Shader
```

例如一个三角形覆盖：

```
████████████████
████████████████
████████████████
████████████████
```

HI-Z 可能一次发现：

```
整个 8×8 Block
都肯定被遮挡
```

那么：

```
64 个像素
```

可以一起拒绝。

而 Early-Z 更接近：

```
Fragment 1 → Depth Test
Fragment 2 → Depth Test
Fragment 3 → Depth Test
...
```

虽然现代 GPU 的实际实现会并行得多，但概念上可以这样理解。

# 十、HI-Z、Early-Z、Z-Prepass 三者不要混

这三个东西非常容易在面试中混为一谈：

|技术|中文|核心作用|
|---|---|---|
|Z-Prepass|深度预处理|**提前生成深度**|
|Early-Z|提前深度测试|**在 Pixel Shader 之前拒绝像素**|
|HI-Z|层次化深度|**一次快速拒绝大片区域**|

例如：

```
Z-Prepass
    ↓
生成 Depth Buffer

    ↓

构建/更新 HI-Z
    ↓
粗粒度判断

    ↓

Early-Z
    ↓
细粒度 Fragment Depth Test

    ↓

Pixel Shader
```

它们不是互相替代关系，甚至可以共同工作。

# 十一、硬件 HI-Z 和软件 HI-Z 也要区分

实际上我们说 HI-Z 时，可能指两类东西。

### GPU 硬件内部 HI-Z

现代 GPU 通常会维护某种：

```
Hierarchical Depth Metadata
// 层次化深度元数据
```

例如按：

```
Tile
Block
Quad
```

记录深度范围。

Rasterizer 在处理三角形的时候，可以先判断：

```
整个 Tile 都失败？
```

如果是：

```
Reject Entire Tile
```

不需要逐像素走完后面的流程。

这种内部结构通常：

```
GPU 厂商私有
硬件实现细节不可见
AMD / NVIDIA / Intel 各有差异
```

它不一定真的是你在 RenderDoc 里看到的一张标准 Mip Texture。

---

### 引擎主动生成的 HZB

UE、现代 GPU Driven Renderer 经常自己构造：

```
HZB
Hierarchical Z Buffer
```

本质可能真的是：

```
Texture2D
+
Mip Chain
```

例如：

```
SceneDepth
↓
Compute Shader
↓
Downsample
↓
HZB Mip0
HZB Mip1
HZB Mip2
...
```

然后给：

```
Occlusion Culling
SSR
SSGI
Screen Space Ray Tracing
GPU Instance Culling
Nanite 等系统
```

使用。

所以：

> 硬件内部的 Hierarchical-Z 和引擎显式构建的 HZB 思想一样，但实现层面不是完全一回事。

# 十二、HI-Z 的构建过程

在 Compute Shader 中可以粗略理解为：

```
// -----------------------------
// Mip0：来自 Scene Depth
// -----------------------------
HiZMip0 = SceneDepth;

// -----------------------------
// Mip1：每个线程处理一个 2×2 block
// -----------------------------

float d0 = Mip0[x * 2,     y * 2];
float d1 = Mip0[x * 2 + 1, y * 2];
float d2 = Mip0[x * 2,     y * 2 + 1];
float d3 = Mip0[x * 2 + 1, y * 2 + 1];

// Traditional Z：
// Near = 0
// Far  = 1
//
// 为了得到这一区域"最远的深度"
// 因此取最大值

Mip1[x, y] = max(
    max(d0, d1),
    max(d2, d3)
);
```

下一层：

```
// -----------------------------
// Mip2
// -----------------------------

float d0 = Mip1[x * 2,     y * 2];
float d1 = Mip1[x * 2 + 1, y * 2];
float d2 = Mip1[x * 2,     y * 2 + 1];
float d3 = Mip1[x * 2 + 1, y * 2 + 1];

Mip2[x, y] = max(
    max(d0, d1),
    max(d2, d3)
);
```

不断：

```
2×2 → 1

2×2 → 1

2×2 → 1
```

最后形成整棵 Depth Pyramid。

# 十三、HI-Z 的最大优点：一次淘汰很多 Fragment

假如一个三角形覆盖：

```
256 × 256
```

大约：

```
65,536 fragments
```

如果普通深度测试：

```
需要处理大量 fragment
```

但 HI-Z 如果能证明：

```
整个 256×256 区域
都被遮挡
```

那么可以在较粗层级：

```
一次大范围 Reject
```

这对以下场景特别有效：

```
城市
室内建筑
大量墙体
复杂开放世界
高 Overdraw 场景
大量实例
```

例如城市：

```
Camera

Building A
██████████

后面：
Building B
Building C
NPC
汽车
树
道具
```

前面的 Building A 能挡掉非常多东西。

HI-Z 的收益会很明显。

# 十四、HI-Z 的主要优点

最核心可以总结为：

|优点|原因|
|---|---|
|降低 Overdraw|大块被挡区域可提前拒绝|
|减少 Pixel Shader 执行|被遮挡 fragment 不必进入复杂 PS|
|提高 Depth Test 效率|从逐像素变成层次化测试|
|很适合 Occlusion Culling|可直接测试 AABB / Instance|
|很适合 GPU Driven|GPU 可以自主做实例剔除|
|适合 Screen Space 算法|SSR、SSGI 等可以快速跳过空间|
|层次结构查询很快|大区域访问高层，小区域访问低层|

尤其现代游戏 Pixel Shader 可能非常贵：

```
PBR
+
多张 Texture
+
Normal Map
+
Shadow
+
Reflection
+
AO
+
Decal
...
```

如果能在执行这些之前拒掉 Fragment，价值非常大。

# 十五、HI-Z 的缺点之一：构建本身有成本

HI-Z 不是免费的。

需要：

```
Scene Depth
    ↓
Downsample
    ↓
Mip1
    ↓
Mip2
    ↓
Mip3
...
```

会产生：

```
Compute Shader 开销
+
Memory Read
+
Memory Write
+
Synchronization
```

所以如果：

```
场景特别简单
几乎没有遮挡
物体数量很少
```

构建一整套 HZB 可能收益不明显。

因此它更适合：

```
复杂大场景
大量物体
大量遮挡
GPU Driven Rendering
```

# 十六、缺点之二：它只是“粗略判断”

例如：

```
████████
████████
████

         Enemy
```

某个 Mip Level 的一个像素可能覆盖：

```
64 × 64 pixels
```

但这块区域里面实际深度非常复杂：

```
墙 墙 墙 天空
墙 墙 墙 天空
墙 墙 墙 天空
```

HI-Z 最后只保存：

```
一个代表值
```

信息一定有所丢失。

所以 HI-Z 本质是：

```
空间换时间
+
精度换速度
```

但利用保守算法，可以保证：

```
精度下降主要导致：
少剔除一些

而不是：
错误剔除
```

---

# 十七、缺点之三：物体越小，HI-Z 优势越小

假设一个模型在屏幕只有：

```
2 × 2 pixels
```

这时候：

```
Mip0
```

本来就只需要查询几个像素。

HI-Z 高层级就没有多少意义。

HI-Z 最适合：

```
大屏幕区域
+
大量遮挡
```

比如：

```
建筑
地形
大模型
大范围 Instance
```

---

# 十八、缺点之四：Depth Pyramid 有显存和带宽成本

假设：

```
Depth：

1920 × 1080
```

然后还有：

```
960 × 540
480 × 270
240 × 135
...
```

好消息是，Mip 总面积并没有无限增长。

完整 Mip Chain 大约：

```
原始面积 × 4/3
```

也就是说额外 mip：

```
约为原始面积的 1/3
```

但依然需要：

```
显存
+
Texture Read
+
Texture Write
+
Cache
```

所以并不是零成本。

# 十九、上一帧 HZB 的问题

GPU Driven Renderer 经常遇到一个问题：

> 当前帧开始做物体剔除的时候，当前帧的完整 Depth Buffer 还没画出来。

怎么办？

一种非常常见的方法：

```
Frame N-1 Depth
    ↓
Build HZB
    ↓
Frame N 使用它做 Occlusion Culling
```

也就是：

```
上一帧深度
判断这一帧
```

好处：

```
避免等当前帧 Depth 完成
```

但问题是：

```
Camera 在移动

Object 在移动

Occluder 在移动
```

例如：

```
上一帧：

█████████
████墙███
█████████

怪物被挡住
```

摄像机突然转动：

```
当前帧：

       Enemy
```

怪物本来应该立刻看到。

但如果你直接相信上一帧 HZB：

```
上一帧判断：
被遮挡

当前帧：
错误 Cull
```

就会导致：

```
一帧消失
Popping
闪烁
```

因此实际工程中需要：

```
扩大 Bounding Box
Conservative Projection
Camera Movement Compensation
上一帧可见性历史
特殊处理 Camera Cut
```

等方式保证安全性。

# 二十、HI-Z 对 SSR 为什么也非常有用？

HI-Z 不只是 Occlusion Culling。

例如 SSR：

```
Screen Space Reflection
// 屏幕空间反射
```

需要沿着一条光线：

```
Ray
───────────────→
```

不断检查是否碰到 Depth。

最暴力的方法：

```
step
↓
sample depth

step
↓
sample depth

step
↓
sample depth
...
```

比如：

```
100 次采样
```

非常贵。

使用 HZB：

```
大空间
↓
查询高 Mip

可能相交
↓
下降一级

可能相交
↓
继续下降

最终
↓
Mip0 精确判断
```

类似：

```
      Mip5
        ↓
      Mip4
        ↓
      Mip3
        ↓
      Mip2
        ↓
      Mip1
        ↓
      Mip0
```

本质就是：

> 远处大步走，接近交点以后再精细搜索。

和：

```
BVH
Octree
QuadTree
```

这些加速结构的思想其实非常相似。

# 二十一、HI-Z 和 QuadTree 思想其实很像

可以把整个屏幕理解成：

```
Root
│
├── 左上
├── 右上
├── 左下
└── 右下
```

然后每一个区域又继续分：

```
               Screen
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
       ...
```

Mip 本质上隐式形成了一种：

```
2D Hierarchy
```

只是 GPU Texture 对：

```
Mip Sampling
Cache
Texture Unit
```

有非常好的硬件支持，因此使用起来非常高效。

# 二十二、HI-Z 什么情况下效果最好？

可以记一个规律：

```
遮挡越强
+
遮挡物越大
+
被遮挡模型越复杂
+
Pixel Shader 越贵

↓

HI-Z 收益越大
```

比如：

```
大型城市
```

特别适合。

因为：

```
Building A
↓
挡住

Building B
NPC
Vehicle
Tree
Prop
```

一次遮挡可能省掉大量 GPU 工作。

反过来，如果是：

```
空旷草原
```

到处都是：

```
小草
树叶
半透明植被
```

遮挡关系不够稳定，HI-Z 的效果可能没那么理想。

# 二十三、透明物体是 HI-Z 的一个麻烦点

例如玻璃：

```
Camera
   ↓

Glass
░░░░░░░░

Enemy
████████
```

玻璃虽然有几何体，但后面的 Enemy 应该能看见。

因此普通透明材质很多时候：

```
不写 Depth
```

如果把玻璃错误地当 Occluder：

```
玻璃写入 Depth

↓

HZB 认为：

"后面完全被挡住"

↓

Enemy 被 Cull

↓

错误
```

所以：

```
Opaque
// 不透明物体
```

通常才是最可靠的 Occluder。

---

# 二十四、HI-Z 对 Alpha Test 材质也比较特殊

例如树叶：

```
█   █
 █ █
█   █
  █
```

实际有大量孔洞。

但 AABB 或粗粒度深度可能感觉它像：

```
██████
██████
██████
```

如果处理不当，会高估遮挡能力。

因此：

```
Masked / Alpha Test
```

材质作为 Occluder 时通常需要更加谨慎。

# 二十五、HI-Z 的核心缺点总结

如果面试官问：

> HI-Z 有什么缺点？

比较完整的回答可以概括成：

|缺点|本质原因|
|---|---|
|构建有 GPU 开销|要生成 Depth Pyramid|
|占用显存|需要多级 Mip|
|占用带宽|不断读取/写入 Depth|
|粗粒度会损失信息|一个值代表整个区域|
|小物体收益低|本身覆盖像素少|
|遮挡少时收益低|无法大量 Reject|
|上一帧 HZB 有延迟问题|Camera/Object 会移动|
|动态场景处理复杂|遮挡关系不断变化|
|透明材质不好处理|透明物体不能简单当 Occluder|
|算法必须保守|错误 Cull 会产生明显画面错误|

---

# 二十六、用一句话理解 HI-Z

你可以这样记：

> **HI-Z 就是把深度缓冲做成一个多层级的 Depth Pyramid，用低分辨率层级快速判断大范围区域是否被遮挡，再逐步向更高精度层级细化，从而减少大量无意义的光栅化、深度测试和像素着色工作。**

---

# 二十七、面试时 HI-Z 最推荐的回答方式

如果面试官问：

> 什么是 Hierarchical Z？

你可以这样回答：

> HI-Z，即 Hierarchical Z-Buffer，是一种层次化深度加速结构。它通常会基于场景的 Depth Buffer 构建类似 Mipmap 的 Depth Pyramid，每一级表示更大屏幕区域的保守深度信息。
> 
> 在做遮挡测试时，可以先选择较高 Mip，用少量采样判断一个物体的屏幕包围区域是否完全位于已有几何体之后。如果能够确定完全被遮挡，就可以提前剔除；如果不能确定，再访问更低一级或者直接正常渲染。
> 
> 它最大的优势是能以 Tile 或 Block 为单位一次拒绝大量被遮挡像素，从而降低 Overdraw 和 Pixel Shader 开销，也非常适合 GPU Driven Occlusion Culling、SSR 和其他 Screen Space Ray Tracing。
> 
> 缺点是需要额外构建 Depth Pyramid，占用一定计算、带宽和显存，而且因为高层级深度是粗粒度信息，算法必须保持保守，否则容易错误剔除。另外使用上一帧 HZB 时还需要处理摄像机和物体运动造成的遮挡延迟问题。

---

# 二十八、把你最近问的几个 Z 技术串起来

你前面刚问过 **Early-Z**，现在可以形成完整知识链：

```
                    深度优化
                       │
         ┌─────────────┼─────────────┐
         │             │             │
         ↓             ↓             ↓
     Z-Prepass      Early-Z         HI-Z
     深度预处理      提前深度测试      层次化深度
         │             │             │
         ↓             ↓             ↓
  提前写 Depth     PS 前 Reject    Block级 Reject
         │             │             │
         └─────────────┼─────────────┘
                       ↓
                 减少 Overdraw
                       ↓
             减少 Pixel Shader
                       ↓
                  提升 GPU 性能
```

其中最值得记住的区别是：

**Z-Prepass 解决的是“深度什么时候写好”；Early-Z 解决的是“能不能在 Pixel Shader 前拒绝这个 Fragment”；HI-Z 解决的是“能不能一次粗粒度拒绝一大片 Fragment / 一个物体”。**

这三个概念在渲染面试里经常会被连续追问。
