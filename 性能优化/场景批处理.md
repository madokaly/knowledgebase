# 游戏场景批处理（Batching）原理详解

场景批处理（Batching）是游戏客户端渲染性能优化中的重要技术，也是 Unity、UE5 渲染优化相关的高频面试知识点。

它主要解决的问题是：场景中存在大量物体时，如何减少 CPU 向 GPU 提交绘制命令的开销，提高渲染效率。

但批处理并不是简单地把所有 Mesh 合成一个 Mesh。不同批处理技术，优化的对象和实现方式都有明显区别。

主要分为：

1. 静态批处理（Static Batching）：通过共享或合并静态几何数据，降低绘制提交成本。
    
2. 动态批处理（Dynamic Batching）：运行时将符合条件的小型 Mesh 合并绘制。
    
3. GPU Instancing（GPU 实例化）：同一个 Mesh，通过一次实例化绘制提交渲染多个对象。
    
4. SRP Batcher：Unity 中通过缓存材质数据、减少状态切换来降低 CPU 开销。
    
5. ISM / HISM：UE 中针对大量重复 Static Mesh 的实例化渲染技术。
    
6. Mesh Merge（网格合并）：直接合并多个网格，减少独立绘制对象和材质批次。
    
7. GPU Driven Rendering（GPU 驱动渲染）：将可见性筛选、实例组织和间接绘制等工作更多地放到 GPU 上。
    

先理解最核心的原理，再看各个技术的实现。

## 一、为什么需要场景批处理？

### 1. Draw Call 是什么？

Draw Call（绘制调用）可以理解为 CPU 通过图形 API 向 GPU 提交的一条绘制指令。

例如：

```
// 伪代码，展示绘制一个 Mesh 的基本流程

// 1. 设置使用的 Shader
SetShader(ShaderA);

// 2. 绑定材质资源
SetTexture(TextureA);
SetMaterialParameters(MaterialA);

// 3. 绑定 Mesh 顶点与索引数据
SetVertexBuffer(VertexBufferA);
SetIndexBuffer(IndexBufferA);

// 4. 提交绘制指令
DrawIndexed(IndexCount);
```

这里最关键的就是：

```
DrawIndexed(IndexCount);
```

它表示向 GPU 提交一次绘制命令。

如果场景有 1000 个物体，每个物体单独绘制，那么在最简单的情况下，需要提交 1000 次 Draw Call。

![[局部截取_20261026_230929.png]]

注意：一个物体不一定只产生一次 Draw Call。

比如一个物体：

- 有 3 个材质槽，可能需要 3 次绘制。
    
- 需要参与阴影渲染，会产生额外的 Shadow Pass 绘制。
    
- 参与 Depth Prepass（深度预处理），可能还要额外绘制。
    
- 参与特殊的描边、透明或其他渲染 Pass，也可能增加提交次数。
    

因此不能简单认为：

`Draw Call 数量 = 物体数量`

### 2. 为什么 Draw Call 多了会影响性能？

每次绘制提交，CPU 可能需要执行以下工作：

```
CPU（游戏线程 / 渲染线程）
    │
    ├── 确定可见物体
    │
    ├── 整理绘制列表
    │
    ├── 选择 Shader / Pipeline State
    │
    ├── 绑定材质与纹理资源
    │
    ├── 设置常量缓冲区与实例参数
    │
    ├── 生成 / 记录 Draw Command
    │
    └── 通过 RHI / 图形 API 提交
                 │
                 ▼
          GPU 执行绘制
                 │
                 ├── 顶点处理
                 ├── 光栅化
                 ├── 像素着色
                 └── 输出结果
```

真正的性能问题不是 `DrawIndexed` 这个函数本身很慢，而是大量绘制命令会带来：

- CPU 命令生成、排序和提交的成本。
    
- Shader、材质、纹理等渲染状态切换成本。
    
- 驱动和图形 API 调用开销。
    
- CPU 向 GPU 组织、更新和传递资源的开销。
    

可以用一个简化模型理解：

$$
T_{\text{CPU}} \approx T_{\text{其他}} + N_{\text{Draw}}\times C_{\text{Draw}} + N_{\text{State}}\times C_{\text{State}}
$$

其中：

$$
N_{\text{Draw}}：绘制调用数量。
$$
    
$$
C_{\text{Draw}}：平均绘制提交成本。
$$
    
$$
N_{\text{State}}：渲染状态切换数量。
$$
    
$$
C_{\text{State}}：平均状态切换成本。
$$
    

实际还存在多线程、驱动批量提交、命令缓存等影响，这个公式只是用来解释优化方向。

批处理的核心就是降低绘制提交和状态切换的总体成本，而不一定要让 Draw Call 数量减少。

这也是为什么 GPU Instancing 和 SRP Batcher 的原理不同。

## 二、静态批处理（Static Batching）

### 1. 核心原理

静态批处理主要用于场景中不需要移动的物体。

例如：

- 建筑物
    
- 地板
    
- 墙壁
    
- 固定的岩石
    
- 场景装饰
    

假设场景有三个物体：

```
物体 A：墙壁
    VertexBuffer_A
    IndexBuffer_A

物体 B：地板
    VertexBuffer_B
    IndexBuffer_B

物体 C：柱子
    VertexBuffer_C
    IndexBuffer_C
```

普通情况下，每个物体有自己的网格数据。

静态批处理可以将其整理到共享的几何缓冲区中：

```
合并后的 VertexBuffer

┌────────────┬────────────┬────────────┐
│ 墙壁顶点   │ 地板顶点   │ 柱子顶点   │
└────────────┴────────────┴────────────┘

合并后的 IndexBuffer

┌────────────┬────────────┬────────────┐
│ 墙壁索引   │ 地板索引   │ 柱子索引   │
└────────────┴────────────┴────────────┘
```

这样便可以减少顶点缓冲区切换与部分绘制准备工作。

### 2. 静态批处理是否一定减少 Draw Call？

不一定。这是非常重要的面试考点。

以 Unity 内置的 Static Batching 为例：

- 将静态几何组织进组合后的 Mesh 数据。
    
- 各物体仍可保留自己的可见性判断。
    
- 对组合中的不同 Mesh，仍可能分别提交绘制命令。
    
- 主要收益是减少相关状态设置和绘制准备成本。
    

例如：

```
静态批处理前：

Draw Mesh A
Draw Mesh B
Draw Mesh C

静态批处理后：

绑定共享 Geometry Buffer

Draw Range A
Draw Range B
Draw Range C
```

因此并不能保证 3 次 Draw Call 变成 1 次。

但如果采用 真正的网格合并（Mesh Merge），并且合并后的网格只有一个材质 Section，就可能通过一次绘制完成。

Unity 官方也区分 Static Batching 与手动合并 Mesh 的行为。

### 3. 静态批处理的优缺点

|优点|缺点|
|---|---|
|减少几何资源切换及部分 CPU 提交开销|合并后的顶点数据可能增加内存|
|适合大量不动的场景物体|不适合频繁移动或变形的物体|
|引擎自动批处理时通常保留物体级剔除|合并数据需要构建时间|
|渲染结果稳定|不同材质、Pass 等仍可能导致多个绘制调用|

### 4. 静态批处理为什么会增加内存？

这是另一个高频问题。

假设有 100 个物体都使用同一个 Mesh：

```
原始情况：

        Mesh A
      /   |   \
  物体1 物体2 ...物体100
```

理论上，100 个物体可以共享同一份 Mesh 资源。

但传统静态批处理可能需要将每个物体的顶点变换到批处理空间，并存储对应的静态顶点数据。

结果会变成：

```
原始共享 Mesh
      +
静态批处理中展开的几何数据
```

于是可能出现：

- CPU / GPU 内存增加。
    
- 构建包体增大。
    
- 加载时间增加。
    

因此，大量重复使用的相同 Mesh，通常更适合考虑 GPU Instancing，而不是无差别开启静态批处理。

## 三、动态批处理（Dynamic Batching）

### 1. 核心原理

动态批处理主要针对运行时需要移动、但顶点数量较少的物体。

例如：

- 小型场景道具
    
- 简单的动态装饰
    
- 低面数物体
    

它与静态批处理最大的不同是：

动态批处理需要在运行时进行顶点变换，再把符合条件的几何数据组织起来一起绘制。

假设有三个小物体：

```
物体 A：MeshA，TransformA
物体 B：MeshB，TransformB
物体 C：MeshC，TransformC
```

正常情况下，顶点着色器会分别完成：

$$
P_{world}=M_{object}\times P_{local}
$$

其中：

$$
P_{local}：顶点在物体局部空间的位置。
$$
    
$$
M_{object}：物体的世界变换矩阵。
$$
    
$$
P_{world}：世界空间位置。
$$
    

动态批处理则可以先在 CPU 上计算：

```
// 伪代码：CPU 处理每个物体的顶点

for (Object& Obj : VisibleObjects)
{
    // 遍历 Mesh 顶点
    for (Vertex& V : Obj.Mesh.Vertices)
    {
        // 将局部空间坐标变换到统一空间
        Vector3 WorldPos =
            Obj.LocalToWorldMatrix * V.Position;

        // 加入临时顶点缓冲区
        DynamicVertexBuffer.Add(WorldPos);
    }
}

// 将多个小 Mesh 的顶点集中起来
UploadVertexBuffer(DynamicVertexBuffer);

// 使用合并后的几何数据绘制
DrawIndexed(TotalIndexCount);
```

这段代码只是原理示意，实际还要处理法线、切线、UV、索引偏移等数据。

### 2. 为什么动态批处理可能反而降低性能？

原因就在于：为了减少 Draw Call，CPU 需要额外处理大量顶点。

假设：

- 原本分别绘制 100 个 Mesh。
    
- 每个 Mesh 有 200 个顶点。
    
- 一共需要处理 20000 个顶点。
    

动态批处理虽然减少了一些绘制提交，但 CPU 每帧可能需要重新进行顶点变换、缓冲区组织与上传。

对于现代 GPU 来说，顶点变换通常比 CPU 上进行相同工作更合适。

因此出现了这样的矛盾：

```
动态批处理

收益：
    减少 Draw Call
    减少部分渲染状态切换

成本：
    CPU 顶点变换
    动态缓冲区更新
    额外内存带宽
    批处理组织工作
```

如果：

$$
T_{\text{CPU额外处理}} > T_{\text{DrawCall节省}}
$$

动态批处理就是负优化。

Unity 官方目前也不再推荐将传统 Dynamic Batching 作为现代项目的优先优化方案。

### 3. 动态批处理的限制

以传统 Unity Mesh 动态批处理为例：

- 只能处理足够小的 Mesh。
    
- 通常需要相同或兼容的材质状态。
    
- 顶点属性数量会影响可批处理的顶点上限。
    
- 不同缩放方式、渲染顺序或 Shader 设置可能影响合批。
    
- 不适合大量高面数模型。
    

旧版 Unity 文档中常见的限制是 300 个顶点、900 个顶点属性，这属于特定版本和传统动态批处理路径的限制，并不是所有引擎或批处理技术的通用规则。


在 UE5 中，Dynamic Instancing 指的是另一种基于绘制命令合并的实例化技术，不能直接等同于 Unity 的 Dynamic Batching。

## 四、GPU Instancing（GPU 实例化）

这是场景批处理中非常重要的一种技术。

也是现代游戏中重复物体渲染的常见方案。

### 1. GPU Instancing 解决什么问题？

假设一个森林场景中有 10000 棵树。

它们使用：

- 同一个 Mesh。
    
- 相同的材质。
    
- 不同的位置。
    
- 不同的旋转。
    
- 不同的缩放。
    

如果传统绘制：

```
for (int i = 0; i < 10000; i++)
{
    SetMesh(TreeMesh);
    SetMaterial(TreeMaterial);

    SetTransform(TreeTransforms[i]);

    // 每棵树单独提交一次绘制
    DrawIndexed(TreeIndexCount);
}
```

理论上需要 10000 次绘制调用，暂不考虑剔除、LOD 和额外 Pass。

但这些树的几何数据完全相同，区别只是 Transform。

因此没有必要对每棵树都单独提交一条绘制命令。

### 2. GPU Instancing 的核心原理

把同一个 Mesh 的顶点和索引数据上传一次，并把所有树的 Transform 存储在实例缓冲区（Instance Buffer）中。

```
             CPU
              │
              ▼
   ┌───────────────────┐
   │ Mesh：TreeMesh    │
   │ Material：TreeMat │
   │ InstanceCount     │
   └───────────────────┘
              │
              │ 一次实例化绘制
              ▼
   ┌───────────────────┐
   │       GPU         │
   │                   │
   │   VertexBuffer    │
   │   IndexBuffer     │
   │   InstanceBuffer  │
   └───────────────────┘
              │
              ▼
   处理多个 Mesh 实例
```

核心调用可以理解为：

```
// 普通绘制
DrawIndexed(
    IndexCount
);

// 实例化绘制
DrawIndexedInstanced(
    IndexCount,
    InstanceCount
);
```

区别在于 `InstanceCount`。

例如：

```
DrawIndexedInstanced(
    TreeIndexCount,
    10000
);
```

这条绘制指令能够让 GPU 渲染 10000 个实例。

当然，真实引擎可能根据可见性、LOD、材质和渲染 Pass 拆分成多个绘制批次，并不保证整个森林只有一次 Draw Call。

### 3. GPU 如何区分不同实例？

通过 `InstanceID`。

在顶点着色器中，每个实例可以根据自己的 ID 读取不同的 Transform。

下面用 HLSL 伪代码演示：

```
// 每个实例对应一个不同的世界变换矩阵
StructuredBuffer<float4x4> InstanceMatrices;

struct VSInput
{
    // 顶点局部坐标
    float3 PositionOS : POSITION;

    // 实例编号
    uint InstanceID : SV_InstanceID;
};

struct VSOutput
{
    // 裁剪空间坐标
    float4 PositionCS : SV_POSITION;
};

VSOutput VSMain(VSInput input)
{
    VSOutput output;

    // 1. 通过 InstanceID 获取当前实例矩阵
    float4x4 WorldMatrix =
        InstanceMatrices[input.InstanceID];

    // 2. 把顶点从局部空间变换到世界空间
    float4 WorldPosition = mul(
        WorldMatrix,
        float4(input.PositionOS, 1.0)
    );

    // 3. 从世界空间变换到裁剪空间
    output.PositionCS = mul(
        ViewProjectionMatrix,
        WorldPosition
    );

    return output;
}
```

这里的核心是：

```
InstanceMatrices[input.InstanceID]
```

虽然所有树都使用相同 Mesh，但不同实例会获得不同的 Transform。

因此可以把它们绘制在不同位置。

实际项目中矩阵的排列方式、乘法顺序和实例编号语义应与引擎 Shader 约定保持一致。

### 4. GPU Instancing 可以实现不同颜色吗？

可以。

实例化并不要求每个物体的所有属性完全一样。

除了 Transform，还可以提供：

- 颜色
    
- 动画偏移
    
- 风吹动参数
    
- 材质混合参数
    
- 随机数
    
- 自定义实例参数
    

例如：

```
// 每个实例都有自己的颜色
StructuredBuffer<float4> InstanceColors;

float4 GetInstanceColor(uint InstanceID)
{
    return InstanceColors[InstanceID];
}
```

所以场景里的 10000 棵树，即使共享同一个材质，也可以呈现不同颜色。

但是，如果不同实例使用了不同 Shader、纹理绑定或者其他不兼容的渲染状态，就可能无法放进同一个实例化绘制批次。

### 5. GPU Instancing 的限制

GPU Instancing 也不是万能的。

主要限制有：

1. 通常需要共享同一个 Mesh 和兼容的材质状态。
    
2. 不同材质槽或不同 LOD 可能需要分别绘制。
    
3. GPU 仍然需要处理所有实际参与绘制的实例顶点。
    
4. Instance Buffer 需要额外的内存和更新成本。
    
5. 如果实例范围过大，而没有合适的实例级或集群级剔除，可能浪费 GPU 计算资源。
    
6. 对复杂骨骼动画，不能直接按照普通静态 Mesh 的实例化方式处理。
    

其中第五点十分重要。

例如：

```
10000 棵树分布在整张地图

玩家视野中：
    只有 200 棵树

理想：
    只绘制 200 棵

低效情况：
    把 10000 棵全部交给 GPU 绘制
```

即使只用少量 Draw Call，也可能造成巨大的无效顶点处理和光栅化开销。

因此在大型场景中，通常需要将 GPU Instancing 与空间分区、视锥剔除、遮挡剔除以及 LOD 联合使用。

## 五、SRP Batcher（Unity 可编程渲染管线批处理）

这是一个特别容易与 GPU Instancing 混淆的技术。

### 1. 它与 GPU Instancing 有什么不同？

GPU Instancing 主要通过一次绘制提交渲染多个实例，而 SRP Batcher 主要减少 CPU 为每次绘制准备材质和渲染状态的成本。

假设存在 1000 个物体：

```
物体 A：Shader X，Material A
物体 B：Shader X，Material B
物体 C：Shader X，Material C
...
```

虽然这些物体材质参数不同，但可能使用相同的 Shader Variant（着色器变体）。

传统渲染流程中，CPU 需要频繁准备、上传或者重新绑定材质数据。

SRP Batcher 的思路是：

- 将材质数据组织进持久化的常量缓冲区（Constant Buffer）。
    
- 对不变化的材质数据避免重复上传。
    
- 对每个物体的数据使用更高效的更新方式。
    
- 尽可能减少 Shader Variant 切换与绑定开销。
    

### 2. SRP Batcher 为什么不一定减少 Draw Call？

例如：

```
原始绘制：

设置 Shader
设置 MaterialA
Draw A

设置 Shader
设置 MaterialB
Draw B

设置 Shader
设置 MaterialC
Draw C
```

SRP Batcher 优化之后，可以理解为：

```
共享 Shader Variant

材质数据保留在 GPU

快速选择物体 / 材质数据
Draw A

快速选择物体 / 材质数据
Draw B

快速选择物体 / 材质数据
Draw C
```

Draw Call 依然可能是 3 次。

但每次绘制的 CPU 准备成本下降了。

Unity 官方明确区分了这两种优化：SRP Batcher 重点减少渲染状态变更成本，而不是传统意义上的几何合并。

### 3. SRP Batcher 的关键条件

Shader 需要按照 SRP Batcher 的要求组织常量缓冲区。

例如：

```
// 物体级常量缓冲区
// 用于存放引擎需要的每物体参数
CBUFFER_START(UnityPerDraw)
    // 引擎定义的每物体属性
CBUFFER_END

// 材质级常量缓冲区
// 同一个材质的参数集中存放
CBUFFER_START(UnityPerMaterial)

    float4 _BaseColor;
    float _Metallic;
    float _Smoothness;

CBUFFER_END
```

这只是结构示意，实际 `UnityPerDraw` 的字段应使用 Unity 对应管线的标准 Shader 定义。

同时，传统 Unity SRP Batcher 路径中使用 `MaterialPropertyBlock` 可能导致 Renderer 失去 SRP Batcher 兼容性。

Unity 6 还引入并完善了 GPU Resident Drawer 等 GPU 驱动的实例化机制。对于 URP/HDRP 项目，需要根据版本和具体渲染路径选择合适的方法，而不是统一地把所有 Renderer 都切到 GPU Instancing。

## 六、UE5 中的场景批处理实现

UE5 中最值得掌握的是：

- ISM（Instanced Static Mesh）
    
- HISM（Hierarchical Instanced Static Mesh）
    
- Dynamic Instancing（动态实例化）
    
- Mesh Merge（网格合并）
    
- HLOD（Hierarchical Level of Detail，层级细节模型）
    

### 1. ISM：实例化静态网格

ISM 对应 UE 的 `UInstancedStaticMeshComponent`。

假设需要生成 1000 个石头。

普通方式：

```
// 伪代码

for (int i = 0; i < 1000; ++i)
{
    // 创建一个独立 Actor
    AStaticMeshActor* Stone =
        SpawnActor<AStaticMeshActor>();

    Stone->SetStaticMesh(StoneMesh);
}
```

这样通常意味着：

- 1000 个 Actor。
    
- 1000 个独立的 StaticMeshComponent。
    
- 需要管理大量 UObject / Component。
    
- 可能产生大量绘制提交和物体管理开销。
    

使用 ISM 则可以通过一个组件管理这些实例。

![[局部截取_20261026_232308.png]]

#### UE C++ 示例

下面是一个简单的 ISM 使用方法。

头文件：

```
#pragma once

#include "CoreMinimal.h"
#include "GameFramework/Actor.h"
#include "InstancedStaticMeshActor.generated.h"

class UInstancedStaticMeshComponent;
class UStaticMesh;

UCLASS()
class AInstancedStaticMeshActor : public AActor
{
    GENERATED_BODY()

public:
    AInstancedStaticMeshActor();

protected:
    virtual void BeginPlay() override;

    // 实例化静态网格组件
    UPROPERTY(VisibleAnywhere, BlueprintReadOnly)
    TObjectPtr<UInstancedStaticMeshComponent> ISMComponent;

    // 所有实例共享的 Mesh
    UPROPERTY(EditAnywhere, Category = "Instance")
    TObjectPtr<UStaticMesh> InstanceMesh;
};
```

CPP 文件：

```
#include "InstancedStaticMeshActor.h"
#include "Components/InstancedStaticMeshComponent.h"
#include "Engine/StaticMesh.h"

AInstancedStaticMeshActor::AInstancedStaticMeshActor()
{
    PrimaryActorTick.bCanEverTick = false;

    // 创建实例化静态网格组件
    ISMComponent =
        CreateDefaultSubobject<UInstancedStaticMeshComponent>(
            TEXT("ISMComponent")
        );

    RootComponent = ISMComponent;
}

void AInstancedStaticMeshActor::BeginPlay()
{
    Super::BeginPlay();

    if (!InstanceMesh)
    {
        return;
    }

    // 设置共享 Mesh
    ISMComponent->SetStaticMesh(InstanceMesh);

    // 创建 1000 个实例
    for (int32 i = 0; i < 1000; ++i)
    {
        // 每个实例的位置不同
        FVector Location(
            (i % 50) * 200.0f,
            (i / 50) * 200.0f,
            0.0f
        );

        // 每个实例独立的变换
        FTransform InstanceTransform(
            FRotator::ZeroRotator,
            Location,
            FVector(1.0f)
        );

        // 添加一个实例
        // false 表示传入的是组件局部空间变换
        ISMComponent->AddInstance(
            InstanceTransform,
            false
        );
    }
}
```

这样便创建了 1000 个共享 Mesh 的实例。

需要注意：

- 每个实例具有自己的 Transform。
    
- 所有实例共享组件级 Mesh 和材质设置。
    
- 可以使用 Per-Instance Custom Data（实例自定义数据）实现材质表现差异。
    
- 可以更新或删除单个实例。
    
- 但不是 1000 个独立 Actor，所以不能直接把每个实例当成完整 Actor 使用。
    

对于大量生成，`AddInstances` 还提供批量添加实例的接口。

### 2. HISM：层级实例化静态网格

HISM 对应：

```
UHierarchicalInstancedStaticMeshComponent
```

它与 ISM 的核心区别不是能否一次绘制多个物体，而是 HISM 额外利用空间层级结构，提高大量实例的剔除和 LOD 管理效率。

假设一个场景有 10000 棵树。

它们分布在不同区域：

```
                整个森林
                   │
          ┌────────┴────────┐
          │                 │
        区域 A            区域 B
          │                 │
      ┌───┴───┐         ┌───┴───┐
      │       │         │       │
    A1区    A2区      B1区    B2区
      │
   具体树木
```

HISM 可以通过类似 BVH（Bounding Volume Hierarchy，包围体层次结构）的空间组织方法，对实例建立层级。

然后进行层级化剔除。

假设摄像机只能看到区域 A：

```
整个森林
    │
    ├── 区域 A：可能可见
    │       │
    │       ├── A1：可见
    │       └── A2：不可见
    │
    └── 区域 B：不可见
            │
            └── 整个子树跳过
```

通过层级结构，可以避免对每个实例都进行相同程度的可见性检查。

基本流程：

```
// 原理伪代码：层级化视锥剔除

void CullNode(BVHNode* Node, const Frustum& Frustum)
{
    // 先测试当前节点的包围盒
    if (!Frustum.Intersects(Node->Bounds))
    {
        // 整个节点不可见
        // 不需要继续检查内部的实例
        return;
    }

    if (Node->IsLeaf())
    {
        // 对叶节点中的实例进行精细筛选
        CollectVisibleInstances(Node);
        return;
    }

    // 继续向下递归
    for (BVHNode* Child : Node->Children)
    {
        CullNode(Child, Frustum);
    }
}
```

这段代码是 BVH / 层级剔除原理示意，不是 HISM 内部的实际引擎源码。

#### ISM 与 HISM 对比

|对比项|ISM|HISM|
|---|---|---|
|相同 Mesh 实例化|支持|支持|
|减少组件数量|支持|支持|
|空间层级结构|不采用 HISM 那种静态层级|有|
|大量静态实例|适合|很适合|
|频繁移动实例|通常更合适|层级更新可能增加成本|
|LOD 管理|支持实例级 LOD|带有层级/分组特点|
|Nanite 场景|通常优先|视回退网格需求决定|

有一点需要特别注意：旧资料经常说 ISM 只能整体 LOD、HISM 才支持实例级 LOD。这已经不能完整描述新版 UE 的情况。

新版 UE 的 ISM 也可以采用实例级 LOD；如果项目完全使用 Nanite，Epic 文档更倾向于选择 ISM，因为 Nanite 自身具有剔除与 LOD 系统。

### 3. Dynamic Instancing：UE 自动动态实例化

UE 的 Dynamic Instancing 是渲染器对兼容 Draw Command 自动进行合并的一种机制。

关键类包括：

```
FPrimitiveSceneProxy
FMeshBatch
FMeshPassProcessor
FMeshDrawCommand
```

它们的核心关系：

```
UPrimitiveComponent
        │
        ▼
FPrimitiveSceneProxy
（渲染线程的场景代理）
        │
        ▼
     FMeshBatch
（描述网格绘制数据）
        │
        ▼
  FMeshPassProcessor
（处理特定渲染 Pass）
        │
        ▼
   FMeshDrawCommand
（缓存 Shader、资源绑定、绘制参数）
        │
        ▼
    排序 / 兼容性判断
        │
        ├── 无法合并 → 独立 Draw
        │
        └── 可以合并 → Instanced Draw
        │
        ▼
         RHI
        │
        ▼
         GPU
```

UE 的绘制命令合并会检查不同 Draw Command 的 Shader Binding（着色器资源绑定）等状态是否兼容。

如果满足条件，就可能把多个绘制合并为实例化绘制。

这里有几个重要前提：

- 相同 Mesh 并不自动保证合批。
    
- 使用同一个 Shader 不等于所有绘制状态都相同。
    
- 材质绑定、Lightmap、Vertex Factory（顶点工厂）等因素可能影响合并。
    
- 不同 Render Pass 的合并情况可能不同。
    

例如：

```
Mesh A + Material X
Mesh A + Material X
Mesh A + Material X

       ↓ 可兼容

Instanced Draw
```

但如果：

```
Mesh A + Material X
Mesh A + Material Y
Mesh B + Material X
```

则不能简单地假设三个对象都会被合到同一次绘制。

在 UE 中，可以通过以下命令分析动态实例化合并效率：

```
r.MeshDrawCommands.LogDynamicInstancingStats 1
```

这部分属于 UE Mesh Drawing Pipeline 的内容，在引擎源码面试中很有价值。

## 七、Mesh Merge（网格合并）

Mesh Merge 和 GPU Instancing 经常被混为一谈，但它们其实是两种不同技术。

### 1. Mesh Merge 的原理

假设有一栋房子，由多个 Mesh 组成：

```
房子
 ├── 墙壁 Mesh
 ├── 屋顶 Mesh
 ├── 门框 Mesh
 ├── 窗户 Mesh
 └── 地板 Mesh
```

如果这 5 个 Mesh 都需要独立绘制，就会有多次绘制提交。

通过 Mesh Merge：

```
墙壁 ──┐
屋顶 ──┤
门框 ──┼──→ 合并后的 HouseMesh
窗户 ──┤
地板 ──┘
```

可以减少需要独立管理的网格数量。

但要特别注意：5 个 Mesh 合并成一个 Mesh，不代表 Draw Call 一定从 5 变成 1。

如果合并后的 Mesh 仍然拥有 5 个材质 Section，就可能仍需要 5 次绘制。

要进一步降低 Draw Call，通常还需要合并材质。

### 2. 纹理图集（Texture Atlas）

纹理图集就是把多个小纹理整合到一张大纹理中。

![[局部截取_20261026_232343.png]]

合并后的 Mesh 可以使用一套统一材质，通过不同的 UV 区域访问纹理。

因此有机会将多个材质 Section 合并为一个。

需要注意，只有纹理图集而 Shader、渲染状态仍不兼容时，也不一定能合批。

### 3. Mesh Merge 最大的问题是什么？

最大的问题之一是 降低剔除精度。

假设一栋大楼被划分成 100 个小 Mesh。

玩家只看得到其中 10 个。

原始情况：

```
100 个 Mesh

可见性检测

10 个可见 → 参与绘制
90 个不可见 → 剔除
```

如果把整栋楼合并成一个巨大的 Mesh：

```
1 个大型 Mesh

包围盒与相机视锥相交

整个 Mesh 进入绘制流程
```

即使只看到大楼的一小部分，也可能要处理大量不可见区域的几何数据。

当然，实际渲染仍有背面剔除、深度测试、LOD 等机制，不代表每个三角形都会完整执行像素着色。

合并后的网格包围盒越大，通常越难获得细粒度的物体级剔除收益。

### 4. UE 中如何做 Mesh Merge？

UE 的 Merge Actors 工具提供多种方式，包括：

- Merge：合并网格，可选择合并材质。
    
- Simplify：合并并简化几何，生成代理网格。
    
- Batch：将相同网格组织为实例化组件。
    
- Approximate：适用于更复杂的几何近似处理，例如复杂 Nanite 源网格。
    

其中 Batch 不是传统意义上的直接顶点合并，而是通过 ISM 批量组织重复网格。

## 八、GPU Driven Rendering（GPU 驱动渲染）

这是大型开放世界和现代渲染架构中更进一步的优化方向。

传统批处理很多工作仍然由 CPU 完成，而 GPU Driven 则尝试将更多工作交给 GPU。

### 1. 传统 CPU Driven 渲染

```
             CPU
              │
              ▼
       场景物体可见性判断
              │
              ▼
        物体分类与排序
              │
              ▼
         构建绘制命令
              │
              ▼
         提交 Draw Call
              │
              ▼
             GPU
              │
              ▼
           执行绘制
```

对于数万个场景物体，CPU 需要管理大量渲染对象和绘制任务。

即使有 Instancing，CPU 仍然可能承担大量可见性判断、实例分组和数据更新工作。

### 2. GPU Driven 的核心思想

把场景物体信息放进 GPU Buffer，然后通过 Compute Shader（计算着色器）处理可见性等工作。

```
                 CPU
                  │
                  ▼
         上传场景物体数据
                  │
                  ▼
       GPU Scene / InstanceBuffer
                  │
                  ▼
            Compute Shader
                  │
          ┌───────┴────────┐
          │                │
       视锥剔除         遮挡剔除
          │                │
          └───────┬────────┘
                  │
                  ▼
          可见实例列表
                  │
                  ▼
         生成间接绘制参数
                  │
                  ▼
          Indirect Draw
                  │
                  ▼
             GPU 绘制
```

这里最重要的两个技术是：

GPU Culling（GPU 剔除）

通过 GPU 判断物体或实例是否需要绘制。

Indirect Drawing（间接绘制）

绘制命令从 GPU Buffer 中读取参数，而不要求 CPU 每次提供完整的绘制数量等信息。

例如：

```
// 伪代码，展示 Indirect Draw 思路

// CPU 提前准备或更新场景数据
UploadSceneData();

// GPU 计算哪些物体可见
DispatchComputeShader();

// GPU 计算结果写入间接绘制参数缓冲区
// IndirectArgsBuffer 中包含实例数量等信息

// GPU 根据参数缓冲区执行实例化绘制
DrawIndexedInstancedIndirect(
    IndirectArgsBuffer
);
```

上述流程省略了资源同步、状态转换、间接参数构造等步骤。

### 3. 为什么 GPU Driven 适合开放世界？

例如一个大型开放世界：

- 100000 棵树。
    
- 200000 个石头。
    
- 50000 个小型装饰物。
    
- 大量重复建筑部件。
    

如果每一帧全部交由 CPU 逐个组织，可能产生较大的 CPU 开销。

GPU Driven 可以利用 GPU 并行计算能力，对实例和集群进行可见性筛选。

然后只让必要的实例参与后续绘制。

它的核心优势并不是让所有物体只用一个 Draw Call，而是：

减少 CPU 需要逐物体处理的工作量，同时在 GPU 上高效完成大规模可见性筛选和批量绘制。

UE5 的 Nanite 也是 GPU 驱动几何处理的重要代表之一。

但要注意，Nanite 并不只是一个批处理系统。它还包括虚拟化几何数据、集群级剔除、细节选择以及专门的光栅化路径等技术。

## 九、如何结合场景空间管理和批处理？

在实际游戏中，单独使用批处理往往不够。

通常需要把批处理和空间划分、LOD、可见性剔除结合起来。

### 场景案例：开放世界森林

假设场景中有 20000 棵树。

每棵树都使用相同 Mesh。

一种简单做法是：

```
20000 棵树
     │
     ▼
一个 ISM
     │
     ▼
实例化绘制
```

虽然减少了绘制提交，但如果没有有效的实例级剔除，GPU 可能仍然处理大量不可见实例。

更合理的方案是：

```
                   整个森林
                      │
                      ▼
                空间分区管理
                      │
         ┌────────────┼────────────┐
         │            │            │
       区域 A       区域 B       区域 C
         │            │            │
         ▼            ▼            ▼
      ISM/HISM     ISM/HISM     ISM/HISM
         │            │            │
         └────────────┼────────────┘
                      │
                      ▼
                可见性筛选
                      │
                      ▼
                  LOD 选择
                      │
                      ▼
                GPU Instancing
                      │
                      ▼
                    渲染
```

通过分区管理，可以：

- 降低大范围物体统一管理的成本。
    
- 提高剔除效率。
    
- 支持分区加载和卸载。
    
- 按距离选择不同 LOD。
    
- 避免单个实例组件规模过大。
    
- 减少不必要的实例数据更新。
    

例如：

|距离|树木渲染方案|
|---|---|
|0～30m|高精度 Mesh / Nanite|
|30～100m|中低精度 LOD|
|100～300m|低精度 LOD / Impostor|
|更远距离|根据场景选择 HLOD、远景表示或剔除|

这里的距离仅用于说明分级思路，实际项目通常还会结合屏幕空间尺寸决定 LOD。

对于非 Nanite 的大量静态实例，HISM 的空间层级结构可以在剔除和 LOD 管理方面提供帮助。

对于 Nanite 场景，则需要利用 Nanite 自身的实例、集群剔除和细节控制机制。

## 十、各种批处理技术的核心区别

这是最值得记忆的一张表。

|技术|核心优化原理|Draw Call 是否减少|主要代价|
|---|---|---|---|
|静态批处理|整理/共享静态几何缓冲区|不保证|几何内存|
|动态批处理|CPU 运行时变换、合并小 Mesh|通常可以|CPU 计算|
|GPU Instancing|一个 Mesh 绘制多个实例|通常可以|实例数据和 GPU 工作量|
|SRP Batcher|缓存材质数据、降低状态更新成本|不要求减少|需要兼容 Shader|
|UE ISM|同一 Mesh 的大量实例化|通常可以|实例管理、剔除成本|
|UE HISM|实例化 + 空间层级组织|通常可以|层级构建及更新|
|Mesh Merge|直接合并多个网格|视材质 Section 而定|剔除粒度下降|
|GPU Driven|GPU 剔除、组织实例并间接绘制|通常可优化提交数量|GPU Buffer、Compute、同步成本|

## 十二、实际项目中，批处理为什么可能导致性能下降？

### 1. Draw Call 少了，但三角形数量没少

假设：

```
优化前：

Draw Call：5000
Triangle：200万

优化后：

Draw Call：500
Triangle：200万
```

Draw Call 减少了 90%，但 GPU 仍然可能需要处理相同数量的三角形。

如果本来就是 GPU Vertex Bound（顶点处理瓶颈），性能提升可能很小。

甚至因为合并导致剔除变差，实际处理的三角形会更多。

### 2. 合批范围太大，造成剔除失效

假设原始场景有 1000 个小物体。

相机只能看到其中 100 个。

原始情况：

```
1000 个物体
    │
    ▼
可见性剔除
    │
    ▼
100 个物体参与绘制
```

如果把这 1000 个物体合并成一个巨大 Mesh：

```
1 个巨大 Mesh
    │
    ▼
包围盒相交
    │
    ▼
整个 Mesh 进入绘制
```

可能使 GPU 处理更多不可见几何。

这就是典型的 CPU Draw Call 开销和 GPU 几何处理开销之间的权衡。

### 3. 材质过多导致无法合批

例如场景中有 1000 个建筑物，每个建筑物使用不同材质。

即使 Mesh 相同，材质的不兼容也可能导致无法实例化。

因此需要考虑：

- 共享材质。
    
- Material Instance（材质实例）。
    
- Texture Atlas（纹理图集）。
    
- Texture Array（纹理数组）。
    
- 实例级材质参数。
    

但需要注意：使用同一个 Material Parent（材质父类），不代表不同 Material Instance 一定能合到同一个 Instanced Draw。

真正能否合并取决于最终的 Shader、资源绑定和绘制状态。

### 4. 渲染 Pass 过多

一个物体在主渲染 Pass 中已经成功批处理，不代表阴影 Pass、Depth Pass 中也会完全按相同方式批处理。

例如：

```
Base Pass：100 Draw Calls
Depth Pass：80 Draw Calls
Shadow Pass：200 Draw Calls
```

这种情况可能完全正常。

所以需要分别分析各个 Pass，不能仅看场景中物体的数量。

## 十三、实际项目如何检测批处理效果？

### UE5

常用命令：

```
// 查看 Game / Draw / GPU 等帧时间
stat unit

// 查看 RHI 统计和绘制调用数量
stat RHI

// 查看场景渲染相关统计
stat scenerendering

// 查看 GPU 各渲染阶段耗时
stat gpu

// 分析动态实例化合并效率
r.MeshDrawCommands.LogDynamicInstancingStats 1
```

更复杂的问题可以使用：

- Unreal Insights：分析 Game Thread、Render Thread、任务执行时间。
    
- RenderDoc：查看实际 GPU 绘制调用、绑定资源和渲染 Pass。
    
- GPU Profiler：判断顶点、像素、阴影或其他 GPU 阶段的性能瓶颈。
    

Epic 的官方性能指南也推荐使用 `stat RHI` 检查绘制调用，以及通过剔除和 Mesh 合并减少渲染负担。

### Unity

重点关注：

- Profiler 中的 CPU Rendering 开销。
    
- Frame Debugger 中实际绘制批次。
    
- Batches。
    
- SetPass Calls。
    
- Saved by Batching（不同管线和版本中统计含义需结合具体工具解释）。
    
- GPU Profiler 中各阶段的耗时。
    

尤其注意：

Batches、Draw Calls、SetPass Calls 不是完全相同的指标。

一个场景即使 Batches 数量没有明显下降，如果 SetPass 和 CPU 渲染准备成本下降，性能仍然可能有所提高。

## 十四、面试高频问题与参考答案

1. 什么是场景批处理？为什么能够优化性能？

场景批处理是将兼容的绘制工作集中组织，以减少绘制调用、状态切换或绘制命令准备成本。它主要针对 CPU 渲染提交瓶颈，但不一定减少 GPU 实际处理的顶点或像素。

2. 静态批处理和 GPU Instancing 的区别？

静态批处理通常将静态物体的几何数据组织到共享缓冲区中；GPU Instancing 则复用同一个 Mesh，通过 InstanceID 和实例数据分别设置位置、旋转、缩放等属性。前者可能增加几何内存，后者主要增加实例数据开销。

3. 为什么 GPU Instancing 可以通过一次 Draw Call 渲染多个物体？

GPU 可以复用一份 Mesh 的顶点和索引数据，并通过实例化绘制命令指定 InstanceCount。顶点 Shader 利用 InstanceID 获取每个实例独立的变换与属性。

4. SRP Batcher 和 GPU Instancing 有什么区别？

SRP Batcher 通过持久化材质数据和减少状态更新降低每次绘制的 CPU 成本，不要求减少 Draw Call；GPU Instancing 主要通过一条实例化绘制命令渲染多个共享 Mesh 的实例。

5. UE 中 ISM 与 HISM 如何选择？

ISM 适用于一般重复 Mesh 实例化，HISM 通过层级空间结构提高大量静态实例的剔除和 LOD 管理效率。新版 UE 的 ISM 也支持实例级 LOD；Nanite 场景通常优先评估 ISM。

6. 为什么合批后 Draw Call 下降了，FPS 没有提高？

可能瓶颈不在 CPU 绘制提交，而在 GPU 顶点处理、像素着色、Overdraw、带宽、阴影、后处理或游戏逻辑。也可能因合并范围过大降低剔除效率，抵消了 Draw Call 优化收益。

7. 为什么不能把所有场景 Mesh 合并？

大 Mesh 会降低对象级剔除粒度，并影响 LOD、分区加载、局部更新、碰撞管理等能力。应根据空间位置、材质和可见性将场景分为合理批次。

8. GPU Driven 和传统 Instancing 最大的区别？

传统 Instancing 主要解决重复 Mesh 的绘制提交问题；GPU Driven 进一步将实例筛选、可见性计算和间接绘制参数生成等工作转移到 GPU，使大量实例的管理与渲染更加高效。

## 十五、总结：场景批处理的核心设计思路

在大型游戏项目中，批处理通常不是单独使用的，而是与整个场景渲染优化体系配合。

```
                场景渲染优化
                      │
      ┌───────────────┼───────────────┐
      │               │               │
   CPU 优化        GPU 优化        内存优化
      │               │               │
      ▼               ▼               ▼
 降低 Draw Call    LOD / Nanite    资源共享
 降低 SetPass      视锥剔除        纹理压缩
 MeshDraw 缓存     遮挡剔除        Mesh 复用
 GPU Instancing    降低 Overdraw    实例化存储
      │               │               │
      └───────────────┼───────────────┘
                      │
                      ▼
                稳定的帧时间
```

在面试中，可以重点强调三个结论：

第一，批处理不等于一定减少 Draw Call。 例如 SRP Batcher 和 Unity 的 Static Batching 都可能在 Draw Call 数量没有明显变化的情况下改善 CPU 渲染效率。

第二，Draw Call 越少不代表性能一定越好。 合批需要兼顾顶点数量、可见性剔除、LOD、内存、实例更新以及 CPU/GPU 之间的负载平衡。

第三，对于 UE5 大型开放世界，最值得掌握的是 ISM/HISM、Dynamic Instancing、Mesh Merge、HLOD，以及 Nanite 和 GPU Driven 的配合。 这些技术结合起来，才构成比较完整的场景渲染优化方案。
