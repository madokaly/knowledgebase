# 游戏客户端性能优化面试知识总结（UE5 / C++ 方向）

对于 UE5 游戏客户端、动作游戏、开放世界、多人战斗 等岗位，性能优化是非常重要的面试考点，尤其是中高级客户端开发岗位。

性能优化面试通常不只是问“有哪些优化手段”，而是重点考察：

1. 性能瓶颈定位：如何判断是 CPU、GPU、内存、IO 还是网络问题？
    
2. CPU 优化：Tick、Actor、组件、碰撞检测、AI、动画、线程与任务系统。
    
3. GPU 优化：Draw Call、Batching、Instancing、LOD、Overdraw、阴影、后处理。
    
4. 内存优化：内存分配、对象池、GC、资源引用、资源加载与释放。
    
5. 加载与卡顿优化：异步加载、AssetManager、资源流送、Shader 和 PSO。
    
6. UE5 专项优化：Nanite、Lumen、World Partition、Unreal Insights。
    
7. 网络性能优化：复制频率、网络相关性、序列化、带宽优化。
    
8. 实战类面试题：场景掉帧、团战卡顿、开放世界加载卡顿应该如何排查？
    

我会按照 原理 → 优化手段 → UE5 实现 → 面试问题及参考答案 的形式展开，重点放在高频、实用的知识上。

# 一、性能优化基础（必考）

## 1. FPS、Frame Time、CPU 和 GPU 的关系

面试题：为什么游戏帧率低？如何判断 CPU 和 GPU 谁是瓶颈？

FPS（Frames Per Second）表示每秒渲染的帧数。

Frame Time（帧耗时）表示一帧所需的时间。

计算公式：

$$
FPS=\frac{1000}{FrameTime(ms)}
$$

|目标帧率|每帧时间预算|
|---|---|
|30 FPS|33.33 ms|
|60 FPS|16.67 ms|
|90 FPS|11.11 ms|
|120 FPS|8.33 ms|
|144 FPS|6.94 ms|

假设游戏目标是 60 FPS，那么一帧的总耗时最好控制在 16.67ms 以内，并留出一定余量应对负载波动。

### CPU 和 GPU 如何协同工作？

<img width="742" height="456" alt="image" src="https://github.com/user-attachments/assets/0cc386e0-fbc0-4eba-9753-71f24f1b34e7" />


在典型的流水线中：

- Game Thread（游戏线程）：执行角色逻辑、AI、游戏规则和部分物理相关工作。
    
- Render Thread（渲染线程）：处理渲染场景更新、组织渲染工作。
    
- RHI Thread（渲染硬件接口线程）：在启用并适用时，负责部分底层图形命令提交工作。
    
- GPU：执行顶点处理、光栅化、像素着色、计算着色等工作。
    

由于 CPU 和 GPU 可以并行工作，稳定状态下的帧间隔通常更接近瓶颈阶段的耗时，而不是简单相加。

例如：

|阶段|耗时|
|---|---|
|Game Thread|9ms|
|Render Thread|12ms|
|GPU|20ms|

这个场景很可能受 GPU 限制，理论吞吐上限约为 50 FPS，而不是简单计算成 9 + 12 + 20 = 41ms。

不过，实际帧时间还受到线程同步、帧队列、VSync、帧率上限和 Present 等因素影响。

面试重点：

- CPU 瓶颈：优化 CPU 上的游戏逻辑、渲染提交或其他耗时任务。
    
- GPU 瓶颈：优化像素处理、几何处理、阴影、带宽等。
    
- 帧率稳定不代表没有性能问题，还应关注 Frame Time 尖峰（卡顿）。
    
- 不能因为 GPU 使用率低就直接认定 CPU 瓶颈，需要结合线程等待和性能分析数据判断。
    

## 2. UE5 常用性能分析工具（非常高频）

面试题：游戏突然掉到 30 FPS，你会如何定位问题？

面试中最好先说工具，再讲优化方案，而不是上来就说对象池、LOD、异步加载。

### 常用 UE5 性能分析命令

|命令|作用|重点观察|
|---|---|---|
|`stat fps`|查看 FPS|平均帧率及变化|
|`stat unit`|查看线程与 GPU 耗时|Game、Draw、GPU|
|`stat unitgraph`|查看帧耗时曲线|突然出现的尖峰|
|`stat game`|分析游戏线程|Tick、游戏逻辑|
|`stat gpu`|GPU 各渲染阶段耗时|BasePass、Shadow 等|
|`ProfileGPU`|捕获 GPU 性能分析信息|耗时较高的渲染 Pass|
|`stat rhi`|RHI 相关统计|绘制等渲染统计|
|`stat scenerendering`|场景渲染统计|网格绘制、可见性等|
|`stat anim`|动画相关统计|动画更新、求值|
|`stat memory`|查看内存统计|内存消耗|
|`memreport -full`|导出详细内存报告|资源和内存分类|

其中最值得掌握的是：

- Unreal Insights：CPU 多线程性能、任务调度、内存分配、加载、网络等分析。
    
- RenderDoc：抓取 GPU 渲染帧，检查 Draw Call、Shader、纹理和渲染状态。
    
- Memory Insights：分析内存分配、释放、调用栈和内存变化。
    
- Network Insights：分析网络复制和数据包。
    

UE 官方也推荐结合 Stat、Unreal Insights、RenderDoc 等工具完成分层定位。

### 实战：如何使用 Unreal Insights？

例如，一次 Boss 战出现卡顿：

1. 在 Development 或适合性能分析的构建中复现问题，尽量避免编辑器自身的额外开销。
    
2. 通过 Trace 采集 CPU 和帧事件。
    
3. 打开 Unreal Insights 的 Timing Insights。
    
4. 找到 Frame Time 从正常值突然增大的那一帧。
    
5. 展开 Game Thread、Render Thread 及 Worker Thread。
    
6. 判断是计算变多，还是线程等待、锁竞争、异步任务等问题。
    
7. 精确到相关函数或模块，修改后在相同条件下重新测试。
    

例如启动参数：

```
YourGame.exe -trace=cpu,frame,bookmark
```

还可以通过 C++ 增加自己的 CPU 性能采样范围：

```
void ABossCharacter::UpdateBossAI(float DeltaTime)
{
    // 在 Unreal Insights 中创建一个 CPU 时间范围。
    // 方便定位 Boss AI 的具体执行耗时。
    TRACE_CPUPROFILER_EVENT_SCOPE(UpdateBossAI);

    // 执行 AI 更新逻辑
    UpdateTarget();
    UpdateDecision();
    UpdateMovement();
}
```

通过进一步给 `UpdateTarget`、`UpdateDecision` 等函数分别添加采样范围，就能继续缩小问题范围。

Unreal Insights 支持通过 Trace Channel 采集所需事件，例如 `cpu`、`frame`、`bookmark`。


### 3. 平均 FPS 和 1% Low 有什么区别？

这是实际性能测试中很重要的问题。

假设两个游戏都达到平均 60 FPS：

- 游戏 A：多数帧都维持在 16ms 左右。
    
- 游戏 B：多数帧只有 12ms，但偶尔出现 80ms、120ms 的长帧。
    

玩家通常会觉得游戏 B 更卡，因为它存在明显的帧时间尖峰。

常用的分析指标：

|指标|含义|
|---|---|
|Average FPS|整体平均帧率|
|1% Low FPS|最慢 1% 帧的性能指标，常见定义为其平均 FPS 或平均帧时间的倒数，具体依测试工具|
|P95/P99 Frame Time|95%/99% 的帧耗时不超过的数值|
|Hitch Count|超过项目卡顿阈值的帧数|
|Peak Memory|峰值内存使用量|

面试回答：

> 对动作游戏而言，除了平均帧率，我会重点关注 P99 帧耗时和 Hitch。因为玩家在闪避、弹反、连招等操作中对单帧卡顿非常敏感。性能优化既要提高吞吐量，也要保证帧时间稳定。

# 二、CPU 性能优化（必考）

## 4. Tick 优化

面试题：UE 中 1000 个 Actor，每个都运行 Tick，应该如何优化？

Tick 是每帧执行逻辑的重要机制，但过多无意义的 Tick 可能导致 Game Thread 耗时增加。

例如：

```
void AEnemy::Tick(float DeltaTime)
{
    Super::Tick(DeltaTime);

    // 每一帧都执行目标搜索
    FindTarget();

    // 每一帧都执行距离检测
    CheckDistance();

    // 每一帧更新 AI 决策
    UpdateAI();
}
```

假设场景中有 1000 个 Enemy，运行在 60 FPS：

$$
1000\times60=60000
$$

意味着每秒调用 60000 次 Tick，还不包括 Tick 内部的具体工作。

### 优化方案一：关闭不必要的 Tick

```
AEnemy::AEnemy()
{
    // 默认不执行 Tick
    PrimaryActorTick.bCanEverTick = false;
}
```

对于只需要响应事件的 Actor，可以完全不使用 Tick。

例如：

- 拾取物：使用 Overlap 事件。
    
- 开关机关：使用交互事件。
    
- 血量 UI：血量变化时通过事件更新。
    
- 技能冷却 UI：采用集中计时或必要时更新。
    

### 优化方案二：降低 Tick 频率

```
AEnemy::AEnemy()
{
    PrimaryActorTick.bCanEverTick = true;

    // 每 0.2 秒执行一次 Tick
    // 一秒约 5 次，而不是 60 次
    PrimaryActorTick.TickInterval = 0.2f;
}
```

适合：

- 远处敌人的简单 AI 决策。
    
- 非实时环境状态检查。
    
- 与实时战斗无关的周期性检测。
    

但注意，角色移动、关键战斗判定和高实时性逻辑不能随意降低更新频率。

### 优化方案三：事件驱动替代轮询

错误思路：

```
void APlayerCharacter::Tick(float DeltaTime)
{
    Super::Tick(DeltaTime);

    // 每帧更新血条，即使血量没有发生变化
    UpdateHealthUI();
}
```

更好的方法是在血量真正变化时通知 UI：

```
void UHealthComponent::SetHealth(float NewHealth)
{
    if (FMath::IsNearlyEqual(Health, NewHealth))
    {
        return;
    }

    Health = NewHealth;

    // 仅当血量变化时通知 UI
    OnHealthChanged.Broadcast(Health);
}
```

### 优化方案四：根据重要性进行分级更新

例如：

|敌人类型|建议更新策略|
|---|---|
|当前战斗中的 Boss|保持关键逻辑实时更新|
|近距离小怪|高频 AI 更新|
|远距离小怪|低频 AI 更新|
|远处且不可见敌人|暂停非必要视觉逻辑|
|已死亡敌人|关闭无用 Tick，按需处理尸体|

UE 有 Significance Manager（重要性管理器）等机制，可用于实现对象分级管理。

**注意：**降低 Tick 频率只能减少相关逻辑执行次数，并不意味着它会自动减少全部碰撞、动画、渲染或网络开销。

## 5. 对象池优化

面试题：游戏中频繁 SpawnActor 和 DestroyActor 会有什么问题？

在动作游戏中，以下对象经常被创建和销毁：

- 子弹
    
- 投射物
    
- 爆炸特效
    
- 命中特效
    
- 飘字
    
- 临时交互物
    

频繁执行：

```
GetWorld()->SpawnActor<AProjectile>(ProjectileClass);
```

以及：

```
Projectile->Destroy();
```

可能产生：

1. 内存分配和释放开销。
    
2. Actor 和组件注册、初始化、销毁成本。
    
3. 物理、碰撞、渲染状态创建与销毁。
    
4. 垃圾回收压力。
    
5. 瞬时大量创建导致的帧时间尖峰。
    

### 对象池原理

<img width="737" height="340" alt="image" src="https://github.com/user-attachments/assets/acc629fe-828d-4496-90da-cab777e57837" />


示意代码：

```
void AProjectile::ActivateProjectile()
{
    // 激活对象
    SetActorHiddenInGame(false);

    // 开启碰撞
    SetActorEnableCollision(true);

    // 开启必要的逻辑更新
    SetActorTickEnabled(true);
}

void AProjectile::DeactivateProjectile()
{
    // 回收前先重置运行状态
    // 实际项目还需要停止运动、粒子、Timer 等
    SetActorEnableCollision(false);
    SetActorTickEnabled(false);
    SetActorHiddenInGame(true);
}
```

正式项目中，对象池还需要注意：

- 清除旧的 Timer 和 Delegate。
    
- 重置速度、伤害参数、命中列表。
    
- 停止粒子和音频等附属效果。
    
- 防止异步回调访问已回收并复用的对象。
    
- 对网络复制 Actor，需要额外处理网络生命周期和同步状态。
    

面试加分点：

> 对象池并不是越大越好。预创建对象会增加常驻内存，还可能增加组件和渲染资源的维护成本。应根据峰值并发数量设计池容量，并通过数据验证是否值得池化。

## 6. 碰撞检测优化

这是动作游戏岗位很容易深入追问的知识点。

面试题：一个场景中有大量角色、子弹和技能碰撞，如何减少碰撞开销？

### 第一层：Broad Phase（粗检测）

快速筛选可能发生碰撞的物体对。

常见算法：

- Sweep And Prune（扫描与裁剪）
    
- BVH（包围体层次结构）
    
- Dynamic AABB Tree（动态轴对齐包围盒树）
    
- Spatial Hashing（空间哈希）
    
- Uniform Grid（均匀网格）
    

原理是利用空间结构过滤明显不可能碰撞的对象，避免对全部对象对做昂贵的精确检测。

### 第二层：Narrow Phase（精确检测）

对粗检测得到的候选对象进行精细检测。

可能使用：

- 球体、胶囊、盒体专用碰撞算法。
    
- SAT（分离轴定理）。
    
- GJK（Gilbert–Johnson–Keerthi）。
    
- EPA（扩展多面体算法）。
    
- Sweep / Continuous Collision Detection（连续碰撞检测）。
    

### 游戏逻辑层面的优化

1. 使用 Collision Channel：只检测真正需要碰撞的类别。
    
2. 使用简单碰撞体：角色胶囊、球体和盒体通常比复杂网格检测更便宜。
    
3. 按需检测：例如攻击窗口开始后才开启武器命中检测。
    
4. 空间分区：大量技能对象或自定义战斗判定可建立空间索引。
    
5. 减少无意义查询：避免所有敌人每帧执行全场景多次 Sweep。
    
6. 控制命中结果数量：能用 Single Trace 的情况不要无条件使用 Multi Trace。
    

面试加分点：

> UE 的 Chaos 物理系统已经具有自身的 Broad Phase 和空间加速机制。普通游戏层优化应优先减少不必要的查询和碰撞对象，而不是盲目重新实现一套 Broad Phase。

## 7. AI 性能优化

面试题：一个开放世界存在几百个敌人，AI 系统可能有哪些瓶颈？

主要消耗包括：

- Behavior Tree（行为树）更新。
    
- EQS（环境查询系统）搜索。
    
- 感知系统处理。
    
- 寻路算法。
    
- 目标筛选。
    
- MoveTo 和移动更新。
    
- 动画及物理系统。
    

### 高频优化方案

方案一：LOD AI

根据距离和重要性动态调整 AI 复杂度。

例如：

- 近距离：完整战斗逻辑、精确感知、快速决策。
    
- 中距离：简化行为树和降低决策频率。
    
- 远距离：仅维持必要的巡逻或模拟。
    
- 极远距离：休眠或使用轻量级代理模拟。
    

方案二：错峰更新（Time Slicing）

原本 100 个 AI 在同一帧执行寻路：

```
第 1 帧：100 个 AI 寻路
第 2 帧：0 个 AI 寻路
第 3 帧：0 个 AI 寻路
```

优化为：

```
第 1 帧：20 个 AI
第 2 帧：20 个 AI
第 3 帧：20 个 AI
第 4 帧：20 个 AI
第 5 帧：20 个 AI
```

总工作量未必减少，但减少单帧负载尖峰。

方案三：缓存结果

例如多个敌人选择相同目标，可以按条件共享目标信息或者复用部分环境查询结果，而不是每个敌人重新进行全场景搜索。

方案四：事件驱动行为树

避免无条件高频运行复杂 Service，适合通过感知事件、Gameplay Event、黑板值变化触发的行为尽可能采用事件驱动。

## 8. 多线程优化

面试题：Game Thread 成为瓶颈，能否直接把逻辑全部放到其他线程？

不能。

多线程可以让部分工作并行，但 UE 的很多 UObject、Actor、组件以及 World 操作都有线程访问限制，不能任意在工作线程访问或修改。

适合放到工作线程的任务：

- 大量独立数学计算。
    
- 数据排序、过滤与预处理。
    
- 与 UObject 世界状态隔离的部分 AI 计算。
    
- 自定义空间索引构建。
    
- 数据解压缩和其他适合并行的计算任务。
    

不适合不加保护地放到工作线程的工作：

- 修改 Actor Transform。
    
- 创建或销毁 Actor。
    
- 直接更新 UMG。
    
- 任意操作组件和 World。
    

常见技术：

- Task Graph / UE Tasks。
    
- `AsyncTask`。
    
- `ParallelFor`。
    
- `FRunnable`。
    
- 线程池。
    

例如：

```
#include "Async/Async.h"

void UMyComponent::CalculateAsync()
{
    // 把纯计算逻辑调度到后台线程
    Async(EAsyncExecution::ThreadPool, []()
    {
        // 不直接访问或修改 Actor、组件
        // 计算独立的数学结果
        const float Result = FMath::Sqrt(256.0f);

        // 将需要更新游戏对象的操作切回游戏线程
        AsyncTask(ENamedThreads::GameThread, [Result]()
        {
            // 这里可以通过已校验的对象引用
            // 把 Result 应用到游戏逻辑中
        });
    });
}
```

实际项目还需要处理对象生命周期、任务取消和数据竞争问题。

面试重点：

多线程优化还需考虑三个问题：

- 线程创建与任务调度开销。
    
- 锁竞争、内存访问冲突。
    
- 任务粒度过小导致并行收益不足。
    

例如单个任务只有几十微秒，强行放到其他线程，不一定比直接执行快。

# 三、GPU 性能优化（必考）

## 9. Draw Call 优化

面试题：Draw Call 是什么？为什么 Draw Call 多会影响性能？

Draw Call（绘制调用）可以理解为 CPU 向图形 API 提交的一项绘制工作。

典型渲染流程：

```
Game Thread（游戏线程）
    ↓
Render Thread（渲染线程）
    ↓
准备绘制命令、渲染状态
    ↓
RHI / 图形 API
    ↓
GPU 执行绘制
```

Draw Call 数量过多可能带来：

- CPU 构建、提交绘制命令的开销。
    
- GPU 绘制命令处理开销。
    
- Pipeline State（管线状态）切换。
    
- 材质、纹理、缓冲区绑定开销。
    

但要注意：Draw Call 数量多不一定就是性能瓶颈。

现代 UE5 渲染器存在动态实例化、Mesh Draw Command 缓存等优化机制，而且 GPU 执行耗时还取决于网格数量、像素覆盖率、材质和渲染 Pass。

### 常见优化方案

|优化方式|原理|适用场景|
|---|---|---|
|Instancing|多个实例共享网格数据，批量绘制|大量相同物体|
|ISM|Instanced Static Mesh|大量相同静态网格|
|HISM|Hierarchical ISM，支持层次化实例管理|大规模场景实例|
|Mesh Merge|合并网格，减少对象与绘制管理开销|静态场景|
|Material Instance|复用材质着色逻辑|大量材质变体|
|LOD|降低远距离物体复杂度|中远距离物体|
|HLOD|将远处一组对象转换为简化的代理表示|开放世界|

### 面试追问：ISM 与 HISM 有什么区别？

ISM（实例化静态网格）

多个相同网格以实例方式绘制。

例如 1000 棵相同树，可以使用一个 ISM 组件管理。

HISM（层次化实例化静态网格）

在实例化基础上，进一步支持层次化空间组织等机制，方便对大量实例进行可见性及 LOD 管理。

实际选择应结合 Nanite、遮挡结构及项目的引擎版本进行测试。

### 面试追问：Material Instance 一定能降低 Draw Call 吗？

不能。

Material Instance 主要作用是共享父材质逻辑，并通过参数形成材质变体。

它并不意味着不同 Mesh 会自动合并成一个 Draw Call。

只有当渲染状态、网格、实例化条件等满足相应批处理路径的要求时，才可能减少实际绘制提交。

## 10. LOD、HLOD 和 Culling 优化

面试题：LOD、HLOD、视锥剔除、遮挡剔除有什么区别？

### LOD（Level of Detail，细节层次）

根据观察条件选择不同复杂度的网格。

概念示意：物体的屏幕占比越小，通常可以使用越简单的几何表现。

传统 LOD 通常以不同网格表示同一个物体：

- 近距离：高精度模型。
    
- 中距离：中精度模型。
    
- 远距离：低精度模型。
    
- 更远距离：可考虑 Impostor 或直接剔除。
    

### HLOD（Hierarchical LOD，层次细节）

HLOD 更关注一组物体。

例如：

```
近距离：

建筑 A
建筑 B
建筑 C
建筑 D

远距离：

简化建筑群代理
```

目的不只是降低三角形数量，还可以减少远处大量对象的管理和绘制成本。

### Culling（剔除）

剔除是尽量避免渲染不可见或者不值得渲染的对象。

|技术|核心原理|
|---|---|
|Frustum Culling|剔除相机视锥外对象|
|Occlusion Culling|剔除被其他几何体遮挡的对象|
|Distance Culling|根据距离剔除对象|
|Backface Culling|剔除满足条件的背面三角形|
|HZB Occlusion|利用层次深度缓冲加速遮挡判定|

面试加分点：

> LOD 的主要目标是降低被渲染对象的复杂度；Culling 的目标是避免渲染不需要的对象。两者作用不同，通常配合使用。

## 11. Overdraw 优化

面试题：什么是 Overdraw？为什么大量粒子特效会造成 GPU 掉帧？

Overdraw（过度绘制）指同一屏幕位置被重复绘制多次。

例如：

```
同一个屏幕像素：

第一次：背景
第二次：角色
第三次：火焰特效
第四次：烟雾特效
第五次：另一层粒子
```

如果多层半透明粒子覆盖相同区域，就可能产生大量像素着色和混合操作。

### 优化手段

1. 降低半透明特效的屏幕覆盖面积。
    
2. 减少不必要的粒子层数。
    
3. 优化特效材质的 Shader 复杂度。
    
4. 对部分远距离特效降低生成量。
    
5. 合理使用较低分辨率的渲染路径。
    
6. 优先避免没有实际贡献的透明粒子。
    

面试追问：为什么透明物体比不透明物体更容易出现 Overdraw？

不透明物体通常更容易利用深度测试、Early-Z 等机制避免部分被遮挡片元的着色。

传统半透明混合通常需要保留并混合多个可见层，不能像不透明物体那样简单舍弃所有后层，因此可能需要执行更多像素计算。

但具体开销仍然取决于透明材质、深度测试、排序和渲染技术。

## 12. 阴影性能优化

面试题：场景中的动态阴影性能开销太大，如何优化？

常见方案：

- 减少不必要的动态投影光源。
    
- 限制阴影影响范围。
    
- 降低阴影分辨率。
    
- 优化阴影投射对象数量。
    
- 合理配置 Shadow Distance。
    
- 静态场景在合适的渲染路径下使用烘焙阴影。
    
- 根据项目情况调整 CSM、VSM 等阴影方案。
    

### UE5 Virtual Shadow Maps（虚拟阴影贴图）

VSM（Virtual Shadow Maps）是 UE5 中面向高精度几何和动态场景设计的阴影技术。

其中非常重要的优化点是 Shadow Cache（阴影缓存）。

当阴影相关数据没有改变时，可以复用部分缓存结果。

如果场景中存在大量移动或变化的阴影投射物，可能造成缓存失效，需要重新渲染阴影页。

例如：

```
静态场景
    ↓
阴影页面稳定
    ↓
缓存复用率较高
    ↓
阴影更新成本较低


大量动态物体
    ↓
部分阴影缓存失效
    ↓
需要重新渲染页面
    ↓
阴影渲染成本增加
```

官方文档也明确指出，过多页面使用及动态缓存失效会影响 VSM 的 Shadow Depths 性能。

面试重点：

不能简单说“动态阴影统一改成静态阴影”。

对于具有昼夜变化、大量动态敌人、可破坏环境的游戏，需要针对光源和物体分别制定策略。

# 四、UE5 专项渲染优化

## 13. Nanite 性能优化

面试题：Nanite 是不是意味着模型三角形越多也不会影响性能？

不是。

Nanite（虚拟化几何体）通过层次化 Cluster（几何簇）、精细化裁剪和动态细节选择等机制，提高高精度模型的渲染效率。

但它不能消除所有几何成本。

### Nanite 的潜在性能问题

- 大量 Masked Materials（遮罩材质）。
    
- 密集树叶等 Aggregate Geometry（聚合几何）。
    
- 大量重叠表面。
    
- World Position Offset（世界位置偏移）带来的额外计算。
    
- 阴影和材质着色带来的开销。
    
- 数据流送和内存带宽限制。
    

例如，一个场景有大量由透明遮罩卡片组成的树叶，启用 Nanite 后不一定就能获得很高的性能。

Epic 官方指出，密集植被中的遮罩材质和多层重叠几何可能限制 Nanite 的裁剪效果，并造成过度绘制。

面试回答：

> Nanite 主要优化高密度几何体的组织、裁剪和绘制，但像素着色、复杂材质、透明效果、光照和阴影等成本仍然存在。因此不能把 Nanite 理解成完全没有三角形成本。

## 14. Lumen 性能优化

Lumen 是 UE5 的动态全局光照与反射系统。

面试题：Lumen 很耗性能，如何优化？

主要关注三个部分：

1. Lumen Scene Lighting：场景间接光照相关计算。
    
2. Screen Probe Gather：屏幕探针收集与间接漫反射。
    
3. Lumen Reflections：反射计算。
    

优化方案：

- 根据平台合理设置 GI 和反射质量。
    
- 调整 Lumen 的内部追踪和采样参数。
    
- 减少不必要的高质量反射。
    
- 控制场景材质复杂度。
    
- 合理使用屏幕百分比及上采样技术。
    
- 使用 `stat gpu` 或 `ProfileGPU` 对具体 Pass 进行分析。
    

Lumen 在部分平台和配置下可使用 Async Compute（异步计算）与其他渲染工作重叠，因此不能简单把每个 Pass 的耗时相加作为最终帧耗时。

# 五、内存性能优化（必考）

## 15. C++ 内存分配优化

面试题：为什么频繁 new/delete 会产生性能问题？

可能产生：

- 分配器调用开销。
    
- 内存碎片。
    
- 缓存局部性变差。
    
- 多线程分配器竞争。
    
- 帧时间波动。
    

常见解决方案：

- 对象池。
    
- 内存池。
    
- 预分配容量。
    
- 尽量复用临时缓冲区。
    
- 减少热点路径的不必要堆分配。
    
- 数据连续化，提高缓存命中率。
    

### TArray 的 Reserve

```
TArray<int32> Values;

// 提前申请足够容量
Values.Reserve(1000);

for (int32 i = 0; i < 1000; ++i)
{
    // 减少数组扩容的可能
    Values.Add(i);
}
```

`Reserve` 不会把数组的有效元素数量直接改为 1000，而是提前准备容量。

它可能减少后续内存重新分配和元素搬移的次数。

### 缓存友好的数据布局

面试题：AoS 和 SoA 有什么区别？

AoS（Array of Structures，结构体数组）：

```
struct FParticle
{
    FVector Position;
    FVector Velocity;
    float LifeTime;
};

// 每个粒子的所有数据放在一起
TArray<FParticle> Particles;
```

SoA（Structure of Arrays，数组结构）：

```
struct FParticleData
{
    // 同种属性集中存储
    TArray<FVector> Positions;
    TArray<FVector> Velocities;
    TArray<float> LifeTimes;
};
```

## 16. UE 垃圾回收 GC 优化

面试题：UE 为什么会发生 GC 卡顿？如何优化？

UE 使用自身的 UObject 垃圾回收机制来管理由 GC 管理的对象生命周期。

GC 需要完成诸如引用遍历、可达性判断、不可达对象清理等工作。

如果项目短时间产生大量 UObject，可能增加 GC 压力。

### 常见优化方案

- 减少频繁创建和销毁 UObject。
    
- 对适合的对象使用复用机制。
    
- 避免不必要的 UObject 包装，纯数据可使用普通结构体。
    
- 避免在关键战斗时机主动触发昂贵清理。
    
- 通过 Unreal Insights 分析 GC 各阶段的耗时。
    

还要区别：

- GC 时间开销：对象管理与回收消耗了 CPU。
    
- 内存泄漏或引用滞留：对象没有按预期释放。
    
- 内存峰值过高：即使最终可释放，也可能造成 OOM。
    

这三个问题不能混为一谈。

## 17. 硬引用与软引用

面试题：为什么 UE 的配置资源尽量不要全部使用硬引用？

假设一个角色配置对象引用了：

- 角色模型
    
- 动画蓝图
    
- 技能特效
    
- 音效
    
- 其他角色的资源
    

如果资源引用依赖过大，就可能使加载范围超出当前实际所需的内容。

### 硬引用

例如：

```
UPROPERTY(EditDefaultsOnly)
TObjectPtr<UStaticMesh> Mesh;
```

硬引用表示 UObject 之间存在直接引用关系，可能导致依赖资源随相关包一起加载。

### 软引用

```
UPROPERTY(EditDefaultsOnly)
TSoftObjectPtr<UStaticMesh> Mesh;
```

软引用主要保存资源路径或软对象标识，可以在合适的时机解析和加载资源。

其优势是：

- 能控制实际加载时机。
    
- 减少不必要的资源依赖加载。
    
- 更容易实现按角色、关卡、玩法加载资源。
    

需要注意：软引用不会自动异步加载，也不保证资源一定能够释放。

UE 提供 Asset Manager 对 Primary Asset 和 Secondary Asset 进行分类管理，并支持按资产组控制加载和卸载。

# 六、加载速度与卡顿优化

## 18. 同步加载与异步加载

面试题：游戏切换角色时出现明显卡顿，你如何解决？

例如技能第一次释放时：

```
// 示意：同步加载资源
UObject* Asset = StaticLoadObject(
    UObject::StaticClass(),
    nullptr,
    TEXT("/Game/Effects/MyEffect.MyEffect")
);
```

如果需要加载的资源尚未在内存中，执行流程可能涉及：

```
读取资源
    ↓
反序列化
    ↓
创建相关对象
    ↓
准备相关运行时资源
    ↓
继续执行游戏逻辑
```

其中部分阶段可能阻塞当前线程或者产生后续游戏线程工作。

### 异步加载方案

典型方案使用：

- `TSoftObjectPtr`
    
- `FStreamableManager`
    
- `RequestAsyncLoad`
    
- `UAssetManager`
    

基本流程：

```
角色准备切换
    ↓
请求异步加载资源
    ↓
后台执行可以异步处理的加载工作
    ↓
资源就绪
    ↓
游戏线程安全地应用资源
    ↓
完成角色切换
```

但要注意：

异步加载不等于绝对不会卡顿。

资源对象初始化、组件注册、GPU 资源上传、PSO 准备等操作仍可能带来帧时间尖峰。

### 进一步优化

1. 在玩家进入战斗前预加载当前角色的核心技能资源。
    
2. 将角色核心资源与低优先级装饰资源分组。
    
3. 使用资源引用计数或者生命周期管理机制。
    
4. 避免在一帧内完成大量对象实例化。
    
5. 设置合理的资源缓存策略。
    

## 19. Shader 和 PSO 卡顿

面试题：为什么游戏第一次释放技能会卡顿，第二次就比较流畅？

这是实际项目中非常经典的性能问题。

可能的原因：

- 首次加载粒子和材质资源。
    
- 首次创建 Niagara 组件。
    
- 首次创建 GPU 资源。
    
- 首次遇到特定 PSO，产生创建或编译成本。
    

### PSO 是什么？

PSO（Pipeline State Object，管线状态对象）描述 GPU 某一类绘制或计算工作需要的管线状态组合。

它可能涉及：

- Shader
    
- Blend State
    
- Rasterizer State
    
- Depth Stencil State
    
- Render Target Format
    
- Vertex Input Layout
    

某些 PSO 如果直到运行时第一次使用才准备，会产生卡顿。

### 如何优化？

- PSO Precaching（预缓存）。
    
- 启动或加载阶段预热关键资源。
    
- 资源异步加载。
    
- 预创建高频使用的特效组件。
    
- 分析 PSO Miss 和 Too Late 的具体原因。
    
- 在冷缓存环境下验证首次运行体验。
    

UE 的 PSO Precaching 机制支持自动收集潜在 PSO，并通过后台任务预编译。官方也提供对应的 Miss、Hit、Too Late 等统计，用于追查 PSO 引起的卡顿。

面试加分点：

> 我会区分首次 Shader/PSO 准备、资源加载、GPU 上传、对象初始化几种不同的成本，不能只凭“第一次卡、第二次不卡”就认定是 Shader 编译。

# 七、网络性能优化（多人游戏高频）

## 20. UE 网络复制性能优化

面试题：多人场景中有大量 Actor 需要同步，如何优化网络性能？

主要考虑两种成本：

- 服务器 CPU 成本：复制候选筛选、属性比较、序列化和数据包生成。
    
- 网络带宽成本：传输对象状态、RPC、移动数据等。
    

常见优化方案：

|优化方式|核心原理|
|---|---|
|Relevancy|只向相关客户端同步需要的数据|
|NetUpdateFrequency|合理降低 Actor 复制频率|
|Dormancy|不经常变化的 Actor 进入网络休眠|
|NetPriority|让重要对象在带宽受限时获得更高优先级|
|Delta Serialization|只发送相对于已知状态的变化|
|Quantization|使用精度压缩减少数据位数|
|Replication Graph / Iris|使用更适合大规模对象的复制、过滤和管理机制|

UE 官方的网络性能建议特别强调减少不必要的复制，并使用更新频率、休眠、相关性和数据量化等策略。

### 示例：不同对象使用不同同步频率

```
玩家自己：
    重要、需要快速反馈的同步数据

附近其他玩家：
    中高频同步

远处玩家：
    降低同步频率或调整相关性

静态宝箱：
    状态稳定时休眠
```

实际情况还需根据同步模式和具体对象的重要性调整。

### 面试追问：为什么不能将所有角色都降低到 5Hz？

因为同步频率降低可能使远端状态更新不及时，增加插值延迟或外推误差。

尤其是高速运动和近战交互类游戏，需要在：

- 带宽成本
    
- 远端视觉平滑
    
- 状态延迟
    
- 游戏玩法正确性
    

之间做平衡。

因此还要配合插值、预测、服务器权威校验等技术。

# 八、动作游戏专项性能优化

对于以角色战斗为核心的 UE 项目，下面这些问题尤其值得重点准备。

## 21. 骨骼动画优化

面试题：多人战斗场景中同时存在几十个 Skeletal Mesh，动画系统性能如何优化？

动画成本可能来自：

- Animation Blueprint 更新。
    
- Animation Graph 求值。
    
- Blend Space 混合。
    
- 骨骼层级计算。
    
- IK（逆向运动学）。
    
- Control Rig。
    
- Pose 计算与蒙皮。
    
- 布料、物理骨骼。
    
- Socket 与骨骼变换访问。
    

### 常见优化方案

Update Rate Optimization（动画更新率优化）

降低不重要角色的动画更新频率。

Animation Sharing（动画共享）

让适合的多个角色共享部分动画状态或姿态计算结果。

Animation Budget Allocator（动画预算分配器）

在性能预算内，调整多个角色动画更新策略。

LOD 骨骼优化

远距离角色使用更少的骨骼或者减少复杂的骨骼控制计算。

并行动画求值

合理使用引擎支持的并行更新与动画求值路径。

### 面试中的关键区分

动画通常需要区分：

- Update：更新动画状态、参数、节点等。
    
- Evaluate：求值最终动画姿态。
    
- Skinning：根据骨骼变换计算网格顶点位置，可走 GPU 或其他路径。
    

仅仅降低 Animation Blueprint 某一部分逻辑的开销，并不意味着整个骨骼动画系统的成本都得到解决。

## 22. Niagara 特效优化

面试题：一个 Boss 同时释放大量技能，为什么帧率会下降？

常见原因：

1. 粒子数量大。
    
2. 半透明 Overdraw 严重。
    
3. GPU 粒子模拟负担较高。
    
4. 复杂粒子材质。
    
5. 大量光源和阴影。
    
6. 首次加载特效或相关 GPU 资源。
    
7. Niagara 系统及组件的创建、更新开销。
    

### 优化思路

- 减少无效粒子数量。
    
- 使用距离或可见性相关的特效分级。
    
- 降低大面积半透明材质成本。
    
- 复用合适的特效组件。
    
- 减少不必要的粒子光照和碰撞。
    
- 区分 CPU 模拟和 GPU 模拟的负载。
    
- 控制高峰战斗的特效并发。
    

特别要注意：

GPU Particle 并不意味着 Niagara 一定比 CPU Particle 快。

GPU 模拟适合大量并行粒子计算，但某些需要复杂 CPU 交互、频繁读取粒子结果的需求不一定合适。

## 23. UMG UI 性能优化

面试题：游戏里很多血条、伤害飘字和 Buff 图标，会有什么性能问题？

常见问题：

- 每帧轮询属性。
    
- 大量 Widget Tick。
    
- 高频布局计算。
    
- 频繁创建、删除 Widget。
    
- 复杂 Widget 层级。
    
- 大量独立的世界空间 Widget Component。
    

### 优化方案

- 使用事件驱动 UI 更新。
    
- 复用伤害飘字 Widget。
    
- 减少不必要的 Widget Tick。
    
- 使用合适的 Invalidation 机制。
    
- 区分真正需要更新的 UI 数据。
    
- 对远距离目标隐藏不需要显示的血条。
    

例如 Boss 血量只有在受伤或回血时才改变，可以通过 Attribute Change Delegate 通知 UI，而不是所有 Widget 每帧读取 ASC 属性。

这也能与 UE GAS 系统结合。

# 九、实战性能排查题（中高级必考）

## 24. 实战题一：游戏从 60 FPS 突然下降到 30 FPS，如何排查？

建议用以下顺序回答：

<img width="738" height="364" alt="image" src="https://github.com/user-attachments/assets/943c4d13-3d6f-4c26-b591-452f399a6ac8" />


面试官很喜欢追问：“如果只在特定场景卡顿呢？”

这时要进一步判断：

- 持续掉帧：通常优先检查持续负载。
    
- 偶发长帧：优先检查加载、GC、PSO、同步等待和任务集中执行。
    
- 镜头转向时卡顿：关注资源流送、可见对象增加及渲染提交。
    
- 进入战斗瞬间卡顿：关注技能资源准备、Actor 创建和组件注册。
    
- 长时间运行后越来越卡：关注内存增长、资源滞留、对象数量和热负载变化。
    

## 25. 实战题二：Boss 释放大招时明显掉帧，怎么解决？

以大型动作游戏中的 Boss 战为例。

Boss 释放大招时通常同时触发：

```
Boss 开始释放大招
    │
    ├── 动画 Montage 与 Notify
    │
    ├── Niagara 特效
    │
    ├── 动态光照与阴影
    │
    ├── 范围碰撞查询
    │
    ├── GAS GameplayEffect
    │
    ├── 音频播放
    │
    └── 多人网络同步
```

需要分模块分析：

|模块|可能问题|优化方向|
|---|---|---|
|动画|复杂骨骼控制、物理|优化动画图、骨骼、IK|
|特效|大量透明粒子|LOD、减少 Overdraw|
|GPU|动态光照和阴影|优化光源、阴影、材质|
|碰撞|多次大范围 Sweep|空间过滤、批量查询|
|GAS|大量目标应用 Effect|批量处理、错峰非关键工作|
|资源|首次使用才加载|预加载、PSO 预热|
|Actor|大量实例化|复用、减少组件注册|
|网络|高频状态和事件复制|精简复制内容、控制频率|

### 一个重要的面试技巧

不要回答“我把技能特效数量减少一半”。

更好的回答是：

> 我会先录制大招释放前后几秒的 CPU 和 GPU 数据。如果 Game Thread 出现尖峰，就继续查看是 GameplayAbility 执行、碰撞查询还是 Actor 创建。如果 GPU 出现尖峰，就查看 Translucency、Shadow Depths 和其他渲染 Pass。最后针对具体瓶颈进行修改，而不是盲目降低所有特效质量。

## 26. 实战题三：开放世界移动时出现加载卡顿

常见技术：

- World Partition（世界分区）。
    
- Level Streaming（关卡流送）。
    
- Async Asset Loading（异步资源加载）。
    
- Texture Streaming（纹理流送）。
    
- HLOD。
    
- PSO Precaching。
    

优化重点：

1. 提前预测玩家可能前往的区域。
    
2. 合理确定加载距离。
    
3. 将资源按空间和功能进行分组。
    
4. 控制单帧对象创建及组件注册量。
    
5. 分批卸载不再需要的对象。
    
6. 控制纹理和几何数据流送的内存预算。
    
7. 分析 CPU、IO 和 GPU 上传是否互相阻塞。
    

尤其要注意异步资源读取结束之后的工作。即使磁盘读取是异步的，大量对象和组件在短时间内初始化，也可能造成 Game Thread 卡顿。

## 十二、中高级面试最重要的一道综合题

面试官：请完整介绍一次你是如何做性能优化的。

可以采用下面的回答结构：

1. 发现问题

通过目标设备的实际测试，发现某个战斗场景存在明显帧时间尖峰。

2. 量化问题

例如目标 60 FPS，正常帧耗时约 16ms，但团战时经常出现 30ms 以上的长帧。

3. 分析原因

通过 Unreal Insights 和 GPU Profiler，分别观察游戏线程与 GPU 渲染耗时，确定具体瓶颈。

4. 提出优化方案

针对已经测量确认的问题，例如资源加载、碰撞查询、动画计算或粒子 Overdraw，选择合适的优化措施。

5. 验证收益

在相同设备、相同场景、相同画质和相同操作条件下，比较：

- 平均 Frame Time
    
- P95/P99 Frame Time
    
- Hitch 次数
    
- CPU 和 GPU 单项耗时
    
- 峰值内存
    
- 画面与玩法正确性
    

6. 评估副作用

确认优化没有引入新的问题，例如动画不连贯、碰撞漏检、加载时资源闪现、网络状态不一致等。

面试官真正希望听到的是：你是否具有独立分析性能瓶颈、设计优化方案、实施修改并验证优化结果的能力。

对于中高级岗位，除了掌握上述知识，最好还能准备两到三个有明确性能数据的案例。相比单纯列举优化技术，这类实际案例更能体现工程能力。
