**第 1 题：UE5 中如何管理 C++ 与 UObject 的生命周期？**

**题干**

你正在开发锁定与战斗系统，需要保存运行时战斗数据、当前锁定敌人、尚未加载的攻击动画资源。应该分别使用什么指针？为什么不能直接用 `TSharedPtr` 管理 `UObject`？如果敌人调用了 `Destroy()`，强引用能否让它继续使用？

**面试口述版**

我会先区分普通 C++ 对象和 UObject。普通 C++ 对象通常用 RAII 管理资源，优先明确独占所有权，确实需要共享时再使用共享指针；UObject 则交给 UE 的垃圾回收系统。

在被 GC 正确追踪的 UObject 成员中，需要保持对象存活时使用 `UPROPERTY` 标记的 `TObjectPtr`；只观察锁定目标时使用 `TWeakObjectPtr`；资源需要按需加载时使用 `TSoftObjectPtr`。`TSharedPtr` 的引用计数与 UObject 的 GC 是两套生命周期机制，不能直接混用。强引用也不能阻止 Actor 被显式销毁。

**核心原理与详细答案**

**① 普通 C++：先确定谁负责释放资源。**

RAII 是 **Resource Acquisition Is Initialization，资源获取即初始化**：把资源交给一个对象管理，并利用该对象的析构释放资源。它不仅适用于内存，也适用于锁、文件句柄等资源。

常见选择是：

- `TUniquePtr`：独占所有权，可以移动，不能复制。
- `TSharedPtr`：共享所有权，最后一个强引用释放时销毁对象。
- `TWeakPtr`：观察共享对象，不增加强引用计数，可以用于打破共享指针的循环引用。

优先独占所有权，可以减少不必要的共享关系与生命周期复杂度。UE 的这套普通智能指针不能直接用于管理 UObject。

**② UObject：GC 关注对象是否可达。**

可以把 GC 理解为：从根集合出发，沿着引擎能够识别的引用关系寻找对象；正常情况下，不可达的对象可以被回收。因此，需要保活的成员引用必须进入 GC 能识别的引用图。

**一个尚未进入 GC 引用追踪路径的普通指针，不会因为保存了对象地址就自动让对象存活。** Actor 和组件还有世界、关卡、所属 Actor 等引擎管理关系，不能只凭某个成员指针推断其完整生命周期。

|类型|中文理解|常见用途与边界|
|---|---|---|
|`UPROPERTY() TObjectPtr<T>`|GC 可追踪的强引用|UObject 中需要持续持有的对象；持有者本身也需要可达|
|`TWeakObjectPtr<T>`|UObject 弱引用|锁定目标、对象缓存；访问时检查有效性|
|`TSoftObjectPtr<T>`|软对象引用|保存资源路径、支持按需加载；不负责让已加载对象一直存活|
|`T*`|裸指针|短期借用、函数参数；不能自行提供 UObject 保活能力|

`TObjectPtr` 不是引用计数指针；本题中的成员写法需要配合 `UPROPERTY`。软引用也不会在访问时自动完成异步加载。

**③ Actor 的业务生命周期与内存释放时机要分开。**

Actor 进入销毁流程后，即使底层内存尚未回收，也不代表它仍能参与战斗。强引用不能撤销 `Destroy()`。

项目中应在目标死亡、离场等业务事件发生时主动解除锁定，并在使用引用时检查有效性，不能只等待指针变成空值。

**实际项目应用**

假设这些成员位于一个正常被引擎管理的战斗组件中：

```
// UCombatRuntimeData 是项目自定义的 UObject 类型。
UPROPERTY(Transient)
TObjectPtr<UCombatRuntimeData> RuntimeData;

// 锁定系统只观察敌人，不负责维持敌人的生命周期。
TWeakObjectPtr<AActor> LockedTarget;

// 编辑器中配置资源，进入战斗前再按需加载。
UPROPERTY(EditDefaultsOnly)
TSoftObjectPtr<UAnimMontage> HeavyAttackMontage;
```

对应的设计理由是：

- **运行时战斗数据**：组件仍在使用它，适合强引用。
- **锁定敌人**：敌人死亡后应该正常销毁，锁定关系适合弱引用。
- **攻击动画**：不希望所有武器动画随角色一起加载，适合软引用；需要提前预加载，避免第一次攻击时才同步加载造成卡顿。

游戏线程中的访问片段可以写成：

```
if (AActor* Target = LockedTarget.Get())
{
    // 这里只说明对象引用有效。
    // 仍需检查目标是否存活、是否可锁定、是否超出距离。
    UpdateLockOn(Target);
}
```

**常见误区**

- **“有 `TObjectPtr` 就一定不会被 GC。”**  
    要看该引用是否被 GC 追踪，以及持有者是否可达。
- **“弱引用有效，说明目标还能攻击。”**  
    引用有效性和业务状态是两回事。
- **“软引用能解决全部资源生命周期问题。”**  
    它主要解决资源定位与加载依赖；加载完成后的保活仍需安排。
- **“Actor 有强引用就不能被销毁。”**  
    GC 保活与显式销毁不能混为一谈。

**深入追问**

**追问 A：两个 UObject 互相强引用，会像两个 `TSharedPtr` 那样必然泄漏吗？**

不会。对于正常进入 GC 引用图的引用，如果这组对象整体从根集合不可达，就仍可被回收。共享指针依赖引用计数，互相持有会使计数无法归零；两者判断对象存活的方式不同。

**追问 B：异步加载回调直接捕获 `[this]` 有什么风险？**

回调执行时，发起加载的角色可能已经死亡或被替换。可以捕获弱引用，在回到游戏线程后检查对象有效性；还需要检查请求是否过期。例如，玩家已经换武器，旧武器的动画加载结果就不应覆盖新配置。

**术语注释**

`Ownership`：所有权；`GC`：垃圾回收；`Reachability`：可达性；`Dangling Pointer`：悬空指针；`Weak Reference`：弱引用。

**第 2 题：如何用 GAS 实现响应及时、结果可靠的联机闪避技能？**

**题干**

设计一个消耗 20 点体力、冷却 1 秒的闪避技能。玩家按键后需要立即得到反馈，但服务器必须检查体力、冷却和眩晕状态。你会如何拆分 GAS 职责？预测失败和技能被打断时分别怎么处理？

**面试口述版**

我会用 GameplayAbility 组织闪避流程，用 AttributeSet 保存体力，用 GameplayEffect 表达消耗和冷却，用 GameplayTag 表达眩晕、闪避中等状态。

对于玩家主动释放的闪避，可以采用 `LocalPredicted`：拥有该角色的客户端先执行支持预测的部分，同时请求服务器激活；服务器独立校验并决定结果。GAS 利用 PredictionKey 关联预测操作与服务器结果，但自定义位移、Actor 生成和任意成员变量不会因此自动获得预测能力。

正常结束、取消和打断都要完成清理；激活被拒绝与技能成功释放后被打断，则需要分别处理。

**核心原理与详细答案**

**① 先把“流程、数值、状态、表现”分清楚。**

|GAS 概念|中文注释|本题职责|
|---|---|---|
|`ASC`：Ability System Component|技能系统组件|管理技能、效果、标签及相关网络交互|
|`GA`：GameplayAbility|游戏技能|组织检查、提交、移动、动画、结束流程|
|`AttributeSet`|属性集|定义体力等数值属性|
|`GE`：GameplayEffect|游戏效果|表达体力消耗、冷却及属性修饰|
|`GameplayTag`|游戏标签|表达眩晕、闪避中等语义状态|
|`AbilityTask`|技能任务|等待动画、输入或其他异步过程|
|`GameplayCue`|游戏表现提示|组织与技能相关的特效、音效等表现|

这是一种可复用的拆分：换成攻击、格挡或蓄力技能时，不必重新设计整套资源与状态管理方式。

**② 理解几个关键阶段。**

- `CanActivateAbility`：判断是否允许激活，适合检查条件，不应承担扣资源等提交行为。
- `ActivateAbility`：开始技能执行。
- `CommitAbility`：提交配置的资源消耗和冷却，需要处理返回失败的情况。
- `EndAbility`：结束技能。正常完成的路径也必须正确结束，否则系统可能一直认为技能仍在运行。

技能检查通过后，资源仍可能因为其他操作发生变化，因此不能把早先检查通过当成后续提交必然成功。

本题可以选择“闪避开始时付费”的规则：

```
尝试激活
  → 检查眩晕、冷却、体力等条件
  → 提交消耗与冷却
      → 失败：结束技能
      → 成功：启动闪避移动与动画任务
  → 正常完成 / 打断 / 取消
  → 清理临时状态并结束技能
```

`PredictionKey`，即**预测键**，用于关联某次预测与服务器产生的结果，帮助处理拒绝后的撤销，以及服务器同步回来时的重复表现问题。

不过，**技能激活成功的确认，不代表所有属性与效果已经同步到客户端**；预测状态还需要与后续到达的权威状态衔接。

**实际项目应用**

假设玩家客户端显示体力为 25，但服务器已处理另一笔消耗，实际只剩 15：

1. 客户端按照本地状态开始预测闪避，立即给出动画和镜头反馈。
2. 服务器收到请求，发现体力不足，拒绝激活。
3. GAS 处理与该预测关联、受支持的效果撤销。
4. 项目代码负责停止自定义拖尾、恢复临时镜头参数等额外表现。
5. 客户端体力最终与服务器状态保持一致。

位移也要单独设计。可以结合 CharacterMovement 支持的移动机制及合适的任务实现；不能只在客户端每帧修改位置，就认为 GAS 会自动完成移动预测和校正。

若闪避带无敌帧，无敌是否生效、攻击是否命中，应进入服务器的战斗判定流程。本地动画播放到某个时刻，不能直接成为服务器认可无敌或免伤的依据。

**常见误区**

- **“设置 `LocalPredicted` 后，整个技能都会自动同步和回滚。”**  
    GAS 只覆盖支持预测、并正确接入预测上下文的操作；自定义逻辑需要另外处理。
- **“瞬时 GE 一律不能预测。”**  
    不能这样概括。有效预测上下文中的瞬时属性 Modifier 可以参与属性预测；`ExecutionCalculation`、周期效果等有不同限制，不能一并套用。
- **“客户端已经检查体力，服务器不用再检查。”**  
    客户端状态可能滞后，也不能作为最终裁决依据。
- **“动画播放完就等于技能结束。”**  
    还需要处理任务、委托、临时状态，并正确走结束流程。

**深入追问**

**追问 A：预测被服务器拒绝，与闪避过程中受到打断，有什么区别？**

预测被拒绝，表示服务器不认可这次激活；需要撤销相应预测结果。

技能已经成功提交后再被打断，表示“这次闪避确实发生过，但提前结束”。是否返还体力、是否保留冷却，属于游戏规则，不能把它等同于激活失败。

**追问 B：技能被取消后，为什么角色可能仍然不能攻击？**

应检查是否残留了阻挡标签、输入限制、移动限制，或者技能根本没有正确结束。结束清理要覆盖正常完成、动画中断、外部取消、角色死亡等路径；重复执行清理时也应避免产生错误。

**术语注释**

`Local Predicted`：本地预测；`Authority`：权威裁决；`Rollback`：回滚；`Reconciliation`：预测与权威结果协调；`Modifier`：属性修饰项；`ExecutionCalculation`：自定义效果执行计算。

**第 3 题：联机动作游戏中，角色相关逻辑应该放在哪些框架类里？**

**题干**

你正在开发支持死亡重生的联机动作游戏。输入、角色移动、玩家积分、比赛阶段和技能状态应该放在哪里？ASC 挂在 Character 与 PlayerState 上有什么区别？重生后技能无法释放，你会如何排查？

**面试口述版**

我会从职责、生命周期和网络可见范围三个维度划分。

PlayerController 代表玩家控制关系，Pawn 或 Character 代表当前操控的身体；PlayerState 保存玩家级状态；GameMode 在服务器执行规则，GameState 同步比赛状态。

ASC 挂在哪里取决于技能状态应该活多久：如果与当前身体同生共灭，放 Character 较直接；如果需要跨死亡或换身体保留部分状态，放 PlayerState 更合适。重生后必须重新关联 OwnerActor、AvatarActor，并处理旧角色状态清理、客户端初始化和界面重新绑定。

**核心原理与详细答案**

**① 类放在哪里，要同时考虑网络上谁能看到它。**

|类|主要职责|默认或常见的网络范围|
|---|---|---|
|`PlayerController`|玩家控制关系、输入协调、本地界面入口|服务器及其拥有客户端|
|`Pawn / Character`|当前身体、移动、碰撞、动画与身体相关能力|服务器及相关客户端|
|`PlayerState`|玩家身份、队伍、积分等玩家级状态|通常在服务器和各客户端存在；属性仍可设置复制条件|
|`GameMode`|比赛规则、重生规则、胜负裁决|仅服务器存在运行实例|
|`GameState`|比赛阶段、队伍比分等共享状态|服务器及客户端|
|`GameInstance`|应用实例内跨地图的本地管理数据|各端独立存在，不自动复制|

输入既可以在 Controller 中协调，也可以由 Pawn 或相关组件绑定；重点是控制切换与生命周期是否清楚。Character 则在 Pawn 基础上提供角色移动、胶囊体、骨骼网格等常用能力。

例如，服务器由 GameMode 判断比赛结束，再把需要客户端知道的比赛阶段写入 GameState。客户端界面读取 GameState，而不是尝试读取服务器 GameMode 的运行数据。

**② ASC 的挂载位置决定了状态天然跟随谁。**

|方案|适用情况|必须处理的问题|
|---|---|---|
|ASC 挂 Character|技能和属性主要属于当前身体|身体销毁后，需要重新创建或恢复相关状态|
|ASC 挂 PlayerState|部分技能状态需要跨重生、换身体保留|更换 Avatar、清理身体专属状态、重新绑定动画与界面|

Epic 的 Lyra 把玩家 ASC 放在 PlayerState 上，以便把技能状态与具体 Pawn 分开，同时专门处理 Pawn 初始化和解除关联。这是一种项目架构选择，并非所有项目的强制写法。

即使 ASC 放在 PlayerState，也应该逐项定义保留规则。例如：

- 积分、已解锁能力：可以保留。
- 某些技能冷却：根据玩法决定是否跨死亡保留。
- 当前连招段数、攻击中状态：通常清理。
- 生命值、眩晕与临时增益：根据重生规则重置。

**③ GAS 中的 OwnerActor 与 AvatarActor 是不同概念。**

- **OwnerActor**：逻辑上拥有 ASC 的 Actor。
- **AvatarActor**：当前在世界中执行动作的实体。

ASC 放在 PlayerState 时，典型关联为：

```
// PS：玩家的 PlayerState
// NewCharacter：重生后的角色
ASC->InitAbilityActorInfo(PS, NewCharacter);
```

这两个 Actor 可以相同，也可以不同。GAS 的逻辑 OwnerActor 还需要与网络复制中的 Actor Owner 概念区分。

**实际项目应用：死亡重生流程**

一种可行方案是：

1. **服务器处理死亡**：取消当前身体执行中的技能，清理攻击、闪避等临时状态。
2. **按规则保留玩家状态**：例如积分与指定冷却。
3. **服务器重生并控制新角色**：GameMode 负责重生规则，PlayerController 控制新的 Character。
4. **重新关联 ASC**：OwnerActor 仍是 PlayerState，AvatarActor 更新为新 Character。
5. **在客户端依赖就绪后初始化**：不能假设客户端 `BeginPlay` 时 PlayerState、Controller 和角色信息已经全部可用。
6. **重绑界面与监听**：解绑旧对象的委托，绑定新的有效数据源。
7. **防止重复授予技能**：区分玩家长期拥有的技能与当前身体、装备临时授予的技能。

对于常规 Character 项目，服务器可以在 `PossessedBy` 等控制关系就绪的入口处理关联，客户端可以结合 `OnRep_PlayerState` 等入口检查依赖。更复杂的架构应使用明确的初始化状态管理，避免只靠某一个回调的触发顺序。

**重生后无法释放技能，优先检查：**

- ASC 是否仍引用旧 Avatar？
- 技能是否实际被授予，是否重复授予？
- 死亡、眩晕或攻击阻挡标签是否残留？
- 客户端是否完成 ActorInfo 初始化？
- 输入是否绑定到新角色对应的有效技能系统？
- 网络所有权链是否允许该客户端发起请求？

**④ 请求入口与权威状态要连起来。**

客户端通常通过自己拥有的 PlayerController、Pawn 或相应复制组件向服务器发请求。不能因为客户端拿到了一个敌人引用，就直接通过该敌人调用 Server RPC。

网络 Owner 影响 RPC 路由以及部分复制条件；它不等于把服务器权威交给客户端。默认情况下，客户端也只接收自己的 PlayerController。

服务器确认结果后，积分、比赛阶段等持续状态通过属性复制同步；客户端在适当的 RepNotify 回调中更新表现。客户端自己修改一个复制属性，并不会把该值自动上传为服务器状态。

**常见误区**

- **“所有东西都放 Character，访问方便。”**  
    重生、换身体和观战会使状态保留与依赖管理变得困难。
- **“放进 PlayerState 就自动复制了。”**  
    自定义属性、组件和 GAS 属性仍需要正确配置复制。
- **“PlayerState 可以永久保存玩家数据。”**  
    跨 Pawn 重生与跨地图、断线重连、账号持久化是不同需求。
- **“发一次 Multicast 就能保存角色死亡状态。”**  
    RPC 表达事件调用，不会自动成为后来加入玩家可恢复的状态记录。

**深入追问**

**追问 A：为什么不把所有玩家都要看的积分放在 PlayerController？**

因为其他客户端默认没有该玩家的 PlayerController。玩家公开积分更适合由 PlayerState 承载，队伍或比赛总分则适合由 GameState 承载。

**追问 B：`HasAuthority()` 与 `IsLocallyControlled()` 有什么区别？**

前者判断当前 Actor 实例是否具有权威角色；后者判断 Pawn 是否由本机控制。

在常规服务器生成并复制的玩家 Character 上：

|所在位置|`HasAuthority()`|`IsLocallyControlled()`|
|---|---|---|
|专用服务器上的远程玩家角色|true|false|
|拥有该角色的玩家客户端|false|true|
|其他玩家客户端上的该角色|false|false|

因此，服务器战斗裁决与本地输入、镜头反馈，不能使用同一套判断条件。

**术语注释**

`Possess`：控制器接管 Pawn；`Avatar`：执行行为的世界实体；`Owning Connection`：拥有连接；`Replication`：网络复制；`RepNotify / OnRep`：复制通知回调；`Relevancy`：网络相关性，决定哪些连接需要接收该 Actor。
