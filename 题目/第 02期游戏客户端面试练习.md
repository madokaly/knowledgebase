**第 1 题：UE5 如何把游戏场景变成屏幕画面？掉帧时怎样定位瓶颈？**

**题干**

联机战斗中，多个角色同时释放技能，帧率从 60 FPS 降到 40 FPS。你会怎样解释一帧画面的生成过程，又会如何判断应该优化游戏逻辑、绘制提交还是 GPU 渲染？

**面试口述版**

一帧画面需要 CPU 和 GPU 协作。游戏线程组织玩法、角色和场景状态的更新；渲染线程根据渲染数据准备绘制工作，再通过 RHI 等机制提交给 GPU。GPU 执行几何处理、光栅化、着色及后处理等任务。

排查时，我先看毫秒级帧耗时，用 `stat unit` 判断主要压力在哪，再用 Unreal Insights 或 GPU 分析工具定位具体工作。各阶段可以流水线并行，所以不能把 Game、Draw 和 GPU 时间简单相加。优化应该针对实际瓶颈，并在相同场景与设备上复测。

**核心原理与详细答案**

**① 先区分 CPU 侧的不同职责。**

|环节|主要工作|战斗场景中的相关开销|
|---|---|---|
|Game Thread：游戏线程|组织玩法、对象状态和各类更新|技能逻辑、碰撞查询、组件 Tick|
|Render Thread：渲染线程|处理渲染场景数据、准备各类绘制工作|可见对象、动态网格、绘制命令|
|RHI：渲染硬件接口|抽象图形 API，组织底层命令提交|资源绑定、命令提交等|
|GPU：图形处理器|执行图形与计算任务|材质、阴影、光照、透明特效、后处理|

渲染侧通常使用自己的数据表示。例如，游戏侧的 `UPrimitiveComponent` 对应渲染侧的 `FPrimitiveSceneProxy`。渲染线程不能随意读取游戏线程正在修改的对象数据，否则可能产生竞争或生命周期问题。

**② 理解常见的 GPU 渲染流程。**

传统光栅化可以概括为：

```
顶点与图元处理 → 光栅化生成片元 → 着色与深度/混合等处理 → 输出图像
```

在常见延迟渲染路径中，还需要理解几个阶段：

- **深度预处理**：按配置先写入深度，帮助后续减少无效着色。
- **Base Pass，基础通道**：处理不透明等表面，把材质属性写入 GBuffer 等目标。
- **光照阶段**：利用表面属性和光照信息计算画面。
- **透明与后处理**：处理相应透明表现、色调映射及其他屏幕效果。

**GBuffer，几何缓冲区**，可以理解为保存法线、粗糙度等表面属性的一组缓冲，用于后续着色。实际 Pass 会随平台、渲染路径和启用功能变化，不能把示意流程当成固定源码顺序。

**③ 用帧耗时判断预算，而不是只看 FPS。**

换算关系为：

```
帧耗时（毫秒）= 1000 ÷ FPS

60 FPS ≈ 16.67 ms
40 FPS = 25 ms
```

稳定的流水线中，吞吐通常受最慢阶段限制；另外还要考虑同步等待、帧率限制等因素。**Game 8 ms、Draw 9 ms、GPU 20 ms，不能直接相加成 37 ms。**

`stat unit` 适合初步查看 Frame、Game、Draw、GPU 等时间，但接近的数值可能包含等待，仍需进一步分析。

**实际项目应用**

假设战斗场景测得：

```
Frame：25 ms
Game： 7 ms
Draw： 9 ms
GPU：24 ms
```

我会先怀疑 GPU 压力，再按以下步骤验证：

1. **固定复现条件**：相同设备、镜头、角色数量和技能组合，使用具有代表性的运行版本。
2. **检查 GPU 开销分布**：利用 `stat gpu`、`profilegpu` 等查看透明、阴影、光照等阶段。
3. **做单变量实验**：临时减少某类特效，或降低渲染分辨率，观察对应耗时变化。
4. **针对热点修改并复测**：确认画质代价和实际收益。

例如，如果分析发现大量技能烟雾导致透明阶段昂贵，可以尝试缩小粒子屏幕覆盖面积、减少重叠层数、简化材质。这里关注的是**同一片屏幕区域被反复着色的成本**，不能只数粒子数量。

如果热点实际出现在游戏线程，则应转而检查技能 Tick、碰撞查询、对象生成等工作。

**常见误区**

- **“掉帧先减少模型面数。”**  
    模型面数只是潜在成本之一，瓶颈也可能是透明、阴影、材质或 CPU 逻辑。
- **“GPU 使用率不满，说明 GPU 一定不是瓶颈。”**  
    使用率不足以解释同步、等待和局部资源限制，需要结合耗时与捕获结果。
- **“优化后平均 FPS 提高，就结束了。”**  
    还应观察战斗高峰和明显卡顿，平均值可能掩盖尖峰。

**深入追问**

**追问 A：前向渲染和延迟渲染的核心区别是什么？**

前向渲染通常在绘制表面时计算相关光照；延迟渲染先记录表面属性，再进行后续光照计算。

延迟渲染便于组织丰富的光照与屏幕效果，但需要相应缓冲和带宽；前向路径在部分内容、平台或抗锯齿需求下有优势。实际选择应结合功能与性能测试，不能断言某一种永远更快。

**追问 B：一个模型是否对应一次 Draw Call？**

不能这样计算。同一网格可能涉及多个材质区段、多个视图以及深度、阴影等多个 Pass；部分绘制也可能被合并或实例化。

减少提交开销需要理解材质、绘制状态与合并条件，不能只根据场景对象数量估算。

**术语注释**

`Draw Call`：绘制调用；`Pass`：完成某项渲染工作的阶段；`Overdraw`：同一区域被多次绘制；`Bottleneck`：性能瓶颈；`Frame Time`：帧耗时。

**第 2 题：CharacterMovement 如何实现移动预测？为什么冲刺时角色会被拉回？**

**题干**

角色普通行走正常，但你在客户端把 `MaxWalkSpeed` 改成冲刺速度后，角色不断向前移动又被拉回。原因可能是什么？一个支持联机的冲刺功能，需要怎样接入移动系统？

**面试口述版**

拥有角色的客户端会先模拟移动，以获得即时反馈，并保存移动记录；服务器收到移动数据后独立模拟和校验。有差异时，客户端应用服务器校正，再回放尚未确认的移动。

冲刺被拉回，常见原因是客户端与服务器使用了不同的速度或移动状态。只修改客户端速度，或者单独复制一个当前冲刺变量，都不一定能让历史移动被正确还原。我会把影响移动的冲刺意图接入移动记录、网络传输和回放流程，并让服务器验证实际冲刺资格。

**核心原理与详细答案**

**① 移动同步同时解决响应与一致性。**

对于常规玩家 Character：

|实例|主要行为|
|---|---|
|拥有客户端上的自主代理|立即响应输入、预测移动、保存移动记录|
|服务器上的权威实例|根据收到的数据模拟、校验并确认或校正|
|其他客户端上的模拟代理|根据服务器状态更新，配合网络平滑显示|

客户端预测并不是“客户端上传位置，服务器照单接受”。服务器会重现移动并检查结果。

**② 校正后需要回放，而不只是退回旧位置。**

假设服务器校正的是时间点 T100 的状态，但客户端已经预测到 T130：

```
收到 T100 的权威状态
    → 恢复相应状态
    → 从该状态重新模拟尚未确认的移动
    → 得到接近客户端当前时刻的新结果
```

否则，客户端每次收到校正都停留在过去，操作体验会明显变差。

`FSavedMove_Character` 就参与保存这种历史移动信息。它与“当前角色身上的变量”用途不同：**当前状态正确，不代表历史移动回放时也能恢复正确状态。**

**③ 冲刺至少需要打通三条路径。**

```
本地预测使用冲刺状态
        ↓
服务器处理对应移动时得到必要状态
        ↓
客户端回放该移动时恢复同样的输入条件
```

一个普通复制属性主要同步服务器当前状态，不会自动替你记录每个历史移动对应的冲刺意图。

**实际项目应用**

假设普通速度为 450，冲刺速度为 750，可采用以下实现思路。数字仅用于示例。

|环节|需要完成的工作|
|---|---|
|输入|记录“希望冲刺”，而不是直接决定最终合法速度|
|移动计算|根据冲刺意图和允许条件选择速度|
|保存移动|在自定义 SavedMove 中记录本次移动需要的状态|
|网络传输|将必要状态编码到移动数据中|
|服务器校验|检查体力、眩晕、移动模式等条件|
|回放|恢复对应移动的状态，再重新模拟|

相关 C++ 扩展点可以这样理解：

- `SetMoveFor`：保存本次移动所需数据。
- `GetCompressedFlags`：编码适合放入标志位的信息。
- `PrepMoveFor`：在回放前恢复必要状态。
- `CanCombineWith`：判断相邻移动能否合并，不能丢失影响行为的状态变化。

面试重点是解释各环节为什么存在，不必机械背诵完整类实现。

若需要传输的不只是少量布尔状态，还可扩展 `FCharacterNetworkMoveData` 与对应容器，负责从 SavedMove 提取数据及网络序列化。

需要特别注意：**服务器收到的是冲刺请求或移动输入，不应直接相信客户端任意指定的速度。** 涉及体力消耗、减速效果等随时间变化的条件，还需要考虑它们如何与移动时间线保持一致。

验证时，应测试延迟、丢包、快速按下与松开冲刺、体力耗尽、空中切换和受击减速。只在本机无延迟情况下正常，不能说明联机实现完整。

**常见误区**

- **“客户端和服务器分别设置一次速度就够了。”**  
    还要考虑状态到达顺序、历史记录和回放。
- **“加大平滑参数就能修复冲刺拉回。”**  
    平滑改善视觉过渡，不能修复两端模拟规则不一致。
- **“关闭校正后不拉回，问题就解决了。”**  
    这可能只是隐藏了分歧。
- **“技能用了 GAS 本地预测，移动自动全部正确。”**  
    技能预测与移动预测需要正确配合，上期的预测选项不能替代本题的移动实现。

**深入追问**

**追问 A：为什么不每帧发送一个 Reliable RPC 同步移动？**

高频可靠消息在丢包时可能累积，并产生等待与带宽压力。CMC 的移动协议使用时间戳、移动记录、确认与必要的重发信息组织同步，不能简单替换成“每帧可靠发送位置”。

这里要区分：**单条消息是否可靠送达，与整套协议能否恢复一致，是两个层面。

**追问 B：移动回放时，冲刺特效和体力消耗会不会重复触发？**

如果把一次性业务行为直接混进可能反复执行的移动模拟逻辑，就有重复执行风险。

项目应区分“可重复计算的运动过程”和“一次性业务提交”。体力等权威结果按明确规则处理，表现事件可以关联操作编号并去重，不能把一次回放当成玩家又按了一次冲刺。

**术语注释**

`Autonomous Proxy`：自主代理；`Simulated Proxy`：模拟代理；`Saved Move`：保存的移动记录；`Replay / Resimulation`：回放、重新模拟；`Network Smoothing`：网络视觉平滑；`Rubber Banding`：角色被拉回的橡皮筋现象。

**第 3 题：如何设计支持输入缓存、打断和联机判定的三段连招？**

**题干**

设计轻攻击三连击，要求提前按键可以接下一段，按键不能无限缓存，受击后可以打断，同一段攻击不能对同一敌人重复扣血。你会怎样组织 Montage、战斗逻辑和服务器判定？

**面试口述版**

我会用 Montage 组织攻击动画与分段，用技能或战斗组件管理每个角色的运行状态。输入缓存只保存短期攻击意图，只有当前阶段允许续段时才消费，消费后不能再次触发。

伤害窗口、续段窗口和取消窗口分别配置。动画通知负责传递时机，战斗逻辑检查转换条件；服务器验证攻击状态并结算伤害。同一攻击窗口维护已命中目标集合，避免逐帧检测造成重复伤害。打断时统一关闭窗口、清理缓存和攻击状态。

**核心原理与详细答案**

**① 连招不是单纯“播放三段动画”。**

至少需要管理：

|内容|建议职责|
|---|---|
|动画播放、混合、分段|Montage 与动画系统|
|当前段数、缓存输入、转换规则|GA 或角色战斗组件|
|伤害计算与合法性|服务器战斗逻辑|
|镜头、音效、拖尾等反馈|本地表现与适当的同步机制|

Montage 可以组合多个动画，并利用 Section 控制播放结构，但项目仍要定义什么时候允许进入下一段。

**② 输入缓存与允许续段是不同条件。**

- **输入缓存**：玩家提前按下攻击，把短期意图记下来。
- **续段窗口**：当前攻击允许接受下一段转换。
- **伤害窗口**：本段攻击可以产生伤害的时间范围。
- **取消窗口**：允许转入闪避、格挡等动作的时间范围。

这些窗口可以重叠，也可以分开。

例如，第一段可设计为：

```
0.18～0.30 秒：伤害窗口
0.20～0.42 秒：接受短期续段输入
0.32～0.42 秒：允许确认续段
0.45 秒：到达当前攻击 Section 边界
```

玩家在 0.25 秒按下攻击，系统先缓存；进入允许续段阶段后，检查缓存有效期和角色状态，通过后消费输入，并安排第二段。

这些数值属于手感设计示例，还需要结合播放速率、顿帧和实际操作测试调整。

**③ 一次缓存只能消费一次。**

下面是项目逻辑伪代码：

```
攻击按下：
    保存输入动作、时间与当前攻击编号
    尝试消费缓存

续段窗口开启：
    尝试消费缓存

尝试消费缓存：
    检查窗口、输入有效期、攻击编号和角色状态
    条件通过后，先标记输入已消费
    再执行下一段请求与动画安排

攻击结束或打断：
    关闭窗口，清理缓存与临时攻击状态
```

关联攻击编号，可以防止旧攻击留下的输入或延迟回调影响新攻击。先消费再转换，则能避免同一输入因多个事件触发而被重复处理。

**实际项目应用**

**动画转换方面：**

如果希望当前 Section 自然结束后接第二段，可以动态设置下一 Section；如果设计要求立即切段，可以使用跳转，但要正确结束旧段的伤害与状态。

`Montage_SetNextSection` 修改后续连接关系，`Montage_JumpToSection` 则直接跳到指定 Section，两者不能混用。

**命中方面：**

服务器在有效伤害窗口中执行命中检测，并维护：

```
当前攻击编号 + 当前伤害窗口编号 → 已命中目标集合
```

同一窗口再次检测到同一目标时，不重复结算。下一段或新的多段伤害窗口按规则重新建立记录，不能把“整套连招只能命中一次”写死。

高速挥刀还要考虑从上一采样位置到当前采样位置的扫掠与必要的补充采样，不能只检查当前一帧的武器位置。

**联机方面：**

客户端可以先提供攻击反馈，但服务器仍要验证段数、转换条件、资源和目标合法性。客户端报告命中，可以作为待验证数据，不能直接决定最终扣血。

**中断方面：**

受击、死亡、武器切换、技能取消等路径应进入统一清理逻辑。不要把所有清理都寄托在正常播放结束后的动画通知上；迟到的旧回调也需要检查攻击编号。

**常见误区**

- **“按键立即跳下一段，连招就完成了。”**  
    可能截断当前攻击、破坏节奏，还会让输入时机失去意义。
- **“一个 `bCanCombo` 可以表示所有战斗窗口。”**  
    伤害、续段和取消是不同规则，混在一起很难扩展。
- **“命中检测每帧执行，所以每帧扣一次血。”**  
    检测频率与伤害结算次数必须分开管理。
- **“低帧率一定会漏掉所有 Notify。”**  
    不能一概而论。项目要验证跨时间区间、跳段、混合和中断的行为，避免依赖某个浮点时间恰好相等。

**深入追问**

**追问 A：Queued Notify 与 Branching Point 有什么区别？**

Queued 是异步排队处理方式，成本较低，但允许一定时机偏差；Branching Point 更强调同步顺序和精确时机，成本也更高，适合某些会影响播放流程的分支决策。

它们解决的是动画事件执行方式，不能替代网络验证，也不意味着所有通知都应设成 Branching Point。

**追问 B：为什么本机命中正常，专用服务器上的武器轨迹却可能不正确？**

如果判定依赖骨骼 Socket，服务器就需要获得符合判定需求的骨骼变换。骨骼网格的动画更新设置会受到“是否被渲染”等条件影响；专用服务器没有正常画面显示，不能假设它与客户端的更新行为相同。

应检查姿态与骨骼刷新策略，并选择按需更新骨骼，或使用独立的权威攻击轨迹。直接让所有角色始终完整刷新骨骼，也需要评估服务器 CPU 成本。
