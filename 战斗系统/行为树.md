# **一、行为树（Behavior Tree，BT）是什么？**

行为树是一种以**树形结构组织 AI 决策逻辑，并通过节点执行结果控制行为流转**的 AI 架构。

它广泛应用于游戏中的：

- 普通怪物 AI：巡逻、追击、攻击、返回出生点。
    
- Boss AI：阶段切换、技能选择、连招、闪避、受击、狂暴。
    
- NPC AI：工作、交谈、休息、逃跑。
    
- 射击游戏 AI：寻找掩体、射击、换弹、包抄。
    
- 伙伴 AI：跟随玩家、协助攻击、救援。
    

下面重点结合 UE5 和类似《鸣潮》的动作战斗游戏进行讲解，最后总结高频面试问题。

## **1. 行为树的基本结构**

<img width="740" height="547" alt="image" src="https://github.com/user-attachments/assets/a46930e5-60ce-4310-819e-465ba22622cc" />

假设一个怪物存在三种行为，优先级为：

**攻击 > 追击 > 巡逻**

AI 进行决策时：

1. 判断是否满足攻击条件，满足则攻击。
    
2. 无法攻击时，判断是否存在追击目标。
    
3. 不存在追击目标时，执行巡逻。
    

每个行为分支还可以继续拆分成更细小的子行为，形成树形结构。

行为树的核心思想就是：**将复杂的 AI 决策拆分为可以独立实现、组合和复用的小节点。**

# **二、行为树的核心组成**

|英文名称|中文名称|主要作用|
|---|---|---|
|Root|根节点|行为树的入口|
|Composite|组合节点|控制子节点执行顺序|
|Selector|选择节点|从多个行为中选择可执行行为|
|Sequence|顺序节点|按顺序完成一系列行为|
|Parallel|并行节点|同时推进多个行为|
|Task / Action|任务节点|执行移动、攻击等具体行为|
|Condition|条件节点|判断某个条件是否成立|
|Decorator|装饰器节点|控制行为的执行条件、中断等|
|Service|服务节点|定期更新 AI 所需的信息，UE 常用|
|Blackboard|黑板|保存、共享 AI 决策数据|

## **1. 节点的执行返回值**

行为树最重要的机制，就是节点执行后向父节点返回执行结果。

|返回值|中文含义|说明|
|---|---|---|
|Success|成功|当前节点成功完成|
|Failure|失败|当前节点无法执行或执行失败|
|Running|运行中|当前节点还没有执行完毕|

UE C++ 中对应的 `EBTNodeResult` 为：

```
EBTNodeResult::Succeeded;  // 执行成功
EBTNodeResult::Failed;     // 执行失败
EBTNodeResult::InProgress; // 正在执行
EBTNodeResult::Aborted;    // 执行被中断
```

其中 Running（运行中）非常重要。

例如，一个怪物距离玩家 10 米，需要花费 2 秒移动到玩家身边。

```
第 0 秒：开始移动，返回 Running
第 1 秒：还没有到达，仍处于 Running
第 2 秒：成功到达，返回 Success
```

只要当前任务还在运行，普通 Sequence 就不会直接执行后面的攻击任务，除非当前行为被中断等。

**Running 并不代表阻塞游戏线程，而是任务尚未完成，等待后续更新或异步回调。**

# **三、Composite（组合节点）详解**

组合节点是行为树控制执行流程的核心。

最常见的三种组合节点为：

- Selector（选择节点）
    
- Sequence（顺序节点）
    
- Parallel（并行节点）
## **1. Selector（选择节点）**

也称为选择器、回退节点（Fallback）。

**只要有一个子节点成功，Selector 就返回成功。**

通常按照从左到右的顺序执行子节点。

<img width="740" height="344" alt="image" src="https://github.com/user-attachments/assets/935225cd-f287-4fd5-9fc9-f0b9b49bded9" />

### **执行规则**

|子节点返回结果|Selector 的处理|
|---|---|
|Success|停止后续节点，返回 Success|
|Failure|尝试下一个子节点|
|Running|保持运行，等待当前任务完成|
|所有子节点 Failure|返回 Failure|

### **C++ 原理伪代码**

```
NodeStatus Selector::Tick()
{
    // CurrentIndex：当前正在执行的子节点下标
    while (CurrentIndex < Children.size())
    {
        NodeStatus Result = Children[CurrentIndex]->Tick();

        if (Result == Success)
        {
            CurrentIndex = 0;
            return Success;
        }

        if (Result == Running)
        {
            // 记录当前执行位置，下次继续执行
            return Running;
        }

        // 当前节点失败，尝试下一个节点
        ++CurrentIndex;
    }

    // 所有子节点都失败
    CurrentIndex = 0;
    return Failure;
}
```

这是带执行位置记忆的 Selector 简化实现，并非 UE 引擎源码。

### **常见使用场景**

Boss 技能优先级：

```
Selector
├── 死亡处理
├── 强制阶段切换
├── 受击硬直
├── 释放必杀技
├── 释放普通技能
├── 追击玩家
└── 待机
```

Selector 非常适合处理具有明确优先级的决策。

但是需要注意：**左侧节点优先级高，不代表它一定可以自动打断正在运行的右侧节点。** 在 UE 中通常需要配合 Observer Aborts（观察者中断）实现。

## **2. Sequence（顺序节点）**

也称为序列节点。

**只有所有子节点都成功，Sequence 才会返回成功。**

只要有一个节点失败，就停止执行后续节点。

<img width="738" height="356" alt="image" src="https://github.com/user-attachments/assets/01b4865f-9ca0-4b5b-9861-b069bb02d893" />

### **执行规则**

|子节点返回结果|Sequence 的处理|
|---|---|
|Success|继续执行下一个子节点|
|Failure|停止执行，返回 Failure|
|Running|等待当前节点执行完毕|
|所有子节点 Success|返回 Success|

### **C++ 原理伪代码**

```
NodeStatus Sequence::Tick()
{
    while (CurrentIndex < Children.size())
    {
        NodeStatus Result = Children[CurrentIndex]->Tick();

        if (Result == Failure)
        {
            // 任何一个节点失败，整个序列失败
            CurrentIndex = 0;
            return Failure;
        }

        if (Result == Running)
        {
            // 当前任务还没有完成
            return Running;
        }

        // 当前节点成功，执行下一个节点
        ++CurrentIndex;
    }

    CurrentIndex = 0;

    // 所有节点都成功
    return Success;
}
```

### **常见使用场景**

例如 Boss 释放一个跳劈技能：

```
Sequence
├── 检查技能释放条件
├── 转向玩家
├── 播放技能前摇
├── 执行跳劈
├── 播放技能后摇
└── 完成技能
```

前一个节点成功完成后，才能继续执行下一个节点。

实际 UE 战斗项目中，也可以将整段技能封装为 GAS Ability，由单个 Task 等待技能结束，而不是让行为树直接管理每一个技能动作。

## **3. Selector 和 Sequence 的区别**

|对比项|Selector|Sequence|
|---|---|---|
|中文|选择节点|顺序节点|
|逻辑类似|OR（或）|AND（与）|
|遇到成功|返回成功|执行下一个|
|遇到失败|执行下一个|返回失败|
|遇到运行中|等待|等待|
|常见用途|行为选择|行为流程|

## **4. Parallel（并行节点）**

用于同时推进多个子行为。

例如：

```
Parallel
├── 移动追击玩家
├── 持续调整朝向
└── 检测周围障碍物
```

并行节点一般可以设置不同的成功或失败策略，例如全部成功才算成功，或者任意一个成功就结束。

**行为树的并行不等于多线程。**

这些任务可以在同一个游戏线程中交替执行，各自维护运行状态，实现逻辑上的并行。

### **UE Simple Parallel（简单并行节点）**

UE 没有采用任意数量子节点的通用并行结构，而是提供 Simple Parallel。

<img width="740" height="343" alt="image" src="https://github.com/user-attachments/assets/c83c20f2-56b3-45f4-b5a1-ea9a439a0884" />

Simple Parallel 只有两个子项：

- Main Task（主任务）：只能是单个 Task。
    
- Background Branch（后台分支）：可以是一棵完整的子树。
    

当主任务完成时，根据 Finish Mode（结束模式）决定如何处理后台分支。

|Finish Mode|说明|
|---|---|
|Immediate|主任务结束，立即中断后台分支|
|Delayed|主任务结束后，等待后台分支完成|

UE 使用 Simple Parallel、Service 和 Observer Aborts 来满足大部分并行行为需求。

# **四、Decorator（装饰器节点）详解**

Decorator 用于修饰 Task 或 Composite，控制某个节点或者整个子树是否允许执行，以及是否需要中断。

例如：

```
Sequence（攻击分支）
│
│  Decorator：TargetActor 有效
│  Decorator：IsInAttackRange == true
│  Decorator：IsSkillReady == true
│
├── 转向玩家
├── 执行攻击
└── 等待攻击结束
```

只有满足装饰器条件，才允许进入攻击分支。

## **1. 常用 Decorator**

|装饰器|中文说明|使用场景|
|---|---|---|
|Blackboard|黑板条件判断|判断目标是否存在|
|Cooldown|冷却时间|限制行为执行频率|
|Time Limit|时间限制|限制追击时间|
|Loop|循环执行|重复执行某个行为|
|Is At Location|位置判断|判断是否到达目标位置|
|Compare Blackboard Entries|黑板数据比较|比较两个黑板变量|
|Force Success|强制成功|忽略某个非必要任务的失败|
|Gameplay Tag Condition|Gameplay Tag 条件|判断角色是否具有某些状态标签|

## **2. Decorator 和 Condition 的区别**

传统行为树通常将 Condition 作为叶子节点。

```
Sequence
├── Condition：目标是否存在
├── Condition：距离是否足够
└── Task：攻击目标
```

UE 推荐使用 Decorator：

```
Sequence
│  Decorator：目标是否存在
│  Decorator：距离是否足够
└── Task：攻击目标
```

Decorator 的优势：

- 可以控制整个子树的执行条件。
    
- 可以监听 Blackboard 数据变化。
    
- 可以在条件改变时中断正在执行的任务。
    
- 条件判断与实际行为更加容易区分。
    

# **五、Observer Aborts（观察者中断机制）——面试重点**

这是 UE 行为树中非常重要的机制。

假设怪物正在巡逻，此时突然发现玩家。

如果行为树没有中断机制，就可能出现怪物必须完成整段巡逻之后，才会开始追击玩家的问题。

Observer Aborts 就是为了解决这类问题。

## **1. 四种中断模式**

|模式|中文|作用|
|---|---|---|
|None|不中断|只在正常搜索该分支时判断条件|
|Self|中断自身|条件失效时，中断当前分支|
|Lower Priority|中断低优先级|条件满足时，抢占右侧低优先级分支|
|Both|双向中断|同时具有 Self 和 Lower Priority 的能力|

具体中断范围由装饰器所在位置和树结构决定，并不是任意中断整棵树。

## **2. None（不中断）**

假设：

```
Selector
├── 攻击分支 [CanAttack == true]
└── 巡逻分支
```

当前正在执行巡逻。

即使 `CanAttack` 从 false 变成 true，也不会单纯因为这个 Decorator 的条件变化而中断巡逻。

需要等正常的行为树搜索重新检查攻击分支。

## **3. Self（中断自身）**

当前正在执行攻击任务。

```
CanAttack = true
        ↓
执行攻击
        ↓
CanAttack = false
        ↓
中断当前攻击分支
        ↓
重新搜索可执行行为
```

常见场景：

- 追击过程中目标死亡。
    
- 追击过程中目标丢失。
    
- 移动过程中目标变得不可达。
    

Self 主要解决的是：**当前行为已经不满足继续执行的条件。**

## **4. Lower Priority（中断低优先级）**

<img width="743" height="551" alt="image" src="https://github.com/user-attachments/assets/1a748721-0510-4f84-8106-d87ff927a546" />

例如怪物正在巡逻，此时 AI Perception（AI 感知系统）发现玩家，将黑板中的 `HasTarget` 修改为 true。

高优先级追击分支上的 Decorator 收到变化通知，发起执行更新请求，中断巡逻任务，进入追击分支。

Lower Priority 主要解决的是：**更高优先级的行为现在可以执行了。**

## **5. Both（双向中断）**

Both = Self + Lower Priority。

对于普通怪物的追击行为，通常可以使用 Both：

```
发现玩家：
    HasTarget = true
    中断巡逻
    开始追击

丢失玩家：
    HasTarget = false
    中断追击
    恢复巡逻
```

## **6. Notify Observer（观察通知方式）**

Blackboard Decorator 还有两个重要设置。

|设置|含义|
|---|---|
|On Result Change|条件判断结果变化时触发相关执行更新|
|On Value Change|被监听的黑板值变化时进行相关检查|

假设黑板中的目标为 `TargetActor`，Decorator 判断条件为 `Is Set`（是否存在目标）。

```
TargetActor = EnemyA;

// 条件仍然为 true
TargetActor = EnemyB;

// 条件仍然为 true
TargetActor = EnemyC;

// 条件从 true 变成 false
TargetActor = nullptr;
```

|目标变化|On Result Change|On Value Change|
|---|---|---|
|EnemyA → EnemyB|否|是|
|EnemyB → EnemyC|否|是|
|EnemyC → nullptr|是|是|

需要注意，收到变化通知并不意味着必然中断任务，还要结合 Observer Aborts、当前执行分支及其他条件进行判断。

# **六、Task（任务节点）详解**

Task 是真正执行 AI 行为的节点。

例如移动、攻击、播放动画、释放技能、寻找掩体等。

## **1. UE 常用 Task**

|Task|中文说明|
|---|---|
|Move To|基于导航系统移动|
|Move Directly Toward|直接朝目标移动，不依赖导航寻路|
|Wait|等待指定时间|
|Play Animation|播放动画|
|Rotate to Face BB Entry|朝向黑板中指定的目标|
|Run Behavior|执行子行为树|
|Run Behavior Dynamic|动态执行子行为树|
|Run EQS Query|执行环境查询|
|Finish With Result|直接以指定结果结束节点|

## **2. Task 生命周期**

<img width="744" height="698" alt="image" src="https://github.com/user-attachments/assets/1cdbb451-5c3e-4f00-8e9f-ea16c3f55370" />

UE C++ 自定义 Task 的核心方法：

|方法|作用|
|---|---|
|ExecuteTask|开始执行任务|
|TickTask|更新运行中的任务，需要开启相应通知|
|AbortTask|处理中断请求|
|FinishLatentTask|通知行为树异步任务结束|
|FinishLatentAbort|通知行为树异步中断结束|
|OnTaskFinished|任务结束时的通知，需要开启相应通知|

## **3. C++ 实现一个等待 Task**

下面使用 UE C++ 实现一个等待 2 秒的 Task，主要用于理解生命周期。

```
// BTTask_CustomWait.h

#pragma once

#include "CoreMinimal.h"
#include "BehaviorTree/BTTaskNode.h"
#include "BTTask_CustomWait.generated.h"

UCLASS()
class UBTTask_CustomWait : public UBTTaskNode
{
    GENERATED_BODY()

public:

    UBTTask_CustomWait();

protected:

    // 开始执行任务
    virtual EBTNodeResult::Type ExecuteTask(
        UBehaviorTreeComponent& OwnerComp,
        uint8* NodeMemory
    ) override;

    // 每帧更新任务
    virtual void TickTask(
        UBehaviorTreeComponent& OwnerComp,
        uint8* NodeMemory,
        float DeltaSeconds
    ) override;

    // 中断任务
    virtual EBTNodeResult::Type AbortTask(
        UBehaviorTreeComponent& OwnerComp,
        uint8* NodeMemory
    ) override;

    // 等待时间，可在行为树中配置
    UPROPERTY(EditAnywhere, Category = "Wait")
    float WaitTime = 2.0f;

private:

    // 当前任务剩余等待时间
    float RemainingTime = 0.0f;
};
```

```
// BTTask_CustomWait.cpp

#include "BTTask_CustomWait.h"

UBTTask_CustomWait::UBTTask_CustomWait()
{
    NodeName = TEXT("Custom Wait");

    // 开启 TickTask 回调
    bNotifyTick = true;

    // 每个行为树组件拥有独立的节点实例
    // 防止不同 AI 共享 RemainingTime
    bCreateNodeInstance = true;
}

EBTNodeResult::Type UBTTask_CustomWait::ExecuteTask(
    UBehaviorTreeComponent& OwnerComp,
    uint8* NodeMemory)
{
    RemainingTime = WaitTime;

    if (RemainingTime <= 0.0f)
    {
        return EBTNodeResult::Succeeded;
    }

    // 任务尚未结束
    return EBTNodeResult::InProgress;
}

void UBTTask_CustomWait::TickTask(
    UBehaviorTreeComponent& OwnerComp,
    uint8* NodeMemory,
    float DeltaSeconds)
{
    RemainingTime -= DeltaSeconds;

    if (RemainingTime <= 0.0f)
    {
        // 通知行为树任务成功完成
        FinishLatentTask(
            OwnerComp,
            EBTNodeResult::Succeeded
        );
    }
}

EBTNodeResult::Type UBTTask_CustomWait::AbortTask(
    UBehaviorTreeComponent& OwnerComp,
    uint8* NodeMemory)
{
    RemainingTime = 0.0f;

    // 中断成功
    return EBTNodeResult::Aborted;
}
```

实际项目可以直接使用 UE 自带的 Wait 节点，上面的代码只是教学示例，未在具体 UE 项目中编译测试；项目模块需要依赖 `AIModule`。

## **4. 为什么 ExecuteTask 返回 InProgress 后还要调用 FinishLatentTask？**

例如释放一个技能：

```
ExecuteTask
    ↓
请求释放技能
    ↓
返回 InProgress
    ↓
技能前摇
    ↓
技能伤害判定
    ↓
技能后摇
    ↓
收到技能结束事件
    ↓
FinishLatentTask(Succeeded)
    ↓
行为树执行后续节点
```

如果一开始就返回 `Succeeded`，行为树会认为技能已经完成，可能立即执行下一个技能。

如果一直返回 `InProgress`，但是没有调用 `FinishLatentTask`，那么在没有其他中断的情况下，行为树就会一直等待这个任务。

异步中断同理，如果 `AbortTask` 返回 `InProgress`，需要通过 `FinishLatentAbort` 通知行为树中断结束。

## **5. 蓝图 Task 对应方法**

|蓝图事件或函数|作用|
|---|---|
|Receive Execute AI|AI 开始执行 Task|
|Receive Tick AI|更新 Task|
|Receive Abort AI|AI 中断 Task|
|Finish Execute|完成 Task，指定成功或失败|
|Finish Abort|完成中断|
|Is Task Executing|判断 Task 是否正在执行|
|Is Task Aborting|判断 Task 是否正在中断|

蓝图开发中非常常见的错误，就是忘记调用 `Finish Execute` 或 `Finish Abort`。

# **七、Service（服务节点）详解**

Service 主要用于在某个行为分支运行期间，周期性地更新 AI 的决策数据。

例如怪物正在追击玩家，同时需要持续更新：

- 与目标的距离。
    
- 玩家是否处于攻击范围。
    
- 玩家是否处于视野中。
    
- 当前最佳攻击目标。
    
- 当前可使用的技能。
    
- 附近是否存在危险区域。

这些逻辑可以放在 Service 中。

<img width="741" height="372" alt="image" src="https://github.com/user-attachments/assets/79317445-83e4-4f4d-9a89-f165ad8b3439" />

## **1. Service 常用参数**

|参数|含义|
|---|---|
|Interval|执行时间间隔|
|Random Deviation|随机时间偏差|
|Call Tick on Search Start|搜索进入时立即调用更新|
|Restart Timer on Each Activation|每次激活时重新开始计时|

例如：

```
Interval = 0.2f;        // 基础执行间隔
RandomDeviation = 0.05f; // 随机时间偏差
```

Service 不一定需要每帧执行。

假设场景中有 500 个怪物，降低 Service 的执行频率可以明显减少重复的距离计算、环境检测和技能评估。

Random Deviation 还可以降低大量 AI 在同一帧执行相同计算造成的 CPU 峰值。

## **2. Service 与 Task 的区别**

|对比|Task|Service|
|---|---|---|
|主要职责|执行行为|更新决策信息|
|返回执行结果|有|通常没有|
|是否控制主流程|是|否|
|执行周期|从开始到完成|分支激活期间周期执行|
|典型用途|移动、攻击|距离检测、目标评估|

**推荐设计：Service 更新数据，Decorator 判断数据，Task 执行行为。**

不要将大量复杂的攻击逻辑直接写在 Service 中，否则容易造成多个行为之间互相冲突。

# **八、Blackboard（黑板系统）详解**

Blackboard 是行为树共享决策数据的容器。

它解决的问题是：不同 Task、Decorator、Service 之间如何共享信息。

## **1. 黑板数据示例**

|Key 名称|类型|作用|
|---|---|---|
|TargetActor|Object|当前攻击目标|
|TargetLocation|Vector|目标位置|
|LastKnownLocation|Vector|目标最后出现的位置|
|DistanceToTarget|Float|与目标的距离|
|HasLineOfSight|Bool|是否能看到目标|
|IsInAttackRange|Bool|是否处于攻击范围|
|IsStunned|Bool|是否处于硬直状态|
|IsDead|Bool|是否死亡|
|CurrentPhase|Enum|Boss 当前阶段|
|SelectedSkillID|Int|当前选中的技能|
|PatrolIndex|Int|当前巡逻点下标|
|HomeLocation|Vector|出生点位置|

## **2. Blackboard 的数据流**

## **3. UE Blackboard C++ 使用**

```
UBlackboardComponent* BB = GetBlackboardComponent();

if (!BB)
{
    return;
}

// 设置攻击目标
BB->SetValueAsObject(
    TEXT("TargetActor"),
    TargetActor
);

// 设置是否发现目标
BB->SetValueAsBool(
    TEXT("HasTarget"),
    IsValid(TargetActor)
);

// 设置目标距离
BB->SetValueAsFloat(
    TEXT("DistanceToTarget"),
    Distance
);

// 设置目标位置
BB->SetValueAsVector(
    TEXT("TargetLocation"),
    TargetLocation
);

// 获取攻击目标
AActor* Target = Cast<AActor>(
    BB->GetValueAsObject(TEXT("TargetActor"))
);

// 清除目标
BB->ClearValue(TEXT("TargetActor"));
```

实际自定义行为树节点中，通常使用 `FBlackboardKeySelector`，而不是到处硬编码 Key 名称。

```
// 在行为树编辑器中选择对应黑板变量
UPROPERTY(EditAnywhere, Category = "Blackboard")
FBlackboardKeySelector TargetKey;
```

这样可以提高节点复用性，降低 Key 名称拼写错误带来的问题。

## **4. Blackboard 应该存储哪些数据？**

推荐存储 AI 决策所需的数据，而不是角色全部数据。

例如角色血量应该由 GAS AttributeSet（属性集）或角色属性组件管理，而不是将 Blackboard 作为血量的权威数据源。

当血量低于某个阈值时，可以更新黑板：

```
BB->SetValueAsBool(
    TEXT("NeedPhaseTransition"),
    HealthPercent <= 0.5f
);
```

Blackboard 更适合作为 AI 决策上下文和部分决策数据的缓存。

## **1. UE 行为树的核心类**

资源负责定义结构，Component 负责维护运行时数据及执行状态。

## **2. 行为树如何启动？**

<img width="740" height="612" alt="image" src="https://github.com/user-attachments/assets/4738a131-712e-417f-95db-46f22c4a148c" />

```
void AEnemyAIController::OnPossess(APawn* InPawn)
{
    Super::OnPossess(InPawn);

    if (!BehaviorTreeAsset)
    {
        return;
    }

    // RunBehaviorTree 会负责建立必要的
    // 行为树组件和黑板初始化流程
    RunBehaviorTree(BehaviorTreeAsset);
}
```

概念上的启动流程：

```
AIController 控制 Pawn
        ↓
RunBehaviorTree
        ↓
初始化 BlackboardComponent
        ↓
初始化 BehaviorTreeComponent
        ↓
加载行为树节点模板
        ↓
分配节点运行时内存
        ↓
从根节点开始搜索
        ↓
找到满足条件的 Task
        ↓
执行 Task
```

## **3. UE 行为树是每帧遍历整棵树吗？**

**不是。UE 行为树采用以事件驱动为主的执行机制。**

传统的 Tick 型行为树可能会周期性地从根节点重新检查行为，具体取决于其实现方式。

UE 则主要在以下情况进行执行更新：

- Task 执行完成。
    
- Blackboard 观察条件发生变化。
    
- Decorator 请求中断。
    
- 相关节点主动发起执行请求。
    
- 行为树启动或重新启动。
    

例如：

```
AI 感知到玩家
        ↓
修改 Blackboard.TargetActor
        ↓
Blackboard 通知观察者
        ↓
Decorator 检查进入条件
        ↓
请求行为树重新搜索
        ↓
中断低优先级任务
        ↓
执行新的高优先级任务
```

事件驱动减少了无意义的整树遍历。

但是，事件驱动不代表行为树完全没有 Tick。

Task 的 `TickTask`、Service 的周期更新、部分 Decorator 的检测以及行为树组件内部的执行处理仍然可能需要 Tick。

## **4. 当前 Task 运行中，行为树如何保存执行位置？**

运行时的 `UBehaviorTreeComponent` 会维护行为树实例、当前活跃节点、执行上下文和节点内存等信息。

例如：

```
Sequence
├── Task A：成功
├── Task B：Running ← 当前执行位置
└── Task C：尚未执行
```

Task B 结束后，行为树根据组合节点规则继续搜索 Task C，而不是无条件地重新执行 Task A。

如果发生中断或重新进入分支，则可能重新执行前面的节点。

# **十、UE 行为树节点的内存管理——高级面试重点**

## **1. 多个 AI 会不会共享同一个 Task 对象？**

**默认情况下，UE 原生行为树节点通常采用共享模板机制。**

假设有 100 个怪物使用同一个行为树资源。

<img width="739" height="490" alt="image" src="https://github.com/user-attachments/assets/8feb95f2-de0d-419d-8adb-2e9689212bf9" />

共享模板可以降低大量 AI 使用同一种行为树时的 UObject 数量及内存开销。

但这也带来了一个问题：不能随意将每个 AI 的运行时数据存储到默认共享节点的成员变量中。

例如：

```
class UBTTask_Attack : public UBTTaskNode
{
    // 如果节点是共享模板，这样存储个体数据有风险
    AActor* CurrentTarget;

    float ElapsedTime;
};
```

假设：

```
AI 1：
CurrentTarget = PlayerA

AI 2：
CurrentTarget = PlayerB

AI 1 再次读取 CurrentTarget：
得到 PlayerB
```

这就产生了数据串扰。

## **2. 如何解决节点共享数据问题？**

主要有三种方案。

### **方案一：bCreateNodeInstance**

```
UBTTask_Attack::UBTTask_Attack()
{
    bCreateNodeInstance = true;
}
```

让行为树组件拥有自己的节点对象实例。

优点是实现简单，可以直接使用成员变量保存运行状态；缺点是大量 AI 会增加 UObject 数量及内存管理成本。

### **方案二：NodeMemory（节点内存）**

UE 为共享节点提供独立的运行时内存块。

```
// 每个 AI 独立的节点运行数据
struct FAttackTaskMemory
{
    float ElapsedTime;
    int32 AttackCount;
};
```

声明所需内存大小：

```
virtual uint16 GetInstanceMemorySize() const override
{
    return sizeof(FAttackTaskMemory);
}
```

执行节点时获取对应内存：

```
EBTNodeResult::Type UBTTask_Attack::ExecuteTask(
    UBehaviorTreeComponent& OwnerComp,
    uint8* NodeMemory)
{
    // 获取当前行为树实例的节点内存
    FAttackTaskMemory* Memory =
        reinterpret_cast<FAttackTaskMemory*>(NodeMemory);

    // 每次执行时初始化本次任务的数据
    Memory->ElapsedTime = 0.0f;
    Memory->AttackCount = 0;

    return EBTNodeResult::InProgress;
}
```

这种方式适合高频、大量 AI 使用的原生 C++ 节点。

实际项目应正确处理内存初始化与清理；如果结构包含非平凡构造或析构的成员，需要遵循 UE 的节点内存生命周期管理方式。

特别注意：NodeMemory 是原始运行时内存，不属于 UObject 反射系统，GC 不会自动扫描其中的 UObject 指针作为强引用。

### **方案三：Blackboard 或角色组件**

如果数据需要被多个节点共享，可以保存到 Blackboard。

如果数据属于角色自身的战斗状态，可以保存到战斗组件、GAS 或其他角色组件。

## **3. 三种方案对比**

|对比项|Node Instance|NodeMemory|Blackboard|
|---|---|---|---|
|节点对象|独立实例|共享模板|不限制|
|个体数据|成员变量|独立内存块|黑板 Key|
|内存开销|相对较高|通常较低|取决于字段|
|使用难度|低|较高|低|
|数据共享范围|当前节点实例|当前节点内存|多个节点|
|适合场景|复杂异步任务|大量简单 AI|公共决策信息|

这三种机制都是 UE 行为树的重要数据存储方式。

# **十一、动作游戏 Boss 行为树设计**

以类似《鸣潮》的动作游戏 Boss 为例，以下是一种推荐架构，不代表《鸣潮》实际采用的内部实现。

## **1. Boss 行为树整体结构**

<img width="740" height="940" alt="image" src="https://github.com/user-attachments/assets/c856201f-f7e7-4332-ac94-827a2df923c1" />

## **2. Boss 技能选择不能只依靠固定 Selector**

假设 Boss 有四个技能。

```
Selector
├── 普通斩击
├── 跳劈
├── 突进
└── 范围攻击
```

如果普通斩击始终满足条件，那么 Boss 可能一直释放普通斩击，后续技能得不到执行机会。

这就是低优先级行为饥饿（Starvation）问题。

解决方案包括：

- 技能冷却限制。
    
- 加权随机选择。
    
- Utility AI（效用 AI）评分。
    
- 技能重复使用惩罚。
    
- 连招组合规则。
    
- 阶段技能池。
    
- 特定技能次数限制。
    

推荐结构：

```
Sequence：技能攻击
├── 更新可用技能列表
├── 根据战斗情况计算技能评分
├── 选择合适技能
├── 调整距离和朝向
├── 激活 Gameplay Ability
└── 等待技能结束
```

例如技能评分：

$$
Score = W_dD + W_cC + W_pP - W_rR
$$

其中：

|参数|含义|
|---|---|
|D|距离适合度|
|C|技能释放条件适合度|
|P|当前 Boss 阶段适合度|
|R|技能重复使用惩罚|
|W|各因素的权重|

<img width="736" height="623" alt="image" src="https://github.com/user-attachments/assets/9922454b-a76a-4888-9720-8de78b9a20ba" />

这样可以实现：

**行为树负责决定做什么类型的行为，Utility AI 负责在多个候选技能中选择最佳技能。**

## **3. 行为树如何与 GAS 配合？**

对于 UE 动作游戏，推荐进行职责划分。

|系统|职责|
|---|---|
|Behavior Tree|高层 AI 决策|
|Utility AI|技能评分和选择|
|GAS|技能执行、冷却、消耗、取消|
|Gameplay Tag|战斗状态及技能限制|
|Character Movement|角色移动|
|Animation Blueprint|动画表现|
|Anim Montage|攻击动作及连招表现|
|Anim Notify|动画关键帧事件|
|Combat Component|战斗业务逻辑|
|Blackboard|AI 决策数据|

<img width="737" height="657" alt="image" src="https://github.com/user-attachments/assets/4a433d32-9817-4d9b-bf1f-e302cdaa64a8" />

Task 不应该仅仅通过等待固定的 2 秒来判断技能结束。

更推荐监听技能结束事件，因为技能实际执行时间可能受到攻速、受击打断、动画播放速率以及技能取消等影响。

需要区分技能正常完成、取消和激活失败，并匹配本次激活对应的技能实例或执行标识，防止其他技能的结束事件误结束当前 Task。

## **4. Boss 技能释放过程中如何处理中断？**

这是动作游戏 AI 设计的核心问题之一。

假设 Boss 正在释放攻击，玩家触发了破韧效果。

```
玩家攻击 Boss
        ↓
韧性下降至 0
        ↓
GAS / Combat 添加 State.Stunned
        ↓
更新 Blackboard.IsStunned
        ↓
Decorator 请求中断攻击分支
        ↓
AbortTask
        ↓
请求取消当前可取消技能
        ↓
清理技能相关状态
        ↓
执行硬直行为
```

但是，不是所有技能都应该允许随时打断。

|技能阶段|推荐中断策略|
|---|---|
|前摇阶段|根据设计允许中断|
|普通攻击阶段|根据霸体、韧性判断|
|不可取消阶段|延迟处理普通中断请求|
|后摇阶段|通常允许部分中断|
|死亡|强制终止相关行为|

因此需要设置类似的 Gameplay Tag：

```
State.Attacking          // 正在攻击
State.Stunned            // 硬直状态
State.SuperArmor         // 霸体状态
State.Uninterruptible    // 不可被普通行为打断
State.PhaseTransition    // 阶段切换
State.Dead               // 死亡状态
```

**行为树中断与技能取消是两个不同的概念。**

行为树中断了 Task，不代表 GAS 中的技能一定已经停止，也不代表 Montage、Timer、Root Motion 和碰撞检测已经停止。

需要在中断流程中根据技能规则进行清理，或者等待技能完成允许的中断过程。

# **十二、行为树与状态机、效用 AI 的区别**

|对比项|FSM 状态机|BT 行为树|Utility AI 效用 AI|
|---|---|---|---|
|核心机制|状态与转换|树形节点组合|行为评分|
|行为选择|状态转换条件|节点顺序及条件|评分高低|
|优先级|手动设计转换规则|通常由树结构决定|动态评分|
|复杂流程|容易出现大量转换|适合层级组织|通常需要配合执行系统|
|行为复用|一般|较强|较强|
|AI 可预测性|高|较高|取决于评分模型|
|调试难度|简单状态时较低|树较大时增加|需要分析评分|
|适用场景|角色状态管理|AI 高层决策|动态行为及技能选择|

## **1. 状态机容易出现什么问题？**

如果角色有攻击、移动、受击、闪避、待机、死亡等状态，并且大量状态之间需要互相切换，就可能出现状态转换膨胀。

<img width="741" height="437" alt="image" src="https://github.com/user-attachments/assets/9a3322d3-0d50-486b-87b1-5d320c17e8c7" />

如果有 N 个状态，每个状态都可能转换到其他状态，最坏情况下转换数量为：

$$
N(N-1)=O(N^2)
$$

不过这是全连接状态转换的最坏情况，并非所有状态机都会达到这个复杂度。层级状态机（HFSM）也可以缓解这一问题。

## **2. 行为树能完全替代状态机吗？**

不能，也没有必要。

在大型动作游戏中，两者通常结合使用。

例如：

```
高层决策：Behavior Tree
    ├── 追击
    ├── 攻击
    ├── 闪避
    └── 逃跑

技能选择：Utility AI
    ├── 普通攻击评分
    ├── 突进攻击评分
    └── 范围攻击评分

底层动作控制：FSM / GAS
    ├── 技能前摇
    ├── 技能生效
    ├── 技能后摇
    └── 技能结束

动画表现：Animation State Machine
    ├── Idle
    ├── Run
    ├── Jump
    └── Fall
```

这样可以避免将所有动作、动画、技能和状态管理都塞进行为树。

# **十三、行为树性能优化**

## **1. 避免大量每帧检测**

不要让每个 AI 每帧都执行距离检测、射线检测、导航查询、技能评分和目标搜索。

根据业务设置不同的更新频率：

|检测内容|示例频率|
|---|---|
|死亡状态|事件驱动|
|受击硬直|事件驱动|
|发现目标|AI 感知事件|
|攻击距离|0.1～0.2 秒|
|技能评分|决策时或 0.2～0.5 秒|
|普通目标搜索|0.5～1 秒|
|昂贵的 EQS 查询|按需或较低频率|

以上频率只是参考，需要结合游戏响应要求和性能分析调整。

## **2. AI LOD（AI 逻辑细节层级）**

根据距离、重要程度和战斗状态控制 AI 更新频率。

<img width="758" height="295" alt="image" src="https://github.com/user-attachments/assets/ee4a6e6c-3f0d-4acb-a13b-0e12c08e25c9" />

## **3. 其他常见优化方案**

|优化方案|主要作用|
|---|---|
|事件驱动|减少无意义条件轮询|
|Service 随机间隔|避免同帧计算峰值|
|NodeMemory|减少节点实例化开销|
|Blackboard 缓存|避免重复计算|
|空间划分|减少目标搜索范围|
|导航请求节流|减少重复寻路|
|EQS 查询节流|降低环境查询成本|
|子行为树复用|降低维护复杂度|
|决策时间预算|避免大量 AI 同时执行昂贵计算|
|AI LOD|降低不重要 AI 的计算频率|

性能分析时需要注意：真正昂贵的部分往往不是 Selector、Sequence 本身，而是节点内部执行的导航、碰撞查询、感知、EQS 和动画等操作。

# **十四、行为树常见工程问题**

## **1. 行为反复切换（Thrashing，行为震荡）**

例如攻击距离为 3 米：

```
Distance <= 3.0f   // 攻击
Distance > 3.0f    // 追击
```

当玩家在 3 米附近移动时：

```
2.99 米：攻击
3.01 米：追击
2.98 米：攻击
3.02 米：追击
```

AI 就可能不断地切换行为。

### **解决方案：Hysteresis（迟滞区间）**

进入攻击状态和退出攻击状态使用不同阈值。

<img width="742" height="365" alt="image" src="https://github.com/user-attachments/assets/a50f3b97-903c-4932-ba34-967f73257247" />

```
if (bInAttackMode)
{
    // 已经处于攻击模式
    // 只有距离达到 4 米才退出
    if (Distance >= 400.0f)
    {
        bInAttackMode = false;
    }
}
else
{
    // 处于追击模式
    // 只有距离进入 3 米才开始攻击
    if (Distance <= 300.0f)
    {
        bInAttackMode = true;
    }
}
```

UE 默认长度单位为厘米，因此这里使用 300 和 400。

此外，还可以使用最短行为持续时间、冷却时间、技能锁定和中断优先级减少行为震荡。

## **2. Task 已经中断，但是回调还在执行**

例如攻击任务绑定了 Montage 结束回调。

```
攻击任务 A 开始
        ↓
绑定动画结束回调
        ↓
A 被中断
        ↓
攻击任务 B 开始
        ↓
A 的旧回调突然触发
        ↓
错误地结束了当前任务
```

解决方式：

- 在 AbortTask 中解绑 Delegate（委托）。
- 清理 Timer（定时器）。
- 取消异步查询或移动请求。
- 使用 RequestID / ExecutionID 区分不同执行请求。
- 检查当前任务状态及对象有效性。
- 确保完成通知不会重复调用。

仅检查 Task 是否正在执行，有时仍然不够，因为同一个 Task 可能已经进入新一轮执行。

## **3. 多人游戏如何同步行为树？**

通常采用服务器权威模式。

<img width="744" height="425" alt="image" src="https://github.com/user-attachments/assets/7054d9f8-7869-4d71-bb22-f73d48247308" />

一般不需要将整棵行为树、当前执行节点和所有 Blackboard Key 都同步到客户端。

主要同步行为结果：

|同步内容|作用|
|---|---|
|角色位置和旋转|AI 移动表现|
|技能激活及必要信息|攻击表现|
|Gameplay Tag|战斗状态|
|血量、韧性|属性表现|
|Montage 状态|动画表现|
|Gameplay Cue|特效、音效|
|Boss Phase|阶段相关表现|

这样可以避免不同客户端独立进行 AI 决策导致结果不一致。

# **十五、行为树高频面试题及答案**

以下重点保留 UE 游戏客户端、动作游戏战斗开发中常见且实用的问题。

## **面试题 1：什么是行为树？**

行为树是一种树形 AI 决策架构，通过 Selector、Sequence 等组合节点组织行为逻辑，并根据子节点的 Success、Failure、Running 返回值控制执行流程。

它的主要优势是模块化、层级化、可复用以及易于扩展。

## **面试题 2：Selector 和 Sequence 有什么区别？**

Selector 类似逻辑或，只要一个子节点成功，整个节点就成功。

Sequence 类似逻辑与，只有全部子节点成功，整个节点才成功。

两者遇到 Running 通常都会等待当前节点完成，但具体的重新评估行为取决于实现。

## **面试题 3：行为树为什么需要 Running 状态？**

因为游戏中的很多行为不是瞬间完成的，例如移动、攻击和播放动画。

Running 允许节点跨帧或异步执行，在不阻塞游戏线程的情况下保持任务状态，直到任务完成或者被中断。

## **面试题 4：Decorator、Service、Task 分别有什么作用？**

Decorator 负责条件判断及执行限制，Service 负责定期更新决策数据，Task 负责执行具体行为。

典型流程是：

```
Service 更新距离
        ↓
Blackboard 保存距离或范围判断结果
        ↓
Decorator 判断是否满足攻击条件
        ↓
Task 执行攻击
```

## **面试题 5：UE 行为树每帧都会从根节点开始遍历吗？**

不会。

UE 行为树主要采用事件驱动机制，通过 Blackboard 观察、Decorator 中断和 Task 完成事件触发执行更新。

但部分 Task、Service 和 Decorator 仍然可能使用 Tick。

## **面试题 6：UE 的 Observer Aborts 有哪些模式？**

四种：

|模式|作用|
|---|---|
|None|不主动中断|
|Self|条件失效时中断自身分支|
|Lower Priority|条件成立时抢占低优先级分支|
|Both|同时支持上述两种中断|

## **面试题 7：高优先级节点一定会立即打断低优先级节点吗？**

不一定。

优先级主要影响行为树搜索时的选择顺序。如果低优先级任务正在执行，需要通过观察者中断等机制触发重新搜索。

如果中断任务还需要进行异步清理，那么新任务可能需要等待中断流程完成。

## **面试题 8：Blackboard 有什么作用？**

Blackboard 用于存储 AI 决策所需的数据，使不同 Task、Service 和 Decorator 能共享决策上下文。

同时它支持观察者机制，可以在数据变化时通知相关节点。

Blackboard 不应该承担所有角色业务数据的管理职责。

## **面试题 9：多个 AI 使用同一个行为树，节点对象是否共享？**

默认的非实例化原生节点采用共享模板。

每个 AI 的 BehaviorTreeComponent 会维护自己的运行状态和节点内存。

如果需要独立节点对象，可以开启：

```
bCreateNodeInstance = true;
```

也可以使用 NodeMemory 保存独立运行数据。

## **面试题 10：NodeMemory 有什么作用？**

NodeMemory 用于在共享节点模板的情况下，为不同的行为树实例提供独立运行时内存。

这样既避免了不同 AI 的数据串扰，又减少了为每个 AI 创建所有节点 UObject 的开销。

## **面试题 11：ExecuteTask 返回 InProgress 后，如何通知任务结束？**

调用：

```
FinishLatentTask(
    OwnerComp,
    EBTNodeResult::Succeeded
);
```

如果执行失败，则传入 `EBTNodeResult::Failed`。

蓝图 Task 中对应的是 `Finish Execute`。

## **面试题 12：AbortTask 返回 InProgress 是什么意思？**

代表任务已经收到中断请求，但是中断清理尚未完成。

例如需要等待技能停止事件、异步资源释放或者某个安全取消时机。

清理完成后需要调用：

```
FinishLatentAbort(OwnerComp);
```

## **面试题 13：Parallel 节点是不是多线程执行？**

不是。

Parallel 表示逻辑上的多个行为同时推进，不代表创建多个操作系统线程。

UE Simple Parallel 由一个主 Task 和一个后台行为分支组成。

## **面试题 14：行为树有哪些优缺点？**

|优点|缺点|
|---|---|
|模块化程度高|大型树可能难以维护|
|子树及节点易复用|分支之间存在隐式优先级|
|适合复杂 AI 决策|中断机制容易设计错误|
|条件和行为相对独立|固定优先级可能导致行为饥饿|
|支持可视化调试|异步任务的生命周期较复杂|
|方便扩展行为|不适合直接管理所有细粒度状态|

## **面试题 15：行为树和状态机的区别是什么？**

状态机以当前状态和状态转换为核心，行为树以树形行为选择和任务执行为核心。

状态机适合明确、稳定的状态转换；行为树适合具有层级结构、优先级和复杂条件的 AI 决策。

两者通常结合，而不是相互替代。

## **面试题 16：如何避免行为树频繁切换行为？**

可以通过以下机制处理：迟滞区间、最短执行时间、技能冷却、重复执行惩罚、中断优先级和不可取消阶段。

例如攻击进入距离为 3 米，退出距离为 4 米，避免 AI 在 3 米附近反复切换。

## **面试题 17：如何设计一个动作游戏 Boss 的行为树？**

将死亡、阶段切换、硬直、技能攻击、战斗移动和待机等行为按优先级组织。

行为树负责高层决策，Utility AI 负责技能选择，GAS 负责技能执行和取消，状态机负责动作状态，动画系统负责表现。

重点处理技能中断、阶段切换、冷却限制、行为震荡和任务异步生命周期。

## **面试题 18：行为树如何处理技能释放过程中的受击？**

通过战斗系统判断是否触发硬直、霸体是否有效以及当前技能是否可取消。

当满足中断条件时，更新 Blackboard 或触发 Decorator 执行更新，行为树中断攻击 Task，并由 Task 请求取消相应的 Gameplay Ability。

技能和动画清理完成后，进入受击分支。

## **面试题 19：如何优化大量 AI 的行为树性能？**

主要从降低决策频率和减少单次决策成本两方面入手。

采用事件驱动、Service 间隔、随机错峰、NodeMemory、AI LOD、目标缓存以及导航和 EQS 查询节流等方案。

重点通过 Unreal Insights、Gameplay Debugger、Behavior Tree Debugger 和 Visual Logger 定位真正的性能瓶颈。

## **面试题 20：行为树节点不执行或者卡住了，如何排查？**

推荐按照以下顺序排查：

1. AIController 是否成功 Possess 角色。
2. RunBehaviorTree 是否成功启动。
3. Blackboard 是否正确初始化。
4. Decorator 条件是否满足。
5. Observer Aborts 是否正确配置。
6. 高优先级分支是否一直占用执行机会。
7. Task 是否忘记调用 FinishExecute 或 FinishLatentTask。
8. 中断流程是否一直处于 Aborting。
9. 导航系统是否正常，Move To 是否可以到达。
10. 技能、动画、异步任务回调是否正确触发。
