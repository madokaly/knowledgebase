可以把我们前面讨论的整套机制整理成一个比较完整、适合 UE 动作游戏的模型：

# 核心原则

**输入不是一律先进入缓存。**

```
玩家产生输入后，系统先判断：

输入发生  
  ↓  
当前状态下能不能立刻执行？  
  ├─ 能 → 立即执行  
  └─ 不能  
      ↓  
   这个输入能不能缓存？  
      ├─ 能 → 进入 Input Buffer  
      └─ 不能 → 丢弃

所以输入最终只有三种结果：

Immediate Execute   立即执行  
Buffered            缓存等待  
Rejected            丢弃
```

# 1. 为什么需要输入缓存

缓存主要解决：

玩家比“真正允许动作衔接的时间点”稍微早按了一点。

例如：

Attack1 正在播放  
      ↓  
玩家提前按 Attack  
      ↓  
现在还不能进入 Attack2  
      ↓  
缓存 Attack  
      ↓  
进入 Combo Window  
      ↓  
消费缓存  
      ↓  
Attack2

所以：

Attack1 → 提前按Attack → Attack2

会感觉非常流畅。

如果没有缓存，就必须正好在那几十毫秒的窗口里按键，手感会很差。

---

# 2. 缓存不是简单 FIFO 队列

不建议把动作游戏理解成：

Queue:  
Attack  
Dodge  
Skill  
Jump

然后：

一个一个执行

因为这样很容易出现：

Attack  
↓  
Dodge  
↓  
角色闪避  
↓  
突然又执行半秒前留下来的 Attack

玩家会觉得角色在执行“过期命令”。

更合理的是：

**缓存表示当前尚未完成的玩家意图，而不是待办事项队列。**

因此状态发生重大变化以后，旧意图可能失效。

---

# 3. 一个输入至少应该包含什么

例如：

struct FBufferedInput  
{  
    EInputType Type;  
    float Timestamp;  
    float ExpireTime;  
};

必要时还可以增加：

InputSourceState;  
Priority;  
SequenceID;

例如：

Type = Attack  
Timestamp = 10.32  
ExpireTime = 0.20  
Source = Attack1

这样系统知道：

 这个 Attack 是在 Attack1 状态下产生的。

---

# 4. 缓存有有效期

缓存不能永久保存。

例如：

Attack Buffer = 0.20s  
Dodge Buffer = 0.15s  
Guard Buffer = 0.12s  
Skill Buffer = 0.20s

典型范围大约：

0.1 ~ 0.25 秒

核心目标是：

允许“早按一点”

但不要变成：

“半秒前按的东西现在突然执行”

---

# 5. 顿帧期间最好不要消耗缓存时间

如果：

Attack Buffer = 0.15s  
HitStop = 0.10s

顿帧期间如果仍然计算过期：

缓存只剩 0.05s

这会让命中顿帧反而更容易吃输入。

所以可以用：

CombatTime

计算缓存寿命。

顿帧时：

WorldTime 继续  
CombatTime 暂停

于是：

InputBuffer 不会因为 HitStop 自动过期

不过可以额外设置一个真实时间最大寿命，避免极端情况下无限保存。

---

# 6. 能立即执行的输入，不需要进入缓存

这是我们后面讨论中最重要的一点。

例如：

当前：Attack1

玩家按：

Dodge

如果 Attack1 当前允许：

Dodge Cancel

那么：

Dodge  
↓  
CanExecuteImmediately = true  
↓  
直接进入 Dodge

而不是：

Dodge → Buffer → 等待 → 执行

所以闪避很可能根本没有和之前缓存的 Attack 进行“缓存优先级竞争”。

---

# 7. 这正好解释你对秧秧的测试

你观察到：

## 情况 A

Attack  
→ Attack

结果：

Attack1  
→ Attack2

解释：

第二次 Attack 当前不能立即执行  
↓  
进入缓存  
↓  
Combo Window 打开  
↓  
执行 Attack2

---

## 情况 B

Attack1  
↓  
按 Attack  
↓  
再按 Dodge

结果：

Attack1 → Dodge

很可能发生的是：

Attack  
↓  
不能立即执行  
↓  
进入缓存  

Dodge  
↓  
当前可以 Dodge Cancel  
↓  
立即执行 Dodge  
↓  
AttackState 结束  
↓  
旧 Attack 缓存失效/清除

所以不是：

Dodge 用高优先级覆盖 Attack

而更可能是：

Dodge 直接执行  
+  
状态切换导致旧 Attack 意图失效

---

# 8. 而另一个实验进一步验证了这个模型

你测试：

Attack  
→ Dodge  
→ 快速 Attack

结果：

Attack  
→ Dodge  
→ Attack

说明：

Dodge 之前产生的 Attack  
→ 旧意图  
→ 清除

但：

Dodge 之后产生的 Attack  
→ 新意图  
→ 可以进入 Dodge 状态下的缓存

因此可以理解成：

Attack State  
│  
├─ Buffered Attack  
│  
└─ Dodge 输入  
      ↓  
   立即执行  
      ↓  
   Enter Dodge State  
      ↓  
   清旧缓存  
      ↓  
   玩家重新按 Attack  
      ↓  
   新 Attack Buffer  
      ↓  
   Dodge Attack Window  
      ↓  
   执行

---

# 9. 所以缓存应该具有“状态上下文”

这是非常重要的。

一个 Attack 输入不应该只是：

Attack

而可以理解为：

Attack Intent  
产生于 Attack1 State  
时间 = 10.2s

当：

Attack1 → Dodge

发生之后：

Attack1 Context 已经结束

因此属于这个上下文的缓存可以全部失效。

类似：

void ExitAttackState()  
{  
    ClearBufferedInputsFromThisState();  
}

或者：

ClearInputsBefore(DodgeExecuteTime);

两种实现都能得到类似效果。

---

# 10. 多个缓存存在时如何决定执行哪个

如果同时确实存在多个有效缓存：

Attack  
Skill  
Jump

应该先：

删除过期输入  
↓  
判断当前哪些能执行  
↓  
从可执行输入里进行仲裁

例如：

Attack CanExecute = Yes  
Skill CanExecute = Yes  
Jump CanExecute = No

然后再比较：

当前状态下的 Priority

比如：

Skill = 90  
Attack = 60

执行：

Skill

所以正确顺序是：

CanExecute  
    ↓  
Priority  
    ↓  
Timestamp

而不是：

谁后按谁执行

也不是：

谁先按谁执行

---

# 11. Priority 最好不是全局固定值

例如不要永久规定：

Dodge > Skill > Attack

而应该：

> **Priority 由当前状态决定。**

比如普通待机：

Skill 90  
Dodge 80  
Attack 70

攻击后摇：

Dodge 100  
Skill 90  
Attack 60

特殊连击窗口：

Attack 100  
Dodge 90  
Skill 80

这样手感才能细调。

---

# 12. 但很多时候甚至不需要 Priority

因为如果：

Dodge 当前能立即执行

而：

Attack 当前只能缓存

那它们根本没有进入同一层竞争。

真正流程是：

Attack 输入  
↓  
不能立即执行  
↓  
缓存  

Dodge 输入  
↓  
可以立即执行  
↓  
直接执行

Priority 主要用在：

> **多个缓存同时变成可执行状态时，决定消费哪个。**

---

# 13. 状态切换时要清理旧缓存

这也是动作游戏输入系统中非常重要的一环。

比如：

Attack → Dodge

可以：

清除：  
旧 Combo Attack  
旧 Jump  
旧 Guard

但保留：

Dodge 状态开始后重新输入的 Attack

因此：

状态切换  
≠  
永远保留所有缓存

更应该：

State Transition  
↓  
Invalidate Old Intent

---

# 14. Combo Buffer 可以和通用 Action Buffer 分开

对于《鸣潮》这种游戏，我更建议：

Input System  
│  
├── Combo Buffer  
│ └── NextAttack  
│  
├── Action Buffer  
│ ├── Skill  
│ ├── Jump  
│ └── Guard  
│  
└── Immediate Actions  
      └── Dodge / Parry 等

这不是绝对要求，但非常符合这类游戏的行为。

例如：

NextAttack

本质上其实不是：

> “未来必须执行一次攻击”。

而是：

> “如果当前连击还能继续，我想接下一段。”

这就是一个 **Combo Intent**。

一旦玩家闪避取消攻击：

Combo Context 消失

那：

NextAttack Intent

自然应该清除。

---

# 15. 最终推荐的完整执行流程

你自己在 UE 里可以做成：

Input Event  
    ↓  
CanExecuteImmediately?  
    │  
    ├── Yes  
    │ ↓  
    │ Execute  
    │ ↓  
    │ State Transition  
    │ ↓  
    │ Clear / Invalidate Old Buffer  
    │  
    └── No  
          ↓  
      CanBuffer?  
          │  
          ├── Yes → Add / Update Buffer  
          │  
          └── No → Reject

然后每次：

进入新的 Cancel Window  
进入新的 Combo Window  
状态发生变化

再执行：

Check Buffered Inputs  
    ↓  
Remove Expired  
    ↓  
CanExecute?  
    ↓  
Priority  
    ↓  
Timestamp  
    ↓  
Execute Best Input

---

## 最后用一句话概括整套机制

> **输入缓存不是“把玩家按过的所有键排队执行”，而是暂时保存当前无法立即执行、但短时间内仍可能有效的玩家意图；能立即执行的动作直接执行，强状态切换会使旧状态下的缓存意图失效，而新状态下产生的新输入则重新进入新的执行/缓存判断。**

如果是你现在做的 UE 战斗系统，我会把这套机制拆成四个概念：

Input Request 玩家输入意图  
Immediate Execute 立即执行判断  
Input Buffer 暂存未来意图  
State Transition 状态切换 + 旧意图失效

这四个一旦分开，后面的**普攻连段、闪避取消、技能取消、格挡、弹刀、闪避攻击**都会很好搭。
