在 Unreal Engine（UE）中，`Actor`、`Pawn`、`Character`、`PlayerController`、`PlayerState` 是 Gameplay Framework（游戏玩法框架）中非常核心的五个类。

理解它们最重要的是区分三件事：

1. 继承关系：谁继承谁？
    
2. 控制关系：谁控制角色移动、攻击和执行动作？
    
3. 数据关系：玩家的数据、角色的数据分别存在哪里？
    

先记住一个核心结论：

> Actor 是世界中的对象，Pawn 是可以被控制的对象，Character 是具有角色移动能力的 Pawn，PlayerController 负责控制 Pawn，PlayerState 负责记录玩家状态。

## 一、五个类的继承关系

<img width="738" height="565" alt="image" src="https://github.com/user-attachments/assets/60bcf294-21b1-44d7-8001-5047802dc605" />


对应的 C++ 继承结构：

```
UObject
└── AActor
    ├── APawn
    │   ├── ACharacter
    │   ├── ADefaultPawn
    │   └── ASpectatorPawn
    │
    ├── AController
    │   ├── APlayerController
    │   └── AAIController
    │
    └── AInfo
        └── APlayerState
```

注意两个关键点：

- `ACharacter` 继承自 `APawn`，`APawn` 继承自 `AActor`。
    
- `APlayerController` 不是 `APawn` 的子类，而是 `AController` 的子类。它与 Pawn 之间是控制关系，而不是继承关系。
    

这意味着 `PlayerController` 和 `Character` 是两个独立的 Actor，它们通过 Possess（控制、接管）建立联系。

## 二、五个类分别负责什么？

|类|中文含义|核心职责|
|---|---|---|
|`AActor`|游戏对象|提供世界中的对象基础能力|
|`APawn`|可控制实体|提供可被 Controller 控制的实体|
|`ACharacter`|游戏角色|提供角色移动、碰撞、骨骼网格体等功能|
|`APlayerController`|玩家控制器|接收玩家意图、管理控制目标|
|`APlayerState`|玩家状态|保存需要共享的玩家级状态数据|

### 1. AActor：所有这些对象的基础

`AActor` 是能够存在于游戏世界中的基本对象。

例如：

- 玩家与敌人
    
- 武器、子弹、可拾取物品
    
- 门、机关、陷阱
    
- PlayerController、PlayerState 等框架对象
    

Actor 提供的基础能力包括：

```
// 获取世界位置
GetActorLocation();

// 设置世界位置
SetActorLocation(NewLocation);

// 获取旋转
GetActorRotation();

// 销毁 Actor
Destroy();

// 获取世界对象
GetWorld();
```

但是，Actor 本身不包含完整的玩家控制体系。

例如，游戏中的一把武器通常可以继承 Actor，但并不需要继承 Pawn。

### 2. APawn：可以被控制的 Actor

`APawn` 的最大特点是：能够被 Controller 接管控制。

例如：

- 可操作的车辆
    
- 可操纵的无人机
    
- 玩家角色
    
- 可以被 AI 控制的实体
    

Pawn 提供了 Controller 关联、控制输入处理等基础机制，但并不默认提供 Character 那套行走、跳跃等移动功能。

```
// 获取当前控制这个 Pawn 的控制器
AController* Controller = GetController();

// 接收移动输入
AddMovementInput(
    FVector(1.0f, 0.0f, 0.0f),
    1.0f
);
```

注意：`AddMovementInput()` 只是提供移动输入，并不代表普通 Pawn 一定能够自动移动。普通 Pawn 往往需要自行实现移动，或者配合合适的 MovementComponent。

### 3. ACharacter：专门用于角色的 Pawn

`ACharacter` 在 `APawn` 基础上提供了较完整的角色功能。

<img width="379" height="348" alt="image" src="https://github.com/user-attachments/assets/88c146b0-2e98-40f5-96f9-e00e1f9fa8db" />


Character 常用组件

- `CapsuleComponent`：胶囊碰撞
    
- `SkeletalMeshComponent`：骨骼网格体
    
- `CharacterMovementComponent`：角色移动组件
    

其中 `CharacterMovementComponent` 是 Character 相比普通 Pawn 的关键优势。

它支持行走、跳跃、下落、游泳、飞行等移动模式，还提供针对网络游戏的角色移动预测与校正机制。

例如：

```
// Character 直接提供跳跃接口
Jump();

// 停止跳跃
StopJumping();

// 获取角色移动组件
UCharacterMovementComponent* Movement =
    GetCharacterMovement();

// 设置最大行走速度
Movement->MaxWalkSpeed = 600.0f;
```

什么时候选 Pawn，什么时候选 Character？

大多数第三人称动作游戏中的人物适合使用 `ACharacter`；特殊车辆、飞船、炮台等具有非标准运动方式的实体通常可以考虑 `APawn`。

### 4. APlayerController：玩家的控制者

`PlayerController` 可以理解为玩家的操作代理。

它不需要像 Character 一样拥有可见的身体，而是负责决定：

- 玩家当前控制哪个 Pawn。
    
- 玩家输入应该如何处理。
    
- 当前相机和视角如何管理。
    
- 玩家如何与服务器进行交互。
    

例如：

```
// 获取当前被控制的 Pawn
APawn* CurrentPawn = GetPawn();

// 获取玩家控制的朝向
FRotator Rotation = GetControlRotation();

// 切换控制目标（应由权威端执行）
Possess(NewPawn);

// 取消控制当前 Pawn
UnPossess();
```

假设玩家从人物切换到汽车：

```
// 最初
PlayerController -> Character

// 上车之后
PlayerController -> VehiclePawn

// 下车之后
PlayerController -> Character
```

在整个过程中，`PlayerController` 可以保持不变，只需要切换它控制的 Pawn。

这也是 PlayerController 和 Pawn 被设计成两个类的重要原因。

### 5. APlayerState：玩家自身的状态数据

`PlayerState` 记录的是玩家级状态，不是单纯的角色身体状态。

例如：

```
UCLASS()
class AMyPlayerState : public APlayerState
{
    GENERATED_BODY()

public:
    // 玩家队伍编号
    UPROPERTY(Replicated)
    int32 TeamId = 0;

    // 玩家累计击杀数
    UPROPERTY(Replicated)
    int32 KillCount = 0;

    // 玩家当前比赛得分
    UPROPERTY(Replicated)
    int32 MatchScore = 0;
};
```

PlayerState 的一个重要特点是能够把玩家的数据同步给其他客户端。

例如，一场多人游戏中：

- 玩家 A 的 PlayerController 在服务器和玩家 A 的客户端存在。
    
- 玩家 A 的 PlayerState 在服务器、玩家 A 和玩家 B 的客户端都可以存在。
    

所以玩家 B 可以通过玩家 A 的 PlayerState 获取他的名字、队伍、击杀数和得分等信息，而不需要访问玩家 A 的 PlayerController。

## 三、最重要：它们之间的实际关联关系

理解下面这张逻辑关系图，比单纯记住继承关系更重要。

```
                   玩家 A
                     │
          ┌──────────┴───────────┐
          │                      │
          ▼                      ▼
   APlayerController        APlayerState
     （控制逻辑）             （玩家数据）
          │                      │
          │ Possess              │ 关联
          ▼                      │
       APawn ◄───────────────────┘
          ▲
          │ 继承
          │
     ACharacter
      （角色实体）
          │
          ├── CapsuleComponent  碰撞
          ├── SkeletalMesh      模型
          ├── CharacterMovement 移动
          ├── AbilitySystem     技能（可选）
          └── CombatComponent   战斗（自定义）
```

这里有三种关系。

第一种：PlayerController 与 Pawn 是控制关系。

```
// PlayerController 获取自己控制的 Pawn
APawn* Pawn = PlayerController->GetPawn();

// Pawn 获取控制自己的 Controller
AController* Controller = Pawn->GetController();
```

第二种：Pawn 与 Character 是继承关系。

```
// Character 本身也是 Pawn 和 Actor
ACharacter* Character = ...;

APawn* Pawn = Character;
AActor* Actor = Character;
```

第三种：PlayerState 与 Pawn 是数据关联关系。

```
// 在 Character 内获取所属玩家的 PlayerState
AMyPlayerState* PS = GetPlayerState<AMyPlayerState>();

if (PS)
{
    int32 Score = PS->MatchScore;
}
```

Pawn 会关联被其玩家控制器拥有的 PlayerState，但 PlayerState 并不是 Pawn 的组件，也不需要附着在 Pawn 身上。

## 四、为什么 PlayerController 和 Character 要分开？

这是 UE Gameplay Framework 的一个重要设计。

假设你在制作一款类似《鸣潮》的动作游戏。

玩家可以控制不同角色：

```
玩家 A
  │
  └── PlayerController
          │
          ├── Character_1（角色 1）
          │
          ├── Character_2（角色 2）
          │
          └── Character_3（角色 3）
```

在普通的直接控制模式下，同一时刻 PlayerController 通常只 Possess 一个 Pawn。

<img width="737" height="296" alt="image" src="https://github.com/user-attachments/assets/548eb34c-270d-422d-8329-3e778dbab100" />


这种设计带来三个好处：

- 控制与身体分离：切换角色时可以保留玩家控制器。
    
- 方便死亡重生：旧 Character 被销毁后，PlayerController 可以控制新生成的 Character。
    
- 方便扩展：例如控制无人机、驾驶车辆、附身其他角色。
    

### C++ 切换角色示例

假设服务器已经生成了一个新角色：

```
void AMyPlayerController::SwitchCharacter(
    ACharacter* NewCharacter)
{
    // Possess 必须在具有权威性的服务器上执行
    if (!HasAuthority() || !NewCharacter)
    {
        return;
    }

    // 原本控制 CharacterA
    APawn* OldPawn = GetPawn();

    // 切换到 CharacterB
    Possess(NewCharacter);

    // OldPawn 可以保留在场景中
    // 不一定需要 Destroy
}
```

`Possess()` 会处理当前控制目标的切换。客户端发起切换请求时，通常通过 Server RPC 请求服务器执行，而不是在普通客户端直接调用。

## 五、玩家死亡、重生时，哪些对象会被销毁？

这是理解 `PlayerState` 作用的最好例子。

假设玩家进入一场多人战斗，初始具有以下对象：

```
PlayerController_A
    │
    ├── PlayerState_A
    │      ├── KillCount = 5
    │      └── MatchScore = 100
    │
    └── Character_A
           ├── HP = 100
           └── Position = (100, 0, 0)
```

接下来玩家被怪物击杀。

1. 角色死亡
    
    `Character_A` 的 HP 变成 0，进入死亡流程，之后可能被销毁。PlayerController 和 PlayerState 通常继续存在。
    
2. 服务器生成新角色
    
    GameMode 负责或协调重生逻辑，生成一个新的 `Character_B`。
    
3. 重新建立控制关系
    
    PlayerController 通过 `Possess(Character_B)` 控制新的角色。
    
4. 恢复游戏
    
    新角色 HP 重新初始化为 100，但玩家的击杀数依然是 5，比赛得分依然是 100。
    

|对象|死亡重生后|原因|
|---|---|---|
|PlayerController|通常保留|玩家仍在游戏中|
|PlayerState|通常保留|玩家身份和比赛数据未改变|
|Character|通常重新生成|新的物理角色实体|
|Character HP|通常重新初始化|属于本次角色生命|
|PlayerState Score|通常保留|属于玩家在本场比赛的数据|

这里说的“保留”，针对的是同一局游戏内的普通死亡重生。断线、重新连接、切换服务器或旅行到新地图时，生命周期可能有所不同，需要额外处理。

## 六、多人网络同步中它们有什么区别？

在多人游戏中，这五个类最关键的区别，是它们分别存在于服务器和哪些客户端。

假设有一个服务器，玩家 A 和玩家 B 两个客户端。

<img width="769" height="248" alt="image" src="https://github.com/user-attachments/assets/84c4cbab-dc24-415b-aa69-80c3a9ecb542" />


典型联网情况下的对象分布。这里假设两个 Character 都配置了网络复制且与客户端相关；实际 Actor 复制还受到网络相关性等条件影响。

重点一：客户端 A 通常拿不到客户端 B 的 PlayerController。

因为远程玩家的 PlayerController 不会复制到其他普通客户端上。

重点二：客户端 A 可以访问客户端 B 的 PlayerState。

这样客户端 A 就能显示其他玩家的名字、等级、队伍、得分等数据。

重点三：Character 的网络同步与 PlayerState 的网络同步负责不同内容。

例如：

```
// Character 中
UPROPERTY(Replicated)
float CurrentHP = 100.0f;

// PlayerState 中
UPROPERTY(Replicated)
int32 KillCount = 0;
```

它们都可以复制到客户端，但是：

- `CurrentHP` 属于角色实体，与当前角色的生命周期关联。
    
- `KillCount` 属于玩家比赛数据，与玩家的生命周期关联。
    

上述自定义属性还需要在 C++ 中使用 `GetLifetimeReplicatedProps` 注册，并满足相应 Actor 的网络复制条件。

另外，PlayerController 和 Character 都是 Actor，但 Actor 并不是都会自动同步。不能因为继承了 Actor 就认为每个实例都必然会出现在所有客户端。

## 七、实际项目应该怎么分配变量与功能？

对于第三人称战斗游戏，可以参考以下架构：

|功能或数据|推荐位置|原因|
|---|---|---|
|处理玩家输入、角色切换|PlayerController|跟随玩家控制逻辑|
|玩家视角 ControlRotation|PlayerController|表示玩家控制朝向|
|角色世界位置、旋转|Character|表示实体状态|
|角色移动、跳跃|Character / MovementComponent|需要角色移动能力|
|角色当前 HP|Character 或属性组件|通常属于当前角色|
|玩家昵称、队伍|PlayerState|所有玩家需要读取|
|玩家比赛得分、击杀数|PlayerState|死亡重生不应该丢失|
|角色攻击、受击|Character / CombatComponent|属于角色行为|
|角色技能与属性|AbilitySystemComponent|GAS 管理|
|全局比赛规则|GameMode|服务器负责规则|
|全局比赛状态|GameState|向客户端同步比赛状态|

GAS 有一个值得特别注意的设计点：`AbilitySystemComponent`（技能系统组件）可以根据游戏需求放在 Character，也可以放在 PlayerState。

例如需要角色死亡后保留技能状态、或者频繁切换角色的项目，可以考虑把 ASC 放到 PlayerState；如果技能系统完全依附于单个角色实体，则可以放在 Character。两种方案对 AbilityActorInfo 初始化、OwnerActor、AvatarActor 的处理也不同。

### 补充：GameMode、GameState、PlayerState 的关系

这三个类容易混淆，可以理解为：

```
GameMode（制定并执行游戏规则）
    │
    │ 创建 / 配置
    ▼
GameState（整局游戏的共享状态）
    │
    └── PlayerArray
          │
          ├── PlayerState_A
          ├── PlayerState_B
          └── PlayerState_C
```

这里是职责和关联关系，而不是继承关系。

例如服务器负责判断比赛是否结束，GameState 保存当前比赛时间与队伍得分，PlayerState 保存每名玩家的个人得分。`AGameStateBase::PlayerArray` 可以访问当前玩家的 PlayerState。


## 八、一个容易忽略的点：Controller Rotation 和 Character Rotation 不一定相同

你之前接触的 `Control Rotation` 正是 PlayerController 和 Character 分离的一个典型体现。

```
// 控制器的朝向
FRotator ControlRotation =
    GetControlRotation();

// 当前 Character 的世界朝向
FRotator CharacterRotation =
    GetCharacter()->GetActorRotation();
```

两者可以不同。

例如，第三人称游戏中：

- 摄像机看向正前方。
    
- 玩家按 A 键向左移动。
    
- Character 根据移动方向转身。
    
- PlayerController 的 ControlRotation 依然保持摄像机的控制朝向。
    

因此，`ControlRotation` 更接近“玩家想看向或瞄准的方向”，`ActorRotation` 才是 Character 在世界中的实际旋转。

两者是否跟随，取决于 `bUseControllerRotationYaw`、`bOrientRotationToMovement` 等设置。

## 九、面试中如何总结？

如果面试官问这五个类之间的关系，可以这样回答：

> `Actor` 是 UE 世界对象的基础类。
> 
> `Pawn` 继承 Actor，表示可被 Controller 控制的实体；`Character` 继承 Pawn，并提供胶囊碰撞、骨骼网格体和 CharacterMovement 等角色功能。
> 
> `PlayerController` 继承 Controller，通过 Possess 控制 Pawn，负责玩家输入和控制逻辑；`PlayerState` 继承 Info，用于保存玩家级状态，并支持将玩家信息同步给其他客户端。
> 
> PlayerController 和 Pawn 解耦，使得玩家可以切换角色、死亡重生；PlayerState 和 Pawn 解耦，则让玩家数据可以独立于角色身体存在。

最后用一句话记忆：PlayerController 是操作者，Character 是被操纵的身体，PlayerState 是玩家的身份与比赛档案，Actor 则是它们共同的对象基础。
