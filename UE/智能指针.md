在 Unreal Engine（UE5）游戏客户端开发中，推荐优先使用 UE 提供的智能指针，而不是直接使用 C++ STL 的 `std::shared_ptr`、`std::unique_ptr` 等。

但是，最重要的不是 UE 指针与 C++ 原生智能指针之间的选择，而是要先判断：你管理的对象是不是 `UObject`。

这是 UE C++ 面试中的高频知识点。

## 一、先记住最重要的区别

UE 存在两套不同的内存管理机制：

- UObject 对象： 使用 UE 的 GC（Garbage Collection，垃圾回收）机制管理。
    
- 普通 C++ 对象： 使用 UE 智能指针的引用计数、独占所有权等机制管理，也可以使用标准 C++ 智能指针。
    

因此：

|对象类型|推荐的指针|管理方式|
|---|---|---|
|`UObject`、`AActor`、`UActorComponent`|`TObjectPtr`|UE GC 强引用追踪|
|只观察、不拥有的 UObject|`TWeakObjectPtr`|不阻止 GC|
|需要延迟加载的资源|`TSoftObjectPtr`|通过资源路径引用|
|非 UObject 持有 UObject 的强引用|`TStrongObjectPtr`|UE GC 强引用|
|普通 C++ 对象，独占所有权|`TUniquePtr`|RAII，自动释放|
|普通 C++ 对象，共享所有权|`TSharedPtr`|引用计数|
|普通 C++ 对象，不允许为空的共享引用|`TSharedRef`|引用计数|
|普通 C++ 对象，非拥有关系|`TWeakPtr`|弱引用|

特别注意：`TSharedPtr` 和 `TObjectPtr` 虽然都属于 UE 提供的指针类型，但底层管理机制完全不同。

Epic 官方明确说明，UE 的共享智能指针系统不适用于 `UObject`，因为 `UObject` 拥有独立的 GC 管理机制。

## 二、UE 指针与 C++ 标准智能指针对比

|UE 指针|标准 C++ 对应类型|主要区别|
|---|---|---|
|`TSharedPtr<T>`|`std::shared_ptr<T>`|都使用共享所有权和引用计数|
|`TWeakPtr<T>`|`std::weak_ptr<T>`|都不会增加强引用计数|
|`TUniquePtr<T>`|`std::unique_ptr<T>`|都表示独占所有权|
|`TSharedRef<T>`|无直接对应|UE 提供的不可为空共享引用|
|`TObjectPtr<T>`|无对应|为 UObject GC 设计|
|`TWeakObjectPtr<T>`|无对应|UObject 专用弱引用|
|`TSoftObjectPtr<T>`|无对应|可按需加载资源的软引用|

对于普通 C++ 对象，两套指针都可以使用，但在 UE 项目中优先采用 UE 类型，能够更方便地与引擎 API、Slate UI、项目代码和 UE 的容器体系配合。

对于需要独立于 UE 编译的公共 C++ 库、第三方库或者明确要求 `std::shared_ptr` 的接口，使用标准库智能指针也是合理的。

## 三、UE 项目中的实际使用示例

### 1. UObject：使用 TObjectPtr、TWeakObjectPtr

例如战斗角色中，持有 GAS 组件、锁定目标和技能资源：

```
UCLASS()
class AMyCharacter : public ACharacter
{
    GENERATED_BODY()

public:
    // 1. 强引用：角色持有的 GAS 组件
    // UPROPERTY 让 GC 能追踪这个引用
    UPROPERTY()
    TObjectPtr<UAbilitySystemComponent> ASC;

    // 2. 弱引用：当前锁定的敌人
    // 敌人销毁时，不会因该引用而阻止销毁
    TWeakObjectPtr<AActor> LockTarget;

    // 3. 软引用：攻击蒙太奇资源
    // 不会仅因为保存了资源路径就强制加载资源
    UPROPERTY(EditDefaultsOnly)
    TSoftObjectPtr<UAnimMontage> AttackMontage;
};
```

使用弱引用时：

```
// 获取当前仍有效的锁定目标
if (AActor* Target = LockTarget.Get())
{
    // 目标有效，执行攻击或锁定逻辑
}
```

注意两个容易出错的地方：

- `TObjectPtr` 只有被 GC 正确追踪时才能形成有效强引用。普通 `UCLASS` 成员通常需要添加 `UPROPERTY()`。
    
- `TSoftObjectPtr` 不会自动完成资源加载，也不会一直保持已加载资源存活。需要结合资源加载系统管理。
    

### 2. 普通 C++ 对象：使用 TSharedPtr、TUniquePtr

假设有一个普通战斗数据结构：

```
// 普通 C++ 结构体，不继承 UObject
struct FCombatData
{
    float Attack = 100.f;
    float Defense = 50.f;
};
```

使用 UE 的智能指针：

```
// 独占所有权
TUniquePtr<FCombatData> Data1 =
    MakeUnique<FCombatData>();

// 共享所有权
TSharedPtr<FCombatData> Data2 =
    MakeShared<FCombatData>();

// 弱引用，不增加强引用计数
TWeakPtr<FCombatData> WeakData = Data2;

// 尝试获取有效的共享引用
if (TSharedPtr<FCombatData> Pinned = WeakData.Pin())
{
    float Attack = Pinned->Attack;
}
```

这种情况下，也可以使用：

```
std::unique_ptr<FCombatData> Data1 =
    std::make_unique<FCombatData>();

std::shared_ptr<FCombatData> Data2 =
    std::make_shared<FCombatData>();
```

两种方案都能正确管理普通 C++ 对象，但同一个对象不要同时交给两套独立的共享所有权机制管理，否则可能造成重复释放。

## 四、面试中容易问到的三个问题

Q1：能不能使用 TSharedPtr 管理 UObject？

不能将它作为 UObject 的所有权管理方案。

```
// 错误用法
TSharedPtr<UObject> Obj;
```

UObject 应通过 `NewObject`、`SpawnActor` 等引擎接口创建，并通过 GC 体系管理。

Q2：为什么 TObjectPtr 不能完全替代 TSharedPtr？

因为两者解决的问题不一样：

- `TObjectPtr` 依赖 UObject 的垃圾回收体系。
    
- `TSharedPtr` 使用引用计数，在最后一个共享所有者释放后销毁普通 C++ 对象。
    

这两种生命周期机制不能直接混用。

Q3：TSharedPtr 是线程安全的吗？

默认不能按跨线程共享来使用。UE 提供线程安全引用计数模式：

```
TSharedPtr<FCombatData, ESPMode::ThreadSafe> Data;
```

但注意，引用计数的线程安全不等于对象内部数据的线程安全。多个线程同时修改 `Data->Attack`，仍然需要同步措施，例如互斥锁。

## 五、UE 游戏客户端开发的选择原则

需要持有或者引用什么类型的对象？

UObject 派生对象

长期强引用：`UPROPERTY() TObjectPtr`

不拥有目标：`TWeakObjectPtr`

资源按需加载：`TSoftObjectPtr`

非 UObject 持有强引用：`TStrongObjectPtr`

普通 C++ 对象

独占所有权：`TUniquePtr`

共享所有权：`TSharedPtr`

不拥有对象：`TWeakPtr`

共享且不可为空：`TSharedRef`

最后再补充一点：UE 并不是任何地方都需要智能指针。

例如：

```
AActor* Target = GetOwner();
```

这种函数内临时使用的非拥有指针，在能保证对象有效的前提下完全正常，没有必要强行改成智能指针。

面试时可以这样总结：

> 在 UE 开发中，我会优先使用引擎提供的指针体系。对于 UObject 派生类型，使用 UObject GC 兼容的 TObjectPtr、TWeakObjectPtr、TSoftObjectPtr 等；对于普通 C++ 对象，根据所有权关系选择 TUniquePtr、TSharedPtr 或 TWeakPtr。标准 C++ 智能指针主要用于第三方库及独立于 UE 的 C++ 模块，不会用共享指针去管理 UObject。

这就是 UE5 游戏客户端最常用、也最值得掌握的指针选择原则。
